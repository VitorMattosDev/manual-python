54  Metaclasses e __init_subclass__: quando (não) usar

O Capítulo 52 deixou uma pergunta em aberto, e ela custa caro em produção. O registro de coletores funciona:

@coletor("snmp")
class Snmp:
    pass


class SnmpV3(Snmp):
    pass
com decorador de classe:
  registrados      : ['snmp']
  SnmpV3 registrado? False

Alguém subclassificou Snmp para tratar a versão 3 do protocolo, e a classe nova simplesmente não existe para o resto do sistema. Nenhum erro: o registro tem uma entrada, o código que procura por protocolo não encontra o novo e cai no caminho padrão. O defeito aparece semanas depois, como “a coleta v3 não está rodando”.

A causa é a do capítulo anterior: decorador de classe não é herdado. Ele age uma vez, sobre a classe que o usa, e a subclasse nasce sem ele. Para que um comportamento valha automaticamente para toda a descendência, é preciso agir num momento diferente — durante a criação de cada classe filha.

Este capítulo fecha o Volume 8 com os dois mecanismos que fazem isso, na ordem em que devem ser considerados: __init_subclass__, que resolve a maioria dos casos, e as metaclasses, que resolvem o resto e cobram por isso.

54.1 __init_subclass__: o gancho que basta

REGISTRO = {}


class Coletor:
    def __init_subclass__(cls, /, protocolo=None, **kwargs):
        super().__init_subclass__(**kwargs)
        if protocolo is None:
            protocolo = cls.__name__.lower()
        cls.protocolo = protocolo
        REGISTRO[protocolo] = cls


class Telnet(Coletor, protocolo="telnet"):
    pass


class Ssh(Coletor):
    pass


class SshSeguro(Ssh, protocolo="ssh-fips"):
    pass
com __init_subclass__:
  registrados : ['ssh', 'ssh-fips', 'telnet']
  neto entrou? True
  atributo    : ssh-fips
  a base entra no registro? False
  tipo do gancho: classmethod

Três classes registradas, incluindo o neto — SshSeguro herda de Ssh, que herda de Coletor, e o gancho foi chamado do mesmo jeito. É exatamente o que faltava.

Quatro pontos do código merecem nota.

O gancho é chamado na classe-mãe, recebendo a filha como cls. Por isso a própria Coletor não entra no registro: ninguém foi criado como subclasse dela ainda quando ela nasceu. Se a base também devesse ser registrada, isso é feito à mão, fora da classe.

__init_subclass__ é implicitamente um classmethod — a última linha da saída confirma. Escrever @classmethod em cima dele é redundante, e não escrever não é erro.

A palavra-chave no class é o recurso mais elegante: class Telnet(Coletor, protocolo="telnet") passa protocolo="telnet" direto para o gancho. É como Enum recebe configuração e como bibliotecas de ORM declaram nome de tabela sem um atributo mágico no corpo. Argumentos não consumidos devem ser repassados com super().__init_subclass__(**kwargs), senão hierarquias com múltiplas bases quebram.

E a barra na assinatura (cls, /, protocolo=None) marca cls como só-posicional, para que uma subclasse possa ter uma palavra-chave chamada cls sem colidir. É detalhe, mas é o que a documentação recomenda.

__init_subclass__ chegou no Python 3.6 pela PEP 487 — a mesma PEP do __set_name__ do Capítulo 53. As duas foram criadas com o mesmo propósito declarado: eliminar a maior parte dos usos legítimos de metaclasse. Antes delas, registrar subclasses ou dar nome a descritores exigia uma metaclasse. Hoje não exige, e é por isso que a ordem de consideração começa aqui.

54.2 Classes são objetos

Para entender o que sobra, é preciso aceitar uma ideia que o resto do manual vinha adiando:

type de uma instancia : Leitura
type da classe        : type
type de type          : type
a classe e um objeto? : True
e type e subclasse de object? True

Uma instância é do tipo da sua classe; a classe é do tipo type. Uma classe é um objeto, criado em tempo de execução, que pode ser guardado numa variável, passado como argumento e — foi isso que os decoradores de classe fizeram — modificado depois de pronto.

E se type é o que cria classes, chamá-lo com três argumentos cria uma:

Dinamica = type(
    "Dinamica",
    (Leitura,),
    {"unidade": "mW", "extra": lambda self: "veio do type()"},
)
classe criada por type(): Dinamica
  herdou o metodo       : leitura em mW
  atributo proprio      : veio do type()
  MRO                   : ['Dinamica', 'Leitura', 'object']
  e uma Leitura?        : True

as duas formas sao equivalentes:
  class X: ... -> <class 'type'>
  type(nome, bases, ns) -> <class 'type'>

Nome, tupla de bases, dicionário do corpo. A instrução class é açúcar para essa chamada — é literalmente isso que o interpretador faz. Uma classe criada assim é indistinguível de uma escrita com class: mesmo MRO, mesma herança, mesmo isinstance.

Uma metaclasse é uma subclasse de type. Se type é a fábrica padrão de classes, uma metaclasse é uma fábrica sua, com o comportamento que você quiser.

54.3 A ordem completa da criação

Instrumentando todos os ganchos de uma vez, a sequência aparece inteira:

criando a subclasse:
   Meta.__prepare__
   corpo da classe executado
   Meta.__new__  (antes de type.__new__)
   __set_name__ de campo
   Base.__init_subclass__
   Meta.__new__  (depois de type.__new__)
   Meta.__init__
   decorador de classe

a metaclasse foi herdada: Meta

Sete momentos, e cada capítulo deste volume ocupa um deles. Repare que __set_name__ e __init_subclass__ acontecem dentro de type.__new__ — são chamados pelo próprio construtor de tipos, o que explica por que funcionam sem nenhuma metaclasse. E o decorador de classe é o último de todos, recebendo a classe já completamente formada.

A linha final é a diferença que decide entre as duas ferramentas: a metaclasse é herdada. Filha não declarou metaclass=Meta; ela herdou de Base, e com isso herdou a metaclasse. Todo o galho da hierarquia passa pelo mesmo processo, para sempre, sem que ninguém precise lembrar de nada. É o poder e é o problema.

54.4 O que só a metaclasse resolve

Sobram três situações, todas envolvendo recusar ou reescrever a classe antes de ela existir.

A primeira é validar o corpo e impedir a criação:

class ExigeDocstring(type):
    def __new__(mcls, nome, bases, ns, **kwargs):
        if bases:
            faltando = [
                k for k, v in ns.items()
                if callable(v) and not k.startswith("_") and not v.__doc__
            ]
            if faltando:
                raise TypeError(
                    f"{nome}: metodos sem docstring: {', '.join(faltando)}"
                )
        return super().__new__(mcls, nome, bases, ns)
classe boa criada: Boa
classe ruim recusada: Ruim: metodos sem docstring: ler, gravar

O erro acontece na importação do módulo, não na primeira chamada. É o mesmo argumento do Capítulo 47 levado ao extremo: quanto mais cedo o erro, mais barato. __init_subclass__ também consegue recusar — mas só depois de a classe existir, o que deixa um objeto meio-construído acessível em casos de captura de exceção.

A segunda é __prepare__, o único gancho que age antes de o corpo da classe rodar. Ele devolve o dicionário onde as definições serão gravadas, e um dicionário próprio vê cada nome sendo definido:

class Duplicado(dict):
    def __setitem__(self, chave, valor):
        if chave in self and not chave.startswith("__"):
            raise TypeError(f"nome '{chave}' definido duas vezes")
        super().__setitem__(chave, valor)
__prepare__ pegou: nome 'processar' definido duas vezes

Dois métodos com o mesmo nome numa classe é um erro real e silencioso — o segundo sobrescreve o primeiro, e Python não reclama. Nenhuma outra ferramenta pega isso, porque quando a classe fica pronta o primeiro processar já não existe. Esse é o tipo de coisa para a qual __prepare__ existe. (É também como enum.Enum proíbe valores repetidos e como classes com ordem de definição significativa a preservam.)

A terceira é alterar o comportamento da própria classe como objeto: __instancecheck__ e __subclasshook__ para mudar isinstance, __call__ na metaclasse para interceptar a instanciação, __repr__ na metaclasse para mudar como a classe se imprime. É assim que ABCMeta funciona — a ABC do Capítulo 47 é uma classe cuja metaclasse redefine isinstance.

54.5 O custo: conflito de metaclasses

E aqui está a fatura:

metaclasse de ABC     : ABCMeta
metaclasse da minha   : MinhaMeta

juntando as duas:
  TypeError: metaclass conflict: the metaclass of a derived class must be a (non-strict) subclass of the metaclasses of all its bases

Uma classe só pode ter uma metaclasse, e ela precisa ser compatível com as de todas as bases. Herdar de uma classe sua com metaclasse própria e de uma ABC ao mesmo tempo é um erro de tipo — não porque as duas façam coisas incompatíveis, mas porque o mecanismo não sabe combiná-las.

A saída existe, e é manual:

class MetaCombinada(MinhaMeta, ABCMeta):
    pass
com metaclasse combinada: MetaCombinada
  MRO da metaclasse     : ['MetaCombinada', 'MinhaMeta', 'ABCMeta', 'type', 'object']

Funciona — e observe o que aconteceu: agora existe uma hierarquia de metaclasses, com MRO próprio, que precisa ser mantida. Cada nova biblioteca que trouxer a própria metaclasse exige mais um cruzamento. É por isso que metaclasse é uma decisão de arquitetura de biblioteca, não uma técnica de código de aplicação: ela impõe uma restrição a todo mundo que herdar das suas classes, inclusive gente que você não conhece.

Some-se a isso que a metaclasse não aparece no corpo da classe que a sofre — Filha do exemplo não menciona Meta em lugar nenhum, e mesmo assim é validada por ela. Depurar comportamento que vem de uma metaclasse herdada três níveis acima é penoso, e é o motivo do conselho de Tim Peters que virou folclore: “metaclasses são magia mais profunda do que 99% dos usuários deveriam se preocupar. Se você está pensando se precisa de uma, não precisa.”

54.6 🐍 Jeito Pythônico

Suba a escada de baixo para cima. Herança, decorador de classe, __init_subclass__, metaclasse — nessa ordem de preferência, e desça só com motivo demonstrado.

Registro de subclasses é __init_subclass__, não decorador e não metaclasse.

# antipadrão: só a classe decorada entra no registro
@coletor("snmp")
class Snmp: ...
# pythônico: toda a descendência entra, para sempre
class Coletor:
    def __init_subclass__(cls, /, protocolo=None, **kwargs):
        super().__init_subclass__(**kwargs)
        REGISTRO[protocolo or cls.__name__.lower()] = cls

Sempre chame super().__init_subclass__(**kwargs), repassando o que não consumiu. Sem isso, hierarquias com várias bases quebram.

Não escreva @classmethod em __init_subclass__. Ele já é um, implicitamente.

Palavra-chave no class em vez de atributo mágico no corpo. class Telnet(Coletor, protocolo="telnet") é mais claro que um _protocolo = "telnet" que alguém precisa saber que existe.

Metaclasse é decisão de biblioteca, não de aplicação. Ela é herdada e pode tornar suas classes incombináveis com as de terceiros.

Se precisar mesmo, herde a metaclasse existente em vez de criar do zero — class MinhaMeta(ABCMeta) evita metade dos conflitos futuros.

__prepare__ só quando a ordem ou a duplicidade de nomes no corpo importa. É o único gancho que enxerga o corpo sendo construído.

Sobre versões:

  • Python 2.2 — metaclasses como as conhecemos, junto com as classes de novo estilo e type como fábrica.
  • Python 3.0 — a sintaxe passa a ser class C(metaclass=M), em vez do atributo __metaclass__.
  • Python 3.0 — __prepare__ (PEP 3115), e o namespace da classe passa a poder ser um mapeamento qualquer.
  • Python 3.6 — __init_subclass__ e __set_name__ (PEP 487), com o objetivo declarado de tornar a metaclasse desnecessária na maioria dos casos.
  • Python 3.6 — o dicionário do corpo passa a preservar a ordem de definição por padrão, o que dispensou __prepare__ para esse fim específico.
  • Python 3.12 — a sintaxe de genéricos (PEP 695) usa __type_params__, e classes genéricas deixam de exigir a metaclasse que Generic usava em versões antigas.

54.8 Resumo

  • Decorador de classe não é herdado: a subclasse nasce sem ele, e o sintoma é ausência silenciosa no registro, não erro.
  • __init_subclass__ é chamado na classe-mãe a cada subclasse criada, em toda a descendência, e resolve registro, validação e configuração sem metaclasse.
  • Ele é implicitamente um classmethod, recebe palavras-chave passadas na própria instrução class, e deve repassar o que não consumir com super().__init_subclass__(**kwargs).
  • A classe-base não é registrada pelo próprio gancho — ele só roda para subclasses.
  • Classes são objetos criados em tempo de execução: type(nome, bases, ns) produz uma classe indistinguível de uma escrita com class, e type(type) is type.
  • Uma metaclasse é uma subclasse de type: uma fábrica de classes própria.
  • A ordem de criação é __prepare__, corpo, Meta.__new__, __set_name__, __init_subclass__, Meta.__init__, decoradores — com os dois ganchos da PEP 487 rodando dentro de type.__new__, sem metaclasse nenhuma.
  • Só a metaclasse consegue recusar a criação da classe, trocar o dicionário onde o corpo é executado (__prepare__) e alterar isinstance — que é como ABCMeta funciona.
  • A metaclasse é herdada por toda a descendência e só pode haver uma: combinar duas hierarquias com metaclasses diferentes é TypeError, e exige criar à mão uma metaclasse que herde de ambas.
  • A escada de decisão é herança, decorador de classe, __init_subclass__, metaclasse — nessa ordem, descendo só quando o degrau acima comprovadamente não resolve.

Com isto fecha o Volume 8. A sintaxe da linguagem deixou de ser um conjunto de regras a decorar e passou a ser um conjunto de protocolos com nome: len() é __len__, for é __iter__ e __next__, @ é uma reatribuição, obj.x é uma ordem de precedência entre descritores, e class é uma chamada a type. O que parecia mágica virou mecanismo — e mecanismo se depura.

A Fase 2 termina aqui. O que vem a seguir muda de natureza: em vez de construir a linguagem por dentro, passa a usá-la com o que já vem pronto. A Fase 3 abre com a biblioteca padrão — os, datetime, collections, itertools, logging — e boa parte dela vai parecer familiar, porque Counter é um dict com __missing__, deque implementa o protocolo de contêiner, e itertools é um catálogo de geradores. O Volume 8 foi o que torna possível ler o código dessas bibliotecas em vez de apenas usá-las.
