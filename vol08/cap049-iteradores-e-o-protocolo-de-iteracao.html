49  Iteradores e o protocolo de iteração

O coletor de telemetria guardava as leituras numa lista. Quando o volume passou de alguns milhares para alguns milhões, alguém trocou a lista por uma classe que lê do arquivo sob demanda — mesma interface, for funcionando, memória sob controle. O relatório noturno continuou rodando e passou a mentir:

c = ColetaRuim([1, 2, 3, 4])

total = sum(c)
quantos = sum(1 for _ in c)
print("  total   :", total)
print("  quantos :", quantos)
print("  media   :", total / quantos if quantos else "divisao por zero")
  total   : 10
  quantos : 0
  media   : divisao por zero

A soma está certa. A contagem deu zero. E o mesmo objeto, no mesmo processo, sem ninguém ter mexido nele entre as duas linhas.

O Capítulo 48 mostrou que for é sintaxe apoiada em método especial, e que __getitem__ sozinho já faz um laço rodar. Este capítulo abre a caixa: o que exatamente o for chama, por que existem dois objetos envolvidos e não um, e por que confundi-los produz erros como esse — que não levantam exceção, não aparecem em teste com lista, e só se manifestam quando os dados ficam grandes o bastante para justificar a mudança que os causou.

49.1 O que o for faz de verdade

Um laço é açúcar sintático para uma sequência bem definida de chamadas:

leituras = [-29.8, -31.7, -21.4]

it = iter(leituras)
while True:
    try:
        v = next(it)
    except StopIteration:
        break
    print("   ", v)
--- o for de sempre
    -29.8
    -31.7
    -21.4
--- o mesmo laco, na mao
    iter() devolveu um list_iterator
    -29.8
    -31.7
    -21.4
    StopIteration: o laco termina aqui

Três passos. iter(obj) chama type(obj).__iter__() e recebe um iterador. next(it) chama type(it).__next__() e recebe o próximo valor. Quando não há próximo valor, __next__ levanta StopIteration, e o for trata essa exceção como fim normal — não é erro, é o sinal combinado de término.

Fora do laço, a exceção é sua para tratar — ou você pede um padrão:

--- e depois de esgotado
    next com padrao: acabou
    next com padrao: acabou
    next sem padrao: StopIteration de novo

Repare no detalhe fundamental: um iterador esgotado permanece esgotado. Não há como rebobinar, não há reset. Chamar next de novo levanta StopIteration de novo, para sempre. Essa é a regra que explica o bug da abertura.

49.2 Iterável não é iterador

A distinção que resolve tudo:

dois iter() da mesma lista sao o mesmo objeto? False
  avanca so o primeiro: -29.8
  o segundo nao mexeu : -29.8
iter() de um iterador devolve ele mesmo?      True

a lista tem __iter__ ? True
a lista tem __next__ ? False
o iterador tem __iter__ ? True
o iterador tem __next__ ? True

lista    : Iterable True | Iterator False
iterador : Iterable True | Iterator True

next(lista): TypeError: 'list' object is not an iterator

Um iterável tem __iter__ e sabe fabricar iteradores. Um iterador tem __iter__ e __next__, e guarda a posição da leitura. A lista é iterável e não é iterador: next(lista) é um erro de tipo, com a mensagem dizendo exatamente isso.

Cada iter(lista) devolve um objeto novo, com contador próprio. É por isso que dois laços sobre a mesma lista são independentes, e por isso um laço aninhado sobre a mesma lista percorre tudo em cada nível.

E há a regra que costura o sistema: __iter__ de um iterador devolve self. Ela existe para que todo iterador também seja iterável, e assim funcione em for, em compreensão, em zip — em qualquer lugar que chame iter() sobre o que recebeu. Sem ela, for x in map(...) não funcionaria.

49.3 Escrevendo o par à mão

A coleção fabrica; o iterador conta:

class IteradorDeColeta:
    def __init__(self, itens):
        self._itens = itens
        self._i = 0

    def __iter__(self):
        return self

    def __next__(self):
        if self._i >= len(self._itens):
            raise StopIteration
        valor = self._itens[self._i]
        self._i += 1
        return valor


class Coleta:
    def __init__(self, leituras):
        self._itens = list(leituras)

    def __iter__(self):
        return IteradorDeColeta(self._itens)
primeira passada : [-29.8, -31.7, -21.4]
segunda passada  : [-29.8, -31.7, -21.4]
list()           : [-29.8, -31.7, -21.4]
max()            : -21.4
in               : True
laco aninhado    : 9 pares
  primeiros      : [(-29.8, -29.8), (-29.8, -31.7), (-29.8, -21.4)]

Toda passada recomeça, porque toda passada ganha um iterador novo. O laço aninhado dá os nove pares esperados. max, in e list funcionam porque todos passam por iter().

Note a divisão de estado: Coleta guarda os dados, IteradorDeColeta guarda a posição. É a razão de ser dos dois objetos. Um único objeto não pode ser percorrido por dois laços simultâneos, porque só tem um contador.

49.4 O erro de fundir os dois

Agora o código da abertura, inteiro:

class ColetaRuim:
    def __init__(self, leituras):
        self._itens = list(leituras)
        self._i = 0

    def __iter__(self):
        return self                      # <- o erro

    def __next__(self):
        if self._i >= len(self._itens):
            raise StopIteration
        valor = self._itens[self._i]
        self._i += 1
        return valor
primeira passada : [-29.8, -31.7, -21.4]
segunda passada  : []
max() depois     : sem dados
laco aninhado    : 2 pares -> [(-29.8, -31.7), (-29.8, -21.4)]

A primeira passada funciona perfeitamente. É por isso que o erro passa em revisão de código e em teste apressado. A segunda vem vazia, e o laço aninhado produz dois pares em vez de nove — o laço interno consumiu o resto do iterador na primeira volta do externo e não sobrou nada para as seguintes.

Nada disso levanta exceção. Coleção vazia é um estado legítimo, e o for sobre um iterador esgotado simplesmente não entra. O resultado é o relatório da abertura, com a divisão por zero — quando dá sorte. Quando não dá, é uma média silenciosamente calculada sobre um subconjunto.

Isso não quer dizer que iterador de um tiro seja errado — zip, map e o arquivo aberto são todos assim, e é o que permite processar sem carregar tudo. O erro é uma classe parecer uma coleção e se comportar como iterador. A regra prática: se o nome sugere um conjunto de coisas (Coleta, Registro, Inventario), __iter__ fabrica; se o nome sugere um fluxo (LeitorDeLog, FluxoDeEventos), devolver self é honesto — e vale documentar.

49.5 O protocolo antigo, por índice

O Capítulo 48 mostrou um laço funcionando com __getitem__ e sem __iter__. Vale ver o mecanismo em ação:

class Ramal:
    def __getitem__(self, i):
        print(f"    [__getitem__({i})]")
        return self._itens[i]
for sobre a classe sem __iter__:
    [__getitem__(0)]
    -29.8
    [__getitem__(1)]
    -31.7
    [__getitem__(2)]

iter() devolveu um iterator
isinstance(r, Iterable): False
hasattr(r, '__iter__') : False
mas iter(r) funciona   : -29.8

O iter() percebeu que não há __iter__, viu __getitem__ e devolveu um iterador de sequência genérico, que chama obj[0], obj[1], obj[2]… até um IndexError — visível na saída como a chamada __getitem__(2) sem valor impresso depois.

A linha desconfortável é a do meio: isinstance(r, Iterable) dá False para um objeto sobre o qual for funciona. A ABC verifica a presença de __iter__, e esse caminho de compatibilidade não tem __iter__. Se você precisa saber se algo é percorrível, a resposta confiável não é isinstance(x, Iterable) — é tentar iter(x) e tratar TypeError.

O protocolo por índice existe por compatibilidade com código anterior ao Python 2.2 e só serve para sequências indexadas por inteiros a partir de zero. Em código novo, escreva __iter__.

49.6 Preguiça: o que a biblioteca padrão devolve

Praticamente tudo que percorre em Python devolve iterador, não lista:

zip       -> zip
map       -> map
enumerate -> enumerate
reversed  -> list_reverseiterator

primeira leitura do zip: [(-29.8, 'a'), (-31.7, 'b'), (-21.4, 'c')]
segunda leitura do zip : []

zip não é uma lista de pares: é um iterador que produz pares sob demanda, e que se esgota. Consumi-lo duas vezes tem o mesmo resultado da ColetaRuim — e pela mesma razão.

A preguiça é o ponto:

map nao roda nada ate ser consumido:
    map criado, nada aconteceu
    [calculando 1]
    primeiro item: 2
    [calculando 2]
    [calculando 3]
    resto        : [4, 6]

Criar o map não executou a função nenhuma vez. Cada elemento só é calculado quando pedido. Isso é o que permite encadear transformações sobre um arquivo de dez gigabytes: nada é materializado, e a memória fica no tamanho de um registro. É também o que faz map(print, itens) não imprimir nada quando o resultado é descartado — armadilha clássica de quem trata map como um laço.

Um efeito colateral vira idioma quando entendido:

zip(it, it) agrupa aos pares: [(1, 2), (3, 4), (5, 6)]
zip strict: zip() argument 2 is shorter than argument 1

zip(it, it) recebe o mesmo iterador duas vezes. Para cada par, ele pede um item ao primeiro argumento e um ao segundo — que é a mesma fila. O resultado é agrupar em pares consecutivos. É o idioma zip(*[iter(x)] * n) para fatiar em blocos de n, e só funciona por causa do compartilhamento de estado.

O strict=True (Python 3.10) resolve um silêncio antigo: zip normal para no mais curto e descarta o resto sem avisar. Se as sequências deveriam ter o mesmo tamanho, strict=True transforma a divergência em ValueError.

49.7 iter() com dois argumentos

A forma menos conhecida de iter recebe um chamável e um sentinela, e produz um iterador que chama a função até ela devolver o valor de parada:

with amostra.open("rb") as f:
    blocos = list(iter(lambda: f.read(8), b""))
blocos de 8 octetos: 3
    00 01 02 03 04 05 06 07
    08 09 0a 0b 0c 0d 0e 0f
    10 11 12 13

ate o sentinela None: [-29.8, -31.7]
chamadas feitas     : 3

É a maneira idiomática de ler um arquivo binário em blocos de tamanho fixo, sem while True e sem break. O último bloco sai menor, o vazio encerra. A segunda parte mostra o caso geral com um sentinela None, e as três chamadas confirmam a semântica: a chamada que devolve o sentinela acontece, mas o valor não é entregue.

O contraponto está no próprio arquivo de texto, que já é iterável linha a linha:

with caminho.open() as f:
    for linha in f:          # não carrega o arquivo inteiro
        ...

Um arquivo aberto é um iterador de um tiro só, exatamente como a ColetaRuim — com a diferença de que isso é o comportamento certo e documentado para um fluxo. Percorrê-lo duas vezes exige f.seek(0).

49.8 🐍 Jeito Pythônico

__iter__ na coleção fabrica um iterador novo; __iter__ no iterador devolve self. Confundir os dois é o erro mais caro deste capítulo.

# antipadrão: coleção que se esgota
class Coleta:
    def __iter__(self):
        return self
# pythônico: cada passada ganha estado próprio
class Coleta:
    def __iter__(self):
        return IteradorDeColeta(self._itens)

Na prática, quase nunca se escreve a classe iteradora. Um __iter__ implementado como gerador faz o mesmo em três linhas — é o assunto do Capítulo 50, e é o que se usa em código real. Vale escrever o par à mão uma vez, para saber o que o gerador está gerando.

next(it, padrao) em vez de try/except StopIteration quando o fim é esperado e você está fora de um laço.

Nunca deixe StopIteration vazar de dentro de uma função consumida por um laço. Ela é o sinal de fim; solta no meio de outro código, encerra o laço de quem chamou como se os dados tivessem acabado.

Para saber se algo é percorrível, tente iter(x). isinstance(x, Iterable) diz False para objetos que só têm __getitem__.

Trate zip, map, filter e enumerate como fluxos de um tiro. Se precisar de duas passadas, materialize com list() — conscientemente.

zip(..., strict=True) quando os comprimentos deveriam bater. O padrão trunca em silêncio.

iter(chamavel, sentinela) para ler em blocos, em vez de while True com break.

Sobre versões:

  • Python 2.2 — o protocolo __iter__/__next__ (então next()) e a palavra iter (PEP 234); antes disso só existia o caminho por __getitem__.
  • Python 3.0 — o método passa a se chamar __next__ e a função embutida next() aparece.
  • Python 3.3 — StopIteration vazando de um gerador começa a ser tratada como erro (PEP 479), comportamento obrigatório no 3.7.
  • Python 3.10 — zip(..., strict=True) (PEP 618).
  • Python 3.12 — itertools.batched cobre o caso do zip(*[iter(x)] * n) com nome legível.

49.10 Resumo

  • for v in obj é açúcar para it = iter(obj) seguido de next(it) até StopIteration, que é sinal de fim e não erro.
  • São dois objetos: o iterável tem __iter__ e fabrica; o iterador tem __iter__ e __next__ e guarda a posição. next() numa lista é TypeError.
  • __iter__ de um iterador devolve self, para que todo iterador também seja iterável e funcione onde quer que iter() seja chamado.
  • Um iterador esgotado permanece esgotado: não há rebobinar. next(it, padrao) evita o try/except quando o fim é esperado.
  • Uma coleção cujo __iter__ devolve self funciona na primeira passada e falha em silêncio em todas as outras — segunda passada vazia, laço aninhado truncado, relatório com contagem zero.
  • Zerar o contador no __iter__ não conserta: o defeito é existir um único contador, que impede duas leituras simultâneas.
  • __getitem__ sem __iter__ ainda habilita for por um caminho de compatibilidade que chama índices até IndexError — mas isinstance(x, Iterable) devolve False nesse caso. Para saber se algo é percorrível, tente iter(x).
  • zip, map, filter, enumerate e reversed devolvem iteradores preguiçosos e de um tiro só; nada é calculado antes de ser pedido, e nada sobra para a segunda leitura.
  • zip(it, it) agrupa em pares consecutivos porque os dois argumentos são a mesma fila; strict=True (3.10) transforma comprimentos divergentes em erro em vez de truncar.
  • iter(chamavel, sentinela) lê em blocos até o valor de parada, e é a forma idiomática de consumir um arquivo binário em pedaços fixos.

Escrever a classe iteradora à mão deixou claro o mecanismo e também o incômodo: quinze linhas, um contador manual e uma exceção para dizer que acabou — tudo isso para descrever “devolva um item de cada vez”. O Capítulo 50 mostra a construção que reduz isso a uma função com yield, e que faz o interpretador guardar a posição por você.
