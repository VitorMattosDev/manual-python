73  Documentação: docstrings, doctest e Sphinx

O coletor de estações está formatado (Capítulo 67), tipado (Capítulo 68), testado (Capítulo 70) e depurável (Capítulo 72). Alguém novo entra na equipe, abre o REPL e digita:

help(estacao.validar)
validar(t: float) -> float

A anotação diz que entra um float e sai um float. Não diz o que a função faz, qual faixa aceita, o que acontece fora dela, nem por que ela existe. A pessoa vai ler o código-fonte — o que é aceitável para uma função de cinco linhas e inviável para um pacote de cinquenta módulos.

Documentação é a parte da qualidade que nenhuma ferramenta consegue verificar sozinha: o linter não sabe se sua explicação está certa, o verificador de tipos não lê português, e o teste não valida um parágrafo. Este capítulo trata do que é verificável — docstrings que o Python expõe, exemplos que se executam, referência que se gera — e do que não é, mas decide se alguém vai conseguir usar o que você escreveu.

73.1 Docstrings: o texto que o objeto carrega

Uma docstring é uma string literal como primeira instrução de um módulo, classe, função ou método. O Python a guarda em __doc__, e é dali que vêm o help(), a dica do editor e o gerador de documentação.

"""Leitura e validacao de temperaturas de estacoes meteorologicas."""

class LeituraInvalidaError(ValueError):
    """Temperatura fora da faixa fisicamente plausivel."""


def celsius_para_fahrenheit(c: float) -> float:
    """Converte uma temperatura de Celsius para Fahrenheit."""
    return c * 9 / 5 + 32
Help on function celsius_para_fahrenheit in module estacao:

celsius_para_fahrenheit(c: float) -> float
    Converte uma temperatura de Celsius para Fahrenheit.

A posição é rígida, com uma exceção que confunde. Comentário antes não atrapalha — o tokenizador o descarta, e a string continua sendo a primeira instrução:

# comentario antes
"""Docstring que continua sendo docstring."""
'Docstring que continua sendo docstring.'

Mas qualquer instrução de verdade antes dela quebra:

VERSAO = "1.0"
"""Docstring depois de uma atribuicao."""
None

A string virou um literal avaliado e descartado, e __doc__ ficou None. É o modo mais comum de “escrevi a documentação e o help não mostra” — e a variante de módulo é traiçoeira porque um import ou um from __future__ no topo já basta.

73.1.1 O que a PEP 257 pede

A PEP 257 é curta e vale as regras principais:

  • Sempre aspas triplas, mesmo numa linha só — para que expandir depois não exija reescrever.
  • A primeira linha é uma frase imperativa curta terminada em ponto: “Converte uma temperatura”, não “Esta função converte” nem “Conversão de temperatura”. Ela aparece sozinha em índices e listas.
  • Numa docstring de várias linhas, uma linha em branco depois do resumo, o corpo, e as aspas de fechamento em linha própria.
  • Documente o contrato, não a implementação. Parâmetros, retorno, exceções, efeitos colaterais. Como o laço interno funciona é assunto do código, e vai ficar desatualizado.

E a regra que decide o resto: não documente o que a assinatura já diz. Com c: float na assinatura, escrever “c (float): a temperatura” é duplicação que envelhece mal — o dia em que o tipo mudar, a docstring vira mentira. Anotações de tipo (Capítulo 68) tornaram obsoleta metade do que as docstrings antigas carregavam.

73.1.2 Os três dialetos

O Python não define formato para o corpo. Três convenções dominam:

Estilo Aparência Onde predomina
Google Args: / Returns: / Raises: com indentação o mais legível em código; padrão de fato hoje
NumPy seções com sublinhado de hifens ciência de dados, SciPy, pandas
reST :param x: / :returns: Sphinx puro, código mais antigo

O estilo Google, que este manual usa:

def validar(t: float) -> float:
    """Devolve ``t`` se estiver na faixa aceitavel.

    Args:
        t: Temperatura em graus Celsius.

    Returns:
        A propria temperatura, inalterada.

    Raises:
        LeituraInvalidaError: Se ``t`` estiver fora da faixa.
    """

Repare que Args: descreve o significado de t, não o tipo — o tipo está na assinatura. A escolha entre os três importa menos do que a consistência: o Sphinx entende os três (via extensão napoleon para Google e NumPy), e misturá-los no mesmo projeto quebra o gerador em silêncio, produzindo seções que não são reconhecidas e saem como texto corrido.

73.2 doctest: exemplo que não pode mentir

O maior problema da documentação é apodrecer. O código muda, o exemplo na docstring fica, e ninguém percebe porque nada quebra.

O doctest resolve isso lendo as docstrings, encontrando o que parece uma sessão do REPL, executando e comparando:

def celsius_para_fahrenheit(c: float) -> float:
    """Converte uma temperatura de Celsius para Fahrenheit.

    >>> celsius_para_fahrenheit(0.0)
    32.0
    >>> celsius_para_fahrenheit(100.0)
    212.0
    >>> celsius_para_fahrenheit(-29.8)
    -21.64
    """
    return c * 9 / 5 + 32
python -m doctest estacao.py -v
   3 tests in estacao.celsius_para_fahrenheit
   1 test in estacao.resumir
   2 tests in estacao.validar
6 tests in 5 items.
6 passed.
Test passed.

Sem -v, o sucesso é silencioso — o comando não imprime nada e sai com status 0.

Exceções também funcionam, com o traceback abreviado por ...:

    """
    >>> validar(200.0)
    Traceback (most recent call last):
        ...
    estacao.LeituraInvalidaError: fora da faixa: 200.0
    """

E, para integrar à suíte do Capítulo 70, o pytest coleta doctests como testes normais:

pytest --doctest-modules
...                                                                      [100%]
3 passed in 0.13s

Uma linha no addopts do pyproject.toml e todo exemplo da sua documentação passa a ser verificado no CI. É o único mecanismo que impede a documentação de mentir.

73.2.1 As cinco armadilhas

O doctest compara texto exato, e isso o torna frágil de maneiras específicas:

def soma_float():
    """
    >>> 0.1 + 0.2
    0.3
    """


def conjunto():
    """
    >>> {"c", "a", "b"}
    {'a', 'b', 'c'}
    """


def objeto():
    """
    >>> object()
    <object object at 0x7f0000000000>
    """
Failed example:
    {"c", "a", "b"}
Expected:
    {'a', 'b', 'c'}
Got:
    {'b', 'a', 'c'}
**********************************************************************
Failed example:
    object()
Expected:
    <object object at 0x7f0000000000>
Got:
    <object object at 0x0000021D68150830>
**********************************************************************
Failed example:
    0.1 + 0.2
Expected:
    0.3
Got:
    0.30000000000000004
  1. Ponto flutuante (Capítulo 10): use round(...), uma comparação booleana, ou valores que tenham representação exata.
  2. Ordem de set varia entre execuções: use sorted(...).
  3. Endereço de objeto e caminho absoluto mudam sempre: use a diretiva # doctest: +ELLIPSIS e 0x... no lugar do endereço.
  4. Espaço em branco conta. Uma linha de saída vazia encerra o exemplo — para uma saída que contém linha em branco, use <BLANKLINE>.
  5. Barra invertida na docstring é interpretada pelo Python antes do doctest ver. Um exemplo com print("a\n\nb") numa docstring comum vira um print("a seguido de quebras de linha reais, e o doctest reporta SyntaxError: unterminated string literal — um erro que não tem relação aparente com o que você escreveu. A correção é a docstring crua, r"""...""", e a regra prática é usá-la sempre que houver \ em qualquer lugar do texto.
def com_vazia():
    r"""
    >>> print("a\n\nb")
    a
    <BLANKLINE>
    b
    """

Com o r, passa. Sem ele, falha com um erro de sintaxe.

As diretivas resolvem os casos que não dá para evitar:

    >>> object()  # doctest: +ELLIPSIS
    <object object at 0x...>

    >>> import pathlib; str(pathlib.Path("a") / "b")  # doctest: +SKIP
    'a/b'

Com +ELLIPSIS, o exemplo passa. O +SKIP documenta sem executar — a saída aqui depende do sistema operacional, e o exemplo existe para o leitor, não para o CI.

E a regra que vem de tudo isso: doctest é para exemplo didático, não para suíte de testes. Um exemplo de três linhas que mostra o uso típico é perfeito; testar oito casos de fronteira em docstring produz uma docstring ilegível e um teste ruim. As fronteiras vão para parametrize (Capítulo 71).

73.3 Gerando a referência

73.3.1 Sphinx

O Sphinx é o gerador que documenta o próprio Python. Um projeto mínimo:

pip install sphinx
mkdir docs

docs/conf.py:

import os
import sys

sys.path.insert(0, os.path.abspath(".."))

project = "Coletor"
extensions = [
    "sphinx.ext.autodoc",     # extrai docstrings do codigo
    "sphinx.ext.napoleon",    # entende os estilos Google e NumPy
    "sphinx.ext.doctest",     # roda os exemplos
    "sphinx.ext.viewcode",    # link para o fonte
]
html_theme = "alabaster"
autodoc_typehints = "description"

docs/index.rst:

Coletor
=======

.. automodule:: estacao
   :members:
   :undoc-members:
   :show-inheritance:
sphinx-build -b html docs docs/_build
build succeeded.

The HTML pages are in docs\_build.

Quatro extensões fazem o trabalho todo. autodoc é a essencial: ele importa o módulo e lê os objetos, o que significa que o código precisa importar sem efeito colateral — um print no nível do módulo aparece na saída do build, e uma conexão de banco aberta no import faz a documentação depender do banco. napoleon traduz Google e NumPy para o dialeto interno; sem ela, um bloco Args: sai como texto corrido. E autodoc_typehints = "description" move as anotações da assinatura para a descrição dos parâmetros, o que evita assinaturas ilegíveis quando os tipos são compostos.

73.3.2 A armadilha do sphinx.ext.doctest

Rodar os exemplos pelo Sphinx não é a mesma coisa que rodá-los pelo doctest ou pelo pytest:

sphinx-build -b doctest docs docs/_doctest
6 tests in 1 item.
0 passed and 6 failed.

Seis passavam há dois parágrafos. O motivo está no relatório:

Failed example:
    celsius_para_fahrenheit(0.0)
Exception raised:
    NameError: name 'celsius_para_fahrenheit' is not defined

O doctest do Python executa os exemplos no espaço de nomes do módulo, onde a função existe. O builder do Sphinx os executa num espaço de nomes do documento, que começa vazio. A correção é declarar o preparo no .rst:

.. testsetup:: *

   from estacao import *

Vale conhecer o caso porque o sintoma — NameError em exemplos que passam em toda outra ferramenta — não sugere a causa. Na prática, a recomendação é rodar doctests por pytest --doctest-modules e deixar o Sphinx só gerando o site.

73.3.3 MkDocs, a alternativa

Sphinx usa reStructuredText por padrão, que é mais poderoso e menos familiar que Markdown. Para projeto novo, a combinação MkDocs + Material + mkdocstrings escreve tudo em Markdown, gera o mesmo tipo de referência a partir das docstrings, e tem uma curva de entrada bem menor. Sphinx continua ganhando em documentação grande, com internacionalização, saída em PDF e referências cruzadas entre projetos (intersphinx) — que é exatamente o caso do próprio CPython. Quem quiser Markdown dentro do Sphinx tem a extensão myst-parser.

73.4 Documentação não é só referência

Referência gerada de docstring responde “o que faz a função validar”. Ela não responde “como começo”, “como faço para X” nem “por que isso funciona assim”. O modelo Diátaxis, adotado pela documentação oficial do Python, separa quatro produtos com propósitos diferentes:

O erro clássico é escrever apenas referência e chamar de documentação. A pessoa que chega ao seu projeto precisa de um tutorial que funcione do começo ao fim sem escolhas; quem já usa precisa de guias práticos para tarefas concretas; e as decisões de projeto — por que a faixa vai até -90, por que o formato de configuração é TOML — só cabem em explicação.

Na raiz do repositório, o mínimo aceitável:

  • README.md — o que é, para que serve, como instalar, um exemplo que funciona. É a única página que a maioria vai ler.
  • CHANGELOG.md — o que mudou em cada versão, com atenção especial ao que quebrou.
  • CONTRIBUTING.md — como rodar os testes e abrir um PR, se você aceita contribuição.

73.5 🐍 Jeito Pythônico

Docstring é a fonte única da referência. Duplicar a assinatura num arquivo .md à parte garante que os dois vão divergir. A referência se gera; o que se escreve à mão é tutorial, guia e explicação.

Documente o contrato, não a implementação, e não repita a assinatura. Com anotações de tipo, Args: descreve significado e unidade (“temperatura em graus Celsius”), não (float). O que a assinatura não diz — o que acontece com entrada vazia, qual exceção sobe, se o argumento é modificado no lugar — é exatamente o que a docstring deve dizer.

Todo exemplo em docstring é um doctest, e roda no CI. --doctest-modules no addopts custa uma linha e é a única defesa real contra documentação obsoleta. Sem isso, seus exemplos são ficção testada por ninguém.

Um estilo por projeto. Google é a escolha razoável hoje: mais legível no código-fonte e bem suportado por napoleon e mkdocstrings. NumPy se o ecossistema ao redor for científico. O que não funciona é misturar.

Não documente o óbvio. """Retorna o nome.""" num método nome() é ruído que ninguém lê e todo mundo tem de rolar. Módulo, classe e função pública merecem docstring; um auxiliar privado de três linhas com nome bom não merece.

O README é a única página garantida. Ele precisa ter, na primeira tela, o que o projeto faz e um exemplo que roda copiado e colado. Um README que começa com o histórico do projeto e a lista de patrocinadores perdeu o leitor antes da instalação.

73.6 🧪 Laboratório

Você vai documentar um módulo, transformar os exemplos em testes que rodam no CI, e gerar um site de referência.

Passo 1 — ambiente.

mkdir lab-docs && cd lab-docs
python3.13 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
python -m pip install pytest sphinx

Passo 2 — o módulo sem documentação. Crie estacao.py com celsius_para_fahrenheit, validar e resumir (as três do capítulo), sem nenhuma docstring. Abra o REPL e rode help(estacao.validar): você vê a assinatura e nada mais. Guarde essa impressão — é o que outra pessoa encontra.

Passo 3 — docstring de módulo e de função. Acrescente uma docstring de módulo na primeira linha do arquivo e uma de uma linha em cada função. Rode help(estacao) e confirme que o texto aparece. Agora faça o teste que ensina a regra da posição, em duas partes. Primeiro ponha um comentário antes da docstring do módulo e confira print(estacao.__doc__): continua aparecendo, porque comentário não é instrução. Depois ponha uma atribuição (VERSAO = "1.0") antes dela:

None

Só a segunda quebra. A distinção importa porque a versão realista do defeito é um import no topo do arquivo, acima da docstring.

Passo 4 — o contrato completo, no estilo Google. Expanda validar com Args:, Returns: e Raises:. Resista a escrever o tipo em Args: — ele já está na assinatura.

Passo 5 — exemplos que rodam. Acrescente três exemplos >>> a celsius_para_fahrenheit e rode:

python -m doctest estacao.py -v
6 tests in 5 items.
6 passed.
Test passed.

Agora quebre a função de propósito (troque 9 / 5 por 9 / 4) e rode de novo sem -v:

Failed example:
    celsius_para_fahrenheit(100.0)
Expected:
    212.0
Got:
    257.0
--
Failed example:
    celsius_para_fahrenheit(-29.8)
Expected:
    -21.64
Got:
    -35.05

Cada exemplo que passou a mentir é apontado com o valor esperado e o obtido. Desfaça.

Passo 6 — as armadilhas, uma a uma. Escreva cinco funções cuja docstring contenha, respectivamente: 0.1 + 0.2 esperando 0.3; um set de três strings; um object() com endereço; uma saída com linha em branco no meio; e um exemplo com \n dentro de uma string. Rode python -m doctest.

Repare que a quinta falha com SyntaxError: unterminated string literal, e não com uma diferença de saída — é a docstring comum interpretando o \n antes do doctest ler. Conserte cada uma pelo caminho certo — round, sorted, +ELLIPSIS com 0x..., <BLANKLINE> e r""" — e confirme o silêncio.

Passo 7 — doctest na suíte. Acrescente ao pyproject.toml:

[tool.pytest.ini_options]
addopts = "-ra --doctest-modules"

Rode pytest. Os doctests aparecem como testes normais. Este é o passo que importa: a partir daqui, um exemplo desatualizado derruba o CI.

Passo 8 — o site de referência. Monte docs/conf.py e docs/index.rst como no capítulo e rode:

sphinx-build -b html docs docs/_build
build succeeded.

Abra docs/_build/index.html. Compare com o help() do passo 2: mesma fonte, saída navegável, com links para o código.

Passo 9 — a armadilha do builder de doctest. Rode sphinx-build -b doctest docs docs/_doctest e leia docs/_doctest/output.txt:

NameError: name 'celsius_para_fahrenheit' is not defined

Os mesmos exemplos que o pytest aprovou. Conserte acrescentando ao index.rst:

.. testsetup:: *

   from estacao import *

Rode outra vez e confirme os seis passando. E então decida conscientemente: manter os dois caminhos, ou rodar doctest só pelo pytest (o mais comum) e deixar o Sphinx gerando o site.

Passo 10 — o que nenhuma ferramenta gera. Escreva um README.md com quatro seções: o que o projeto faz em uma frase, como instalar, um exemplo que roda copiado e colado, e um link para a referência. Depois responda por escrito, em duas linhas, por que a faixa de temperatura vai de -90 a 60 — essa é a “explicação” do Diátaxis, e é a única coisa deste capítulo que nenhuma ferramenta jamais vai gerar por você.

73.7 Resumo

  • Uma docstring é a primeira instrução do módulo, classe ou função. Comentário antes não atrapalha; uma atribuição ou um import antes dela fazem __doc__ virar None. A PEP 257 pede aspas triplas sempre e uma primeira linha imperativa e curta.
  • Documente o contrato, não a implementação, e não repita o que a assinatura já diz: com anotações de tipo, Args: carrega significado e unidade, não o tipo.
  • Três dialetos (Google, NumPy, reST); Google é o padrão de fato hoje, sphinx.ext.napoleon entende os três, e misturá-los no mesmo projeto quebra o gerador em silêncio.
  • doctest é a única defesa contra documentação obsoleta: pytest --doctest-modules no addopts faz todo exemplo da documentação rodar no CI. Cuidado com as cinco armadilhas — ponto flutuante, ordem de set, endereço de objeto, espaço em branco e barra invertida — resolvidas com round, sorted, +ELLIPSIS, <BLANKLINE> e a docstring crua r""".
  • Sphinx com autodoc + napoleon gera a referência a partir do código; autodoc importa o módulo, então import com efeito colateral quebra o build. O builder -b doctest roda os exemplos num espaço de nomes vazio e exige .. testsetup:: — motivo pelo qual a prática comum é deixar os doctests com o pytest.
  • MkDocs + mkdocstrings é a alternativa em Markdown, mais simples para projeto novo; Sphinx ganha em documentação grande, PDF e intersphinx.
  • Referência é um dos quatro produtos do Diátaxis, e o único automatizável. Tutorial, guia prático e explicação alguém precisa escrever — e o README é a única página que a maioria vai ler.
