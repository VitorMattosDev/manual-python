68  Anotações de tipo: fundamentos e o módulo typing

Abra uma função qualquer de um projeto que você não escreveu:

def processar(dados, limite, modo):
    ...

Três perguntas sem resposta. dados é uma lista? Um dicionário? Um caminho de arquivo? limite é um número ou um objeto de configuração? modo é uma string, e se for, quais valores ela aceita? A resposta está espalhada entre a docstring (que pode estar desatualizada), o corpo da função (que você vai ter de ler inteiro) e os locais que a chamam (que você vai ter de procurar).

Anotações de tipo transformam essas três respostas em algo que fica na assinatura, que o editor lê para completar código, e que uma ferramenta verifica automaticamente contra todos os locais de chamada:

def processar(dados: list[float], limite: float, modo: Literal["media", "soma"]) -> float:
    ...

Este capítulo cobre a mecânica: o que uma anotação é (e, principalmente, o que ela não é), a sintaxe moderna do Python 3.13, os construtores do módulo typing que se usa todo dia, e como as anotações são avaliadas — um ponto que mudou de forma importante no 3.14. Genéricos, protocolos e a configuração do mypy são o capítulo seguinte.

68.1 Uma anotação não faz nada

Este é o ponto de partida e o mal-entendido mais comum. O Python não verifica anotações em tempo de execução. Ele as avalia como expressões, guarda o resultado num dicionário e segue em frente.

def media(valores: list[float]) -> float:
    return sum(valores) / len(valores)

print(media.__annotations__)
print(media([1, 2, 3]))
{'valores': list[float], 'return': <class 'float'>}
2.0

A anotação virou uma entrada em media.__annotations__. Nada mais. Chamar a função com o tipo errado não produz erro de tipo:

media(["a", "bb"])
TypeError: unsupported operand type(s) for +: 'int' and 'str'

Repare que o TypeError não veio da anotação — veio do sum tentando somar 0 + "a" lá dentro. A anotação list[float] foi ignorada por completo. Se a função fosse return valores[0], a chamada com strings devolveria "a" sem reclamação nenhuma.

Anotações também valem para variáveis, com ou sem valor atribuído:

TEMPERATURA_MINIMA: float = -40.0
estacoes: dict[str, float] = {}
sem_valor: int
{'TEMPERATURA_MINIMA': <class 'float'>, 'estacoes': dict[str, float], 'sem_valor': <class 'int'>}
sem_valor existe? False

O caso de sem_valor é peculiar e vale entender: a linha registra a anotação no __annotations__ do módulo sem criar a variável. sem_valor não existe; usá-lo levanta NameError. É a forma de declarar “este atributo terá este tipo” sem lhe dar um valor — útil em classes e em TypedDict.

68.1.1 Então para que servem?

Para um segundo leitor do arquivo, que nunca executa nada.

O contraste fica concreto com um arquivo que tem dois defeitos:

def media(valores: list[float]) -> float:
    return sum(valores) / len(valores)


def rotular(estacao: str, temperatura: float) -> str:
    return f"{estacao}: {temperatura:.1f} C"


leituras = [-29.8, -30.1, -28.4]
print(media(leituras))
print(rotular("onu-00043", media(leituras)))
print(rotular(-29.8, "onu-00043"))     # argumentos trocados
print(media(["a", "b"]))

O verificador de tipos lê o arquivo sem executá-lo:

mypy coletor.py
coletor.py:12: error: Argument 1 to "rotular" has incompatible type "float"; expected "str"  [arg-type]
coletor.py:12: error: Argument 2 to "rotular" has incompatible type "str"; expected "float"  [arg-type]
coletor.py:13: error: List item 0 has incompatible type "str"; expected "float"  [list-item]
coletor.py:13: error: List item 1 has incompatible type "str"; expected "float"  [list-item]
Found 4 errors in 1 file (checked 1 source file)

Quatro erros, com linha, posição e a explicação exata. O Python, executando o mesmo arquivo:

-29.433333333333334
onu-00043: -29.4 C
Traceback (most recent call last):
  File "coletor.py", line 12, in <module>
    print(rotular(-29.8, "onu-00043"))
  File "coletor.py", line 6, in rotular
    return f"{estacao}: {temperatura:.1f} C"
ValueError: Unknown format code 'f' for object of type 'str'

Três diferenças que resumem o valor da tipagem estática. Primeira: o programa produziu duas linhas de saída antes de falhar — num script que grava em banco, essas duas linhas já viraram efeito colateral permanente. Segunda: a mensagem é Unknown format code 'f', que aponta para o especificador de formato, não para os argumentos trocados que são a causa real. Terceira: o erro da linha 13 nunca chegou a acontecer, porque o programa morreu antes. O verificador achou os quatro de uma vez, em meio segundo, sem rodar nada.

68.2 A sintaxe moderna

A tipagem em Python acumulou dez anos de sintaxe, e boa parte do que se encontra em tutorial antigo está obsoleta. O que vale no 3.13:

68.2.1 Genéricos embutidos (3.9+)

Nada de typing.List, typing.Dict, typing.Tuple, typing.Set. Desde o Python 3.9 (PEP 585), os próprios tipos embutidos aceitam parâmetro:

def agrupar(leituras: list[float]) -> dict[str, list[float]]:
    ...

coordenadas: tuple[float, float] = (-15.79, -47.88)
codigos: set[str] = {"onu-00043"}

As formas do typing continuam funcionando por compatibilidade, mas estão obsoletas — é o UP006 e o UP035 que o Ruff apontou em Capítulo 67. Para coleções abstratas, a origem correta é collections.abc, não typing:

from collections.abc import Callable, Iterable, Iterator, Mapping, Sequence

68.2.2 União com barra (3.10+)

print(int | None)
print(Optional[int])
print(int | None == Optional[int])
print(type(int | None))
int | None
typing.Optional[int]
True
<class 'types.UnionType'>

X | None e Optional[X] são o mesmo tipo, e a primeira forma é a preferida. Note que Optional não significa “argumento opcional” — significa “pode ser None”. Um argumento com valor padrão não é automaticamente Optional:

# limite tem valor padrao, mas nunca e None: anotacao e int
def buscar(estacao: str, limite: int = 10) -> list[float]:
    ...

# desde pode chegar como None: aqui o `| None` e obrigatorio
def consultar(estacao: str, desde: str | None = None) -> list[float]:
    ...

O objeto produzido por | é um types.UnionType de verdade, e serve em isinstance:

print(isinstance(3, int | float))
print(isinstance("x", int | float))
True
False

68.2.3 Apelidos de tipo (3.12+)

Quando a mesma anotação composta aparece em cinco assinaturas, dê um nome a ela. A instrução type da PEP 695 faz isso:

type Celsius = float
type Registro = dict[str, float | str]

def converter(t: Celsius) -> Celsius: ...
Celsius <class 'typing.TypeAliasType'>
<class 'float'>
dict[str, float | str]

Celsius é um TypeAliasType, e o valor real fica em __value__. Antes do 3.12 escrevia-se Celsius: TypeAlias = float ou simplesmente Celsius = float; ambos ainda funcionam, e a segunda forma é ambígua justamente por ser indistinguível de uma atribuição comum.

Um apelido não cria um tipo novo: Celsius é float, e passar qualquer float onde se pede Celsius é aceito. Para um tipo realmente distinto — que impeça misturar Celsius com Fahrenheit — existe typing.NewType, assunto do próximo capítulo.

68.3 Os construtores que se usa todo dia

68.3.1 Any: a porta de saída

from typing import Any

def qualquer(x: Any) -> Any:
    return x

Any é compatível com tudo, nos dois sentidos: qualquer valor pode ir para um Any, e um Any pode ir para qualquer lugar. Isso o torna a válvula de escape do sistema — e também a forma mais eficiente de desligar a verificação sem perceber. Uma função que devolve Any contamina tudo que toca o resultado dela, silenciosamente.

object é frequentemente o que se queria dizer: também aceita qualquer valor, mas não permite usar o resultado sem antes estreitar o tipo. Se a intenção é “não sei o que é isso e vou verificar depois”, object é honesto; Any é uma promessa vazia.

68.3.2 Literal: quando os valores válidos são poucos e conhecidos

from typing import Literal

Modo = Literal["leitura", "escrita"]

def abrir(caminho: str, modo: Modo = "leitura") -> None: ...
typing.Literal['leitura', 'escrita']

É o construtor mais subestimado do typing. Ele transforma “modo é uma string” — informação quase inútil — em “modo é uma destas duas strings”, que o editor completa e o verificador confere. Para conjuntos maiores ou que precisem existir em tempo de execução, enum.Enum (Capítulo 46) é a escolha; Literal é para o caso pequeno e fechado.

68.3.3 Final: o que não deve ser reatribuído

from typing import Final

LIMITE: Final = 100

O verificador reclama de qualquer reatribuição de LIMITE. Em tempo de execução, nada impede — como todo o resto deste capítulo, é uma promessa verificada estaticamente, não uma constante de verdade.

68.3.4 Callable: funções como parâmetro

from collections.abc import Callable

def aplicar(f: Callable[[float], float], v: list[float]) -> list[float]:
    return [f(x) for x in v]

print(aplicar(lambda t: t * 2, [1.0, 2.0]))
[2.0, 4.0]
{'f': collections.abc.Callable[[float], float], 'v': list[float], 'return': list[float]}

A leitura de Callable[[float], float] é: uma chamada que recebe um float e devolve um float. A lista interna é a de parâmetros — Callable[[], int] não recebe nada, Callable[..., int] recebe qualquer coisa (as reticências são literais).

68.3.5 TypedDict: dicionário com forma conhecida

O coletor lê JSON, e JSON vira dicionário (Capítulo 62). dict[str, Any] descreve isso mal. TypedDict descreve bem:

from typing import TypedDict

class Leitura(TypedDict):
    estacao: str
    temperatura: float

x: Leitura = {"estacao": "onu-00043", "temperatura": -29.8}
print(x, type(x))
print(Leitura.__required_keys__)
{'estacao': 'onu-00043', 'temperatura': -29.8} <class 'dict'>
frozenset({'temperatura', 'estacao'})

Repare no type(x): é dict, um dicionário comum. TypedDict não cria classe nova nem custa nada em tempo de execução — descreve para o verificador quais chaves existem e de que tipo é cada valor. Acessar x["umidade"] vira erro estático; x["temperatura"] + 1 é aceito, enquanto x["estacao"] + 1 não é.

Quando os dados não vêm de JSON e você controla a estrutura, uma dataclass (Capítulo 46) costuma ser melhor: dá validação em tempo de execução, __repr__ e atributos com ponto. TypedDict é para o caso em que o dicionário já existe e você só quer descrevê-lo.

68.4 Quando a anotação é avaliada

Este é o canto escuro do assunto, e ele mudou recentemente.

Até o Python 3.13, anotações são expressões avaliadas na hora em que a definição é executada. Isso quebra referências para frente:

class Config:
    limite: NaoDefinidoAinda
Python 3.13.15
Traceback (most recent call last):
  ...
NameError: name 'NaoDefinidoAinda' is not defined

A saída clássica era escrever a anotação como string — limite: "NaoDefinidoAinda" — ou pôr from __future__ import annotations no topo do arquivo, que faz o Python guardar todas as anotações como strings sem avaliá-las. Quem precisa do valor real usa typing.get_type_hints, que resolve as strings no contexto certo:

def futura(x: "list[int]") -> "str":
    return str(x)

print("cru      :", futura.__annotations__)
print("resolvido:", get_type_hints(futura))
cru      : {'x': 'list[int]', 'return': 'str'}
resolvido: {'x': list[int], 'return': <class 'str'>}

O Python 3.14 muda o modelo (PEP 649): as anotações passam a ser avaliadas sob demanda, na primeira vez que alguém acessa __annotations__. O mesmo arquivo, nas duas versões:

=== Python 3.13 ===
NameError: name 'NaoDefinidoAinda' is not defined      <- ao criar a classe

=== Python 3.14 ===
classe criada sem erro
NameError: name 'NaoDefinidoAinda' is not defined      <- ao ler __annotations__

No 3.14 a classe é construída sem problema; o erro só aparece quando alguém pede as anotações. Isso resolve referência para frente sem from __future__ e sem aspas — e é o motivo pelo qual from __future__ import annotations, que já foi conselho universal, está em caminho de se tornar desnecessário. Em código que precisa rodar em 3.13 e anteriores, ele continua sendo a forma correta de escrever uma referência para frente.

68.5 🐍 Jeito Pythônico

Anotar o contorno, não o interior. O lugar onde a anotação paga é a fronteira: assinatura de função pública, atributo de classe, retorno. Anotar toda variável local é ruído — contador: int = 0 não informa nada que contador = 0 já não diga, e o verificador infere sozinho. A regra prática é anotar o que outra pessoa (ou outro módulo) vai consumir.

Sintaxe moderna, sem exceção. list[str] e não List[str]; X | None e não Optional[X]; collections.abc.Callable e não typing.Callable. Todas as formas antigas continuam funcionando, e é exatamente por isso que elas se perpetuam em código novo copiado de tutorial de 2018. O UP do Ruff (Capítulo 67) pega isso automaticamente, desde que target-version esteja correto.

Any é uma decisão, não um padrão. Escrever Any porque o tipo é complicado é abrir mão da verificação naquele ponto e em tudo que depende dele. Quando você não sabe o tipo, object é mais honesto; quando o tipo é “um dos três”, Union ou Literal resolvem; quando é “qualquer coisa que tenha o método X”, é Protocol, tema do próximo capítulo.

Anotação não valida entrada. Esse é o erro conceitual mais caro. Um def criar(idade: int) não impede que chegue "quarenta" de um formulário web. Validação em tempo de execução, para dados que vêm de fora do programa, é trabalho de pydantic (Volume 14) ou de código de verificação escrito à mão. Tipagem estática cobre o que você escreveu; ela não cobre o que o usuário digitou.

Tipar código existente é incremental — e a meia-tipagem engana. Comece pelos módulos de baixo nível, que os outros importam, e suba. Mas saiba que o mypy, por padrão, não verifica o corpo de funções sem nenhuma anotação: um projeto tipado pela metade produz Success com defeitos evidentes dentro das funções que ficaram de fora. Enquanto a cobertura não fecha, --check-untyped-defs é o que impede que o verde signifique “não olhei”. A configuração que sustenta essa adoção gradual é o próximo capítulo.

68.6 🧪 Laboratório

Você vai anotar um módulo pequeno, ver o verificador achar um defeito real, e descobrir na prática que a anotação não protege nada em tempo de execução.

Passo 1 — ambiente.

mkdir lab-tipos && cd lab-tipos
python3.13 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
python -m pip install mypy
mypy --version
mypy 2.3.0 (compiled: yes)

Passo 2 — o módulo sem anotação. Crie estacao.py:

def media(valores):
    return sum(valores) / len(valores)


def rotular(estacao, temperatura):
    return f"{estacao}: {temperatura:.1f} C"


def resumo(leituras):
    return rotular(media(leituras), "onu-00043")

Repare que resumo tem um defeito: os argumentos de rotular estão trocados. Rode mypy estacao.py:

Success: no issues found in 1 source file

Sem anotação, não há o que verificar. Guarde essa observação — é o motivo de tipagem gradual funcionar, e é a primeira metade de uma armadilha.

Passo 3 — anotar as duas primeiras funções, deixando resumo como está:

def media(valores: list[float]) -> float:
    return sum(valores) / len(valores)


def rotular(estacao: str, temperatura: float) -> str:
    return f"{estacao}: {temperatura:.1f} C"

Rode mypy estacao.py outra vez:

Success: no issues found in 1 source file

Ainda nada — e agora a armadilha está completa. As duas funções chamadas por resumo estão anotadas, o defeito é evidente, e o mypy continua calado. O motivo: por padrão, o mypy não verifica o corpo de funções que não têm nenhuma anotação. resumo é uma função “não tipada”, e o corpo dela é território ignorado.

Há duas saídas. A primeira é ligar a checagem explicitamente:

import json

    estacao: str

    return json.loads(texto)

Repare também que carregar devolve Registro sem nenhuma validação: json.loads devolve Any, e você prometeu ao verificador que aquilo é um Registro. Se o JSON vier diferente, o programa quebra em tempo de execução e o verificador terá aprovado. É a fronteira exata onde tipagem estática acaba e validação começa.

68.7 Resumo

  • Uma anotação não faz nada em tempo de execução. O Python a avalia, guarda em __annotations__ e ignora; passar o tipo errado não levanta erro por causa da anotação.
  • O valor está no segundo leitor: verificador de tipos e editor, que leem o arquivo sem executá-lo e apontam o defeito antes de o programa produzir efeito colateral — e com uma mensagem que aponta a causa, não o sintoma.
  • Sintaxe do 3.13: list[str] e dict[str, float] (PEP 585, 3.9+), X | None no lugar de Optional[X] (PEP 604, 3.10+), type Apelido = ... (PEP 695, 3.12+). As formas de typing.List e typing.Optional estão obsoletas.
  • Os construtores do dia a dia: Literal para conjunto pequeno e fechado de valores, Final para o que não se reatribui, Callable de collections.abc para funções como parâmetro, TypedDict para dicionário de forma conhecida — e Any como decisão consciente, nunca como padrão.
  • Até o 3.13, anotações são avaliadas na definição, o que exige aspas ou from __future__ import annotations para referência para frente; o 3.14 passa a avaliá-las sob demanda (PEP 649), e o erro só aparece ao ler __annotations__.
  • Anotação não valida entrada externa. Na fronteira com JSON, formulário ou banco, a tipagem estática confia na sua promessa; validação em tempo de execução é outro assunto e outra ferramenta.
