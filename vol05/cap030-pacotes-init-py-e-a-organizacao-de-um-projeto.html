30  Pacotes, __init__.py e a organização de um projeto

O projeto da telemetria começou com dois arquivos. Sete meses depois, o diretório estava assim:

coletor.py
csv.py
latencia.py
modelos.py
potencia.py
texto.py
util.py

Nenhum arquivo é grande, nenhum é ruim, e mesmo assim o conjunto já dói em três lugares. csv.py sombreia a biblioteca padrão, exatamente como o statistics.py do Capítulo 29. texto.py não diz se formata relatório ou se analisa texto de log. E util.py — todo projeto tem um — é onde vai parar o que ninguém sabe onde pôr.

O que falta não é disciplina de nomes: é hierarquia. Um módulo é um arquivo; quando os arquivos passam de meia dúzia, o que organiza é o nível de cima.

30.1 Um pacote é um diretório

telemetria/
    __init__.py
    coletor.py
    relatorio/
        __init__.py
        texto.py
    sondas/
        __init__.py
        latencia.py
        potencia.py

Isso é um pacote com dois subpacotes. Os nomes ficam qualificados — telemetria.sondas.potencia — e a colisão com a biblioteca padrão desaparece por construção: um arquivo chamado csv.py dentro de telemetria/ é telemetria.csv, e ninguém confunde os dois.

O uso é o esperado:

import telemetria.coletor

print(telemetria.coletor.coletar("onu-00042"))
{'onu': 'onu-00042', 'olt': 'olt-borda-01', 'nivel': -21.4}

Um pacote também é um objeto módulo — o __init__.py é o corpo dele. A diferença aparece num atributo a mais:

import telemetria

print("__file__:", telemetria.__file__)
print("__path__:", telemetria.__path__)
__file__: /home/vitor/lab30/telemetria/__init__.py
__path__: ['/home/vitor/lab30/telemetria']

__path__ é o que faz de um módulo um pacote: é o sys.path local dele, a lista de diretórios onde os submódulos são procurados. Quando você escreve import telemetria.sondas.potencia, o Python procura telemetria no sys.path, depois procura sondas no telemetria.__path__, depois potencia no telemetria.sondas.__path__. É o mesmo algoritmo do capítulo anterior, aplicado em cadeia.

30.2 Importar o pacote não importa os submódulos

Esta é a surpresa mais comum de quem chega de outras linguagens:

import telemetria

print(telemetria.coletor)
Traceback (most recent call last):
  File "<string>", line 3, in <module>
    print(telemetria.coletor)
          ^^^^^^^^^^^^^^^^^^
AttributeError: module 'telemetria' has no attribute 'coletor'

import telemetria executa só o __init__.py. Se ele estiver vazio, você importou um objeto módulo vazio. Nada de varredura de diretório, nada de carregamento automático: submódulo se importa na unha.

A recíproca vale e é útil: importar um submódulo importa todos os pais no caminho, porque cada __path__ precisa existir antes do passo seguinte.

import sys

import telemetria.sondas.potencia

print([n for n in sys.modules if n.startswith("telemetria")])
['telemetria', 'telemetria.sondas', 'telemetria.sondas.potencia']

E o efeito colateral: depois desse import, telemetria.sondas passa a existir como atributo, porque o mecanismo de import grava o filho no pai ao terminar. Contar com isso é frágil (funciona ou não conforme a ordem dos imports em outro arquivo qualquer), mas explica por que às vezes telemetria.coletor funciona sem você ter importado.

30.3 O que colocar no __init__.py

A resposta padrão é: nada. Um __init__.py vazio de zero byte é o caso mais comum em projetos bons, e não é preguiça — é o pacote dizendo “eu sou só uma pasta com nome”.

O __init__.py executa quando o pacote é importado, e em cascata, de fora para dentro. Com um print em cada um dos dois:

python3 -c "import telemetria.sondas.potencia; print('pronto')"
  [telemetria] __init__ executado
  [telemetria.sondas] __init__ executado
pronto

Isso significa que todo peso no __init__.py é pago por quem importa qualquer coisa do pacote, mesmo quem só queria um submódulo. Ler configuração, abrir conexão ou montar cache no __init__.py é o jeito mais eficiente de deixar uma biblioteca lenta.

O uso legítimo é a fachada: reexportar a API pública para encurtar o caminho de quem usa.

"""Telemetria de rede optica."""

from telemetria.coletor import coletar
from telemetria.relatorio.texto import linha

__all__ = ["coletar", "linha"]
__version__ = "0.1.0"
import telemetria

print(telemetria.__version__)
print(telemetria.coletar("onu-00042"))
print(telemetria.linha("onu-00042"))
print("publicos:", [n for n in dir(telemetria) if not n.startswith("_")])
0.1.0
{'onu': 'onu-00042', 'olt': 'olt-borda-01', 'nivel': -21.4}
   onu-00042    olt-borda-01   -21.4 dBm
publicos: ['coletar', 'coletor', 'linha', 'relatorio']

É assim que from pathlib import Path funciona sem você precisar saber que Path mora em outro arquivo lá dentro. Repare na última linha: além de coletar e linha, aparecem coletor e relatorio — os submódulos que a própria fachada teve de importar. dir() mostra tudo; __all__ declara o que é público.

__all__ faz duas coisas: define o que from telemetria import * traz e serve de contrato para leitores e ferramentas (um verificador reclama se algo listado em __all__ não existe). Não é uma trava: nada impede alguém de importar telemetria.coletor.OLT_PADRAO. É documentação executável, e o resto é convenção — nome com um underscore na frente é privado por acordo.

O preço da fachada é real e vale saber antes de adotá-la: ela importa o pacote inteiro sempre, encarece o tempo de partida (Capítulo 29) e é a origem clássica de ciclos, porque um submódulo que faça from telemetria import algo volta a executar o __init__.py que ainda está no meio da execução. A saída conhecida é submódulo nunca importar da fachada — só de outros submódulos, por caminho explícito.

30.4 Imports relativos

Dentro de um pacote, o ponto significa “aqui”:

"""Formatacao do relatorio em texto."""

from ..coletor import coletar


def linha(onu):
    d = coletar(onu)
    return f"{d['onu']:>12}  {d['olt']:>14}  {d['nivel']:6.1f} dBm"

Um ponto é o pacote atual (telemetria.relatorio), dois pontos é o pai (telemetria), três é o avô. Como telemetria é o topo, subir demais dá erro:

from ...coletor import coletar
ImportError: attempted relative import beyond top-level package

O import relativo tem uma vantagem concreta: renomear o pacote inteiro (de telemetria para telemetria_optica, digamos) não quebra nenhum import interno. E tem uma armadilha:

python3 telemetria/relatorio/texto.py
ImportError: attempted relative import with no known parent package

Chamar o arquivo pelo caminho faz dele o __main__ — um módulo de topo, sem pacote pai, e o .. não tem para onde apontar. A correção é a do capítulo anterior:

python3 -m telemetria.relatorio.texto

Com -m, o Python importa telemetria, depois telemetria.relatorio, e só então executa texto sabendo quem é o pai. É a mesma regra do sys.path[0], vista do outro lado.

Vale mostrar um aviso que aparece justamente quando se tem uma fachada e se usa -m num submódulo que ela já importou:

<frozen runpy>:128: RuntimeWarning: 'telemetria.relatorio.texto' found in sys.modules
after import of package 'telemetria.relatorio', but prior to execution of
'telemetria.relatorio.texto'; this may result in unpredictable behaviour

O runpy está avisando que o módulo vai ser executado de novo, como __main__, embora já exista em sys.modules sob o nome verdadeiro — resultado: duas cópias das mesmas classes e funções no mesmo processo. É inofensivo num script de demonstração e perigoso em código que compara tipos. A saída limpa é dar ao pacote um __main__.py (a seguir) em vez de executar submódulos soltos.

Sobre qual estilo usar, a PEP 8 é morna: prefere absoluto, aceita relativo explícito para layouts complexos. Na prática, a divisão que funciona:

  • Absoluto (from telemetria.coletor import coletar) em scripts, testes e em qualquer lugar fora do pacote. Sempre.
  • Relativo (from ..coletor import coletar) entre módulos irmãos dentro do pacote — mais curto, sobrevive a renomeação.
  • Nunca relativo implícito: import coletor de dentro de telemetria/relatorio/ não funciona desde o Python 3 (PEP 328), e ainda aparece em código antigo portado às pressas.

30.5 Pacotes de namespace

Desde o Python 3.3 (PEP 420), o __init__.py é opcional. Um diretório sem ele também importa:

import ferramentas

print("__file__:", getattr(ferramentas, "__file__", None))
print("__path__:", ferramentas.__path__)
__file__: None
__path__: _NamespacePath(['/home/vitor/lab30/ferramentas'])

Repare no __file__ nulo e no tipo do __path__: isso é um pacote de namespace, e ele existe para um caso específico — permitir que pedaços de um mesmo pacote venham de lugares diferentes do sys.path. Com plugins_a/sondas_ext/temperatura.py e plugins_b/sondas_ext/vibracao.py, nenhum dos dois com __init__.py:

PYTHONPATH=plugins_a:plugins_b python3 -c "
import sondas_ext
print(list(sondas_ext.__path__))
import sondas_ext.temperatura, sondas_ext.vibracao
print(sondas_ext.temperatura.NOME, '+', sondas_ext.vibracao.NOME)
"
['/home/vitor/lab30/plugins_a/sondas_ext', '/home/vitor/lab30/plugins_b/sondas_ext']
temperatura + vibracao

Os dois diretórios viraram um pacote com dois trechos. É assim que funcionam ecossistemas de plugin distribuídos em pacotes separados. Basta criar um __init__.py em qualquer um deles para a mágica acabar:

__path__: ['/home/vitor/lab30/plugins_a/sondas_ext']
ModuleNotFoundError: No module named 'sondas_ext.vibracao'

Um pacote comum é encontrado, a busca para ali, e o segundo diretório desaparece — inclusive de mensagens de erro, o que torna esse um problema difícil de diagnosticar sem olhar __path__.

A segunda mordida do PEP 420 é mais frequente e mais boba: qualquer diretório vira um import válido. Um erro de digitação no nome de um diretório não dá erro de import; dá um pacote vazio.

import telemetrai  # note o "ai" no fim

print("importou sem erro:", telemetrai)
importou sem erro: <module 'telemetrai' (namespace) from ['/home/vitor/lab30/telemetrai']>

Nenhum ModuleNotFoundError. O erro só aparece bem depois, como AttributeError em algo que deveria existir. Daí a regra prática deste manual: use __init__.py, mesmo vazio, em todo pacote seu. Namespace é recurso para quem distribui plugins de terceiros, não estilo de organização — e as ferramentas de empacotamento do Capítulo 32 precisam de configuração extra para achar pacotes sem __init__.py.

30.6 __main__.py: o pacote executável

Um arquivo com esse nome faz o pacote responder a python3 -m:

"""Ponto de entrada: python -m telemetria."""

from telemetria import linha

for onu in ("onu-00042", "onu-00043"):
    print(linha(onu))
python3 -m telemetria
   onu-00042    olt-borda-01   -21.4 dBm
   onu-00043    olt-borda-01   -21.4 dBm

É o mecanismo por trás de python3 -m json.tool, python3 -m http.server e python3 -m venv. O Capítulo 34 fecha o assunto, incluindo a diferença entre isso e um comando de terminal instalado.

30.7 Dados que viajam com o pacote

Limiares, gabaritos, arquivos de tradução e esquemas moram junto do código e precisam ser lidos sem depender do diretório de trabalho. O caminho certo é importlib.resources:

import tomllib
from importlib.resources import files

bruto = files("telemetria").joinpath("limiares.toml").read_text(encoding="utf-8")
print(tomllib.loads(bruto))
{'potencia': {'critico': -28.0, 'atencao': -25.0}}

O que não fazer é open("telemetria/limiares.toml") nem montar caminho a partir de __file__: os dois quebram quando o pacote é instalado em outro lugar, e o segundo quebra também quando ele é distribuído dentro de um .zip. files() pergunta ao próprio mecanismo de import onde o recurso está, e funciona nos dois casos. (tomllib está na biblioteca padrão desde o Python 3.11 e só lê — para escrever TOML ainda é preciso um pacote externo.)

30.8 Layout: plano ou src

Falta decidir onde o pacote mora dentro do repositório. Há duas convenções, e a diferença entre elas é sutil de ver e cara de ignorar.

A demonstração cabe em quatro linhas. Com o layout plano, da raiz do projeto:

python3 -c "import telemetria; print('da raiz: ok')"
cd /tmp && python3 -c "import telemetria"
da raiz: ok
ModuleNotFoundError: No module named 'telemetria'

Funciona da raiz e só da raiz — porque quem colocou o pacote no caminho foi o diretório de trabalho, não uma instalação. Com o layout src, nem da raiz:

cd projeto && python3 -c "import telemetria"
PYTHONPATH=src python3 -c "import telemetria; print(telemetria.__file__)"
ModuleNotFoundError: No module named 'telemetria'
/home/vitor/lab30/projeto/src/telemetria/__init__.py

Parece um retrocesso e é o contrário: o src/ obriga o projeto a ser instalado para ser importado, e é isso que garante que a suíte de testes esteja exercitando o pacote de verdade — com os arquivos de dados que realmente foram incluídos, com os módulos que realmente foram declarados. O erro que o layout plano esconde é sempre o mesmo: esqueceu-se de incluir um subpacote ou um .toml na distribuição, tudo passou verde em casa, e o usuário recebeu um pacote que não importa.

O PYTHONPATH=src acima é muleta de demonstração. A forma correta é pip install -e ., que o Capítulo 32 monta por inteiro; até lá, a estrutura de referência do manual é:

projeto/
    pyproject.toml
    README.md
    src/
        telemetria/
            __init__.py
            __main__.py
            coletor.py
            limiares.toml
            relatorio/
            sondas/
    tests/
        test_coletor.py

tests/ fora do pacote, sem __init__.py — os testes não são parte do que se distribui, e o Volume 9 trata deles.

30.9 🐍 Jeito Pythônico

Um pacote por projeto, src/ na raiz, tests/ ao lado. É o layout que as ferramentas modernas (hatchling, uv init --lib, pytest) assumem por padrão.

__init__.py vazio, até haver motivo. Quando houver, que seja fachada e nada mais:

# antipadrão: o __init__ que trabalha
import requests

CONFIG = json.loads(open("config.json").read())   # roda em todo import
SESSAO = requests.Session()                       # abre socket em todo import
# pythônico: o __init__ que só apresenta
"""Telemetria de rede optica."""

from telemetria.coletor import coletar
from telemetria.relatorio.texto import linha

__all__ = ["coletar", "linha"]

Declare __all__ em módulos e pacotes que formam API pública. Nome com underscore na frente é privado, e a convenção basta.

Import absoluto para fora, relativo entre irmãos. E jamais relativo implícito.

python3 -m pacote em vez de python3 pacote/modulo.py. O primeiro sabe quem é o pai; o segundo, não.

importlib.resources.files() para ler dado do pacote. Nunca caminho relativo, nunca __file__ costurado à mão.

__init__.py mesmo vazio. Pacote de namespace é para distribuir plugins de terceiros; no seu projeto, ele só transforma erro de digitação em bug silencioso.

Sobre versões:

  • Python 3.3 — PEP 420 tornou o __init__.py opcional e criou os pacotes de namespace.
  • Python 3.7 — importlib.resources entrou na biblioteca padrão, aposentando pkg_resources (que era lento e exigia setuptools em tempo de execução).
  • Python 3.9 — importlib.resources.files() trouxe a interface de caminho, que é a que se usa hoje.
  • Python 3.11 — tomllib na biblioteca padrão, o que torna .toml a escolha natural para configuração que viaja com o pacote.
  • Python 3.12 — os utilitários antigos de importlib.resources (open_text, read_binary) ficaram formalmente obsoletos em favor de files().

30.10 🧪 Laboratório

30.11 Resumo

  • Pacote é diretório com __init__.py; o que o distingue de um módulo é __path__, o caminho de busca local onde os submódulos são procurados.
  • import pacote executa só o __init__.py — submódulo não vem de brinde. Já import pacote.sub.mod executa os __init__.py de todos os pais, em cascata.
  • __init__.py vazio é o padrão saudável. Quando não for, que seja fachada de reexportação com __all__, nunca trabalho de verdade: todo peso ali é pago por quem importa qualquer coisa do pacote.
  • Import relativo (from ..coletor import x) vale entre irmãos e sobrevive a renomeação; absoluto vale para o resto. Rodar o arquivo pelo caminho mata o relativo — use python3 -m.
  • Pacote de namespace (sem __init__.py) junta diretórios espalhados pelo sys.path, o que serve a plugins e atrapalha todo o resto: erro de digitação em nome de diretório passa a importar em silêncio.
  • __main__.py faz o pacote responder a python3 -m pacote.
  • Dado que viaja com o pacote se lê com importlib.resources.files(), não com caminho relativo nem com __file__.
  • Layout src/ impede o diretório de trabalho de fingir que o pacote está instalado — é o que faz o teste exercitar o que o usuário vai receber.
