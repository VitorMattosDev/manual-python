33  uv, pipx e Poetry: o ecossistema de gerenciamento

Três coisas ficaram pendentes nos capítulos anteriores.

O Capítulo 31 mostrou que pip freeze produz uma lista de versões, não um arquivo de trava: sem hash, sem origem, sem plataforma, sem separar o que é seu do que veio junto. O Capítulo 32 pediu pip install -e ., python -m build e twine — três ferramentas para três etapas do mesmo trabalho. E o próprio Python que roda tudo isso continua sendo o do sistema, com a versão que a distribuição escolheu.

Enquanto isso, criar um ambiente e instalar dois pacotes leva isto aqui:

--- python3 -m venv .venv-pip
  tempo: 2.919 s
--- pip install rich httpx
  tempo: 2.121 s

Cinco segundos parece pouco. Multiplique por cada vez que o CI roda, por cada contêiner que sobe, por cada troca de branch que muda dependência, e a conta muda de tamanho.

Este capítulo é sobre as três ferramentas que responderam a isso — pipx, Poetry e uv — e sobre quando usar cada uma.

33.1 pipx: aplicação não é dependência

Comece pelo problema mais simples. ruff, httpie, black, yt-dlp e o próprio Poetry são programas escritos em Python, não bibliotecas que seu código importa. Instalá-los no venv do projeto polui o arquivo de dependências com coisas que nada têm a ver com o produto; instalá-los no sistema esbarra na PEP 668 do Capítulo 31.

pipx resolve isso instalando cada aplicação no seu próprio ambiente virtual, e expondo só os comandos:

pipx install uv
pipx install poetry
pipx list
  installed package uv 0.12.3, installed using Python 3.13.12
  These apps are now available
    - uv
    - uvx
  installed package poetry 2.4.1, installed using Python 3.13.12
  These apps are now available
    - poetry
venvs are in /home/vitor/.local/share/pipx/venvs
apps are exposed on your $PATH at /home/vitor/.local/bin

Dois programas, dois ambientes isolados, zero interferência entre eles e com o sistema. O truque é o mesmo do Capítulo 31, visto pelo shebang do comando exposto:

head -1 ~/.local/bin/poetry
#!/home/vitor/.local/share/pipx/venvs/poetry/bin/python -E

Não há cópia nem link mágico: o arquivo em ~/.local/bin aponta para o Python de dentro do venv do pipx. E há a variante descartável, para quando você quer rodar sem instalar:

pipx run cowsay -t "idem, pelo pipx"

O ambiente é criado, usado e cacheado — nada fica no seu PATH.

33.2 uv: a ferramenta que absorveu as outras

uv é escrito em Rust, vem como binário único, e cobre num só comando o que antes exigia pip, venv, pip-tools, pipx, pyenv, build e twine. A diferença de velocidade não é marginal:

--- python3 -m venv .venv-pip
  tempo: 2.919 s
--- uv venv .venv-uv
  tempo: 0.109 s

--- pip install rich httpx        (cache quente)
  tempo: 2.121 s
--- uv pip install rich httpx     (cache quente)
  tempo: 0.156 s

Vinte e seis vezes na criação do ambiente, treze vezes na instalação. Sem cache nenhum, com download real, a distância diminui mas continua grande (2,706 s contra 0,587 s), porque aí o gargalo passa a ser a rede.

E não é só tempo:

du -sh .venv-pip .venv-uv
30M .venv-pip
9.3M    .venv-uv

O mesmo conjunto de pacotes ocupando um terço do espaço. O motivo aparece na contagem de links do arquivo:

stat -c "%h %n" .venv-uv/lib/python3.13/site-packages/rich/__init__.py
stat -c "%h %n" .venv-pip/lib/python3.13/site-packages/rich/__init__.py
2 .venv-uv/lib/python3.13/site-packages/rich/__init__.py
1 .venv-pip/lib/python3.13/site-packages/rich/__init__.py

Dois links para o mesmo inode: o uv não copia o arquivo do cache global para o ambiente, ele cria um link físico. Dez projetos usando rich guardam uma cópia só no disco. É o mesmo princípio de referências compartilhadas do Capítulo 8, aplicado ao sistema de arquivos.

33.2.1 O modo “pip compatível”

O caminho de menor atrito é usar uv como substituto direto do que você já digita. Os comandos existem com os mesmos nomes e as mesmas opções:

uv venv .venv                       # em vez de python3 -m venv .venv
uv pip install rich httpx           # em vez de pip install
uv pip freeze                       # em vez de pip freeze
uv pip compile requirements.in -o requirements.txt --generate-hashes

Ele funciona inclusive dentro de um venv criado pelo venv comum — as duas ferramentas escrevem no mesmo lugar, no mesmo formato:

python3 -m venv .venv-comum
uv pip install --python .venv-comum/bin/python cowsay
.venv-comum/bin/cowsay -t "instalado pelo uv num venv do venv"

O uv pip compile merece destaque: é o pip-tools embutido, e é ele que fecha o buraco do pip freeze do Capítulo 31. Dado um requirements.in com as dependências diretas:

rich>=13,<15
httpx
uv pip compile requirements.in -o requirements.txt --generate-hashes
# This file was autogenerated by uv via the following command:
#    uv pip compile requirements.in -o requirements.txt --generate-hashes
anyio==4.14.2 \
    --hash=sha256:9f505dda5ac9f0c8309b5e8bd445a8c2bf7246f3ce950121e45ea15bc41d1494 \
    --hash=sha256:cfa139f3ed1a23ee8f88a145ddb5ac7605b8bbfd8592baacd7ce3d8bb4313c7f

Quarenta e seis linhas com versão exata, hash duplo e — o mais valioso — o comentário # via dizendo quem pediu cada pacote. Esse arquivo é instalável por pip comum (pip install -r requirements.txt), o que o torna a ponte perfeita para um projeto que ainda não quer adotar uv inteiro.

33.2.2 O modo projeto

O outro modo é o de gerenciador completo, em que o uv cuida do pyproject.toml, do ambiente e da trava, e você não digita pip nunca mais.

uv init --lib telemetria2
find . -type f | sort
./.gitignore
./pyproject.toml
./.python-version
./README.md
./src/telemetria2/__init__.py
./src/telemetria2/py.typed

Layout src, py.typed (a marca de que o pacote tem anotações de tipo, assunto do Volume 10), .python-version fixando o interpretador do projeto, e um pyproject.toml já no formato do Capítulo 32:

[project]
name = "telemetria2"
version = "0.1.0"
description = "Add your description here"
readme = "README.md"
requires-python = ">=3.13"
dependencies = []

[build-system]
requires = ["uv_build>=0.12.3,<0.13.0"]
build-backend = "uv_build"

Acrescentar uma dependência é um comando que faz quatro coisas de uma vez:

uv add "rich>=13,<15"
Using CPython 3.13.12 interpreter at: /usr/bin/python3.13
Creating virtual environment at: .venv
Resolved 5 packages in 105ms
      Built telemetria2 @ file:///home/vitor/lab33/telemetria2
Prepared 2 packages in 96ms
Installed 5 packages in 12ms
 + markdown-it-py==4.2.0
 + mdurl==0.1.2
 + pygments==2.20.0
 + rich==14.3.4
 + telemetria2==0.1.0 (from file:///home/vitor/lab33/telemetria2)

Ele criou o .venv (ninguém pediu, e é o certo), escreveu rich>=13,<15 em [project.dependencies], gerou o uv.lock e instalou tudo — inclusive o próprio projeto, em modo editável. O pip install -e . do capítulo anterior aconteceu sozinho.

O uv.lock é o arquivo de trava que faltava:

version = 1
revision = 3
requires-python = ">=3.13"

[[package]]
name = "markdown-it-py"
version = "4.2.0"
source = { registry = "https://pypi.org/simple" }
dependencies = [
    { name = "mdurl" },
]
sdist = { url = "https://files.pythonhosted.org/.../markdown_it_py-4.2.0.tar.gz", hash = "sha256:04a21681d6fbb623de53f6f364d352309d4094dd4194040a10fd51833e418d49", size = 82454 }
wheels = [
    { url = "https://files.pythonhosted.org/.../markdown_it_py-4.2.0-py3-none-any.whl", hash = "sha256:9f7ebbcd14fe59494226453aed97c1070d83f8d24b6fc3a3bcf9a38092641c4a", size = 91687 },
]

Compare com as cinco linhas de nome==versão do pip freeze: aqui há origem, hash do sdist e de cada roda, tamanho, grafo de dependências e as marcas de plataforma. É um arquivo que descreve o ambiente em Linux, macOS e Windows — por isso ele vai para o Git, e o .venv não.

A partir daí, o ciclo diário são três comandos:

uv sync   # o ambiente passa a ser exatamente o lock
uv run    # roda algo dentro dele, sem ativar nada
uv lock   # recalcula a trava quando o pyproject mudar
rm -rf .venv && uv sync
Creating virtual environment at: .venv
Resolved 10 packages in 1ms
Installed 9 packages in 23ms
  tempo: 0.061 s

Sessenta e um milissegundos para reconstruir do zero um ambiente com nove pacotes. É esse número que muda o hábito: um .venv deixa de ser algo que você preserva e passa a ser algo que você joga fora sem pensar.

uv run é o comando que substitui o activate:

uv run python -c "from telemetria2 import relatorio; relatorio()"
onu-00042  -21.4 dBm  normal

Ele garante, antes de executar, que o ambiente está sincronizado com o uv.lock — o que elimina de vez a classe de bugs “instalei a dependência e esqueci de instalar na outra máquina”. Em CI, uv sync --frozen e uv lock --check recusam-se a prosseguir se a trava estiver desatualizada em relação ao pyproject.toml.

Dependências de desenvolvimento têm lugar próprio, o padrão de grupos da PEP 735:

uv add --dev pytest
[dependency-groups]
dev = [
    "pytest>=9.1.1",
]

Elas não viajam para quem instala o pacote — algo que o requirements-dev.txt fazia por convenção e agora está no padrão.

E há uv tree, que responde “de onde veio este pacote” sem instalar nada extra:

telemetria2 v0.1.0
    rich v14.3.4
        markdown-it-py v4.2.0
            mdurl v0.1.2
        pygments v2.20.0
    pytest v9.1.1 (group: dev)
        iniconfig v2.3.0
        packaging v26.3
        pluggy v1.6.0
        pygments v2.20.0

33.2.3 O interpretador também

uv gerencia versões de Python, o que dispensa pyenv:

uv python install 3.12
Downloading cpython-3.12.13-linux-x86_64-gnu (download) (32.6MiB)
Installed Python 3.12.13 in 2.41s
 + cpython-3.12.13-linux-x86_64-gnu (python3.12)
  tempo: 2.486 s

Dois segundos e meio para ter outro Python, sem compilar nada e sem tocar no do sistema. A partir daí:

uv venv --python 3.12 .venv-312
uv run --python 3.12 python -V
Python 3.12.13

É a resposta prática para testar a biblioteca em três versões antes de publicar — e, no Capítulo 32, para conferir se aquele requires-python = ">=3.11" que você declarou é verdade.

33.2.4 Scripts com dependência (PEP 723)

Um caso que era desagradável: o script de arquivo único que precisa de uma biblioteca. A PEP 723 (2024) permite declarar isso num comentário no topo do arquivo:

# /// script
# requires-python = ">=3.11"
# dependencies = ["rich"]
# ///
"""Um script solto que declara as proprias dependencias."""

from rich.console import Console

Console().print("[bold red]onu-00042[/bold red] fora de servico")
uv run alarme.py
Installed 4 packages in 18ms
onu-00042 fora de servico
  tempo: 0.348 s

O uv leu o cabeçalho, montou um ambiente temporário com rich, rodou e seguiu a vida. Um terço de segundo, nenhum venv no diretório, nenhuma instalação global. Para o script de manutenção que vive num repositório de infraestrutura, isso resolve um problema real de distribuição.

(No Kali deste laboratório, python3 alarme.py também funciona — mas por acidente: o rich existe em dist-packages porque o sistema o instalou. Em outra máquina, o mesmo comando daria ModuleNotFoundError, e é exatamente essa diferença que o cabeçalho elimina.)

33.3 Poetry: o que você vai encontrar em projeto existente

Poetry chegou em 2018, quando pyproject.toml mal existia, e popularizou a ideia de gerenciador único com arquivo de trava. Milhares de projetos usam, e vale saber operar.

poetry new telemetria3
cd telemetria3
poetry config virtualenvs.in-project true --local
poetry add "rich>=13,<15"
Updating dependencies
Resolving dependencies...

Package operations: 4 installs, 0 updates, 0 removals

  - Installing mdurl (0.1.2)
  - Installing pygments (2.20.0)
  - Installing markdown-it-py (4.2.0)
  - Installing rich (14.3.4)

Writing lock file
  tempo: 2.755 s

O resultado é próximo do uv: pyproject.toml atualizado, poetry.lock gravado, ambiente pronto. O poetry.lock tem estrutura parecida, em TOML, com hash por arquivo:

# This file is automatically @generated by Poetry 2.4.1 and should not be changed by hand.

[[package]]
name = "markdown-it-py"
version = "4.2.0"
description = "Python port of markdown-it. Markdown parsing, done right!"
optional = false
python-versions = ">=3.10"
groups = ["main"]
files = [
    {file = "markdown_it_py-4.2.0-py3-none-any.whl", hash = "sha256:9f7ebbcd14fe59494226453aed97c1070d83f8d24b6fc3a3bcf9a38092641c4a"},
    {file = "markdown_it_py-4.2.0.tar.gz", hash = "sha256:04a21681d6fbb623de53f6f364d352309d4094dd4194040a10fd51833e418d49"},
]

Três diferenças práticas em relação ao uv:

A configuração é global por padrão. Sem virtualenvs.in-project true, o Poetry cria o ambiente em ~/.cache/pypoetry/virtualenvs/ com um nome derivado de hash, e não em .venv — o que confunde editor, pytest e quem chega novo no projeto. Aquele poetry config ... --local grava a preferência num poetry.toml ao lado do projeto e deve ser a primeira coisa a fazer.

poetry add não instala o próprio projeto. Diferente do uv:

poetry run python -c "from telemetria3 import relatorio; relatorio()"
ModuleNotFoundError: No module named 'telemetria3'

Falta um passo:

poetry install
Installing dependencies from lock file

No dependencies to install or update

Installing the current project: telemetria3 (0.1.0)
  tempo: 1.699 s
onu-00042  -21.4 dBm  normal

A última linha do log é a que importa: poetry install é quem instala o pacote em modo editável. Esquecer disso é o primeiro tropeço de quase todo mundo.

Metadados fora do padrão, até pouco tempo. Projetos Poetry antigos têm [tool.poetry] com name, version e dependencies num dialeto próprio, anterior à PEP 621. O Poetry 2.0 (2025) passou a aceitar [project] padrão — o poetry new deste laboratório já gerou assim, deixando em [tool.poetry] apenas o que é específico dele:

[project]
name = "telemetria3"
version = "0.1.0"
requires-python = ">=3.13"
dependencies = [
    "rich (>=13,<15)"
]

[tool.poetry]
packages = [{include = "telemetria3", from = "src"}]

[build-system]
requires = ["poetry-core>=2.0.0,<3.0.0"]
build-backend = "poetry.core.masonry.api"

poetry build e poetry publish cobrem o Capítulo 32 sem build nem twine; poetry show --tree é o equivalente do uv tree. É uma ferramenta madura e completa — a razão de este manual não a adotar como padrão é velocidade e o fato de que ela não gerencia interpretador nem ferramenta global.

33.4 Qual usar

  • pip + venv continuam sendo o denominador comum: estão em toda máquina, não exigem instalação e são o que a documentação de qualquer projeto assume. Saber operá-los não é opcional — é o conteúdo do Capítulo 31.
  • pipx para aplicação de linha de comando, sempre. Mesmo que você use uv para tudo o mais (uv tool install faz o mesmo papel).
  • uv para projeto novo, para CI e sempre que o tempo de instalação incomodar. É a recomendação padrão deste manual daqui para a frente.
  • Poetry quando o projeto já é dele. Migrar sem necessidade é gastar um dia para trocar um lock por outro.

Sobre o risco de adotar uma ferramenta nova: uv é jovem (2024) e de uma empresa (a Astral, dona também do ruff), o que é razão legítima de cautela. O mitigante é concreto: tudo o que ele produz é padrão — pyproject.toml da PEP 621, ambiente virtual comum, rodas comuns, requirements.txt compatível via uv export. Sair dele é apagar o uv.lock. Isso não vale para ferramenta que inventa formato próprio de metadados, e é o critério que vale a pena aplicar a qualquer novidade do ecossistema.

33.5 🐍 Jeito Pythônico

Aplicação com pipx (ou uv tool), biblioteca com o gerenciador do projeto. ruff e pytest não são a mesma categoria de coisa: o primeiro é um programa que você usa, o segundo é uma dependência de desenvolvimento do projeto.

# antipadrão
pip install ruff black httpie   # no venv do projeto, poluindo o lock
# pythônico
pipx install ruff
uv add --dev pytest

Trave o que você instala, versione a trava. uv.lock e poetry.lock vão para o Git; .venv/ não. Com pip puro, uv pip compile --generate-hashes produz a trava que falta.

uv run em vez de ativar. Um comando que não depende de o shell estar no estado certo é um comando que funciona no Makefile, no CI e no cron.

uv sync --frozen e uv lock --check no CI. A trava desatualizada tem que falhar no pipeline, não em produção.

Não misture gerenciadores no mesmo projeto. poetry add seguido de pip install produz um ambiente que nenhum dos dois descreve, e o próximo poetry install desfaz metade.

Ferramenta nova, formato padrão. Adote o que produzir pyproject.toml da PEP 621 e ambiente virtual comum; desconfie do que exigir um formato só dele.

Sobre versões e datas:

  • pipx (2019) — isolamento de aplicação; hoje é a resposta padrão à PEP 668 para programas.
  • Poetry 1.0 (2019) — trava e gerenciador único, com dialeto próprio em [tool.poetry].
  • PEP 621 (2020) — [project] padroniza metadados, e o ecossistema converge.
  • PEP 723 (2024) — dependências declaradas dentro de um script de arquivo único; uv run e pipx run implementam.
  • PEP 735 (2024) — [dependency-groups] padroniza o que era requirements-dev.txt.
  • uv (2024) — pip, venv, pip-tools, pyenv e pipx num binário só; Poetry 2.0 (2025) adota [project].

33.7 Resumo

  • pipx instala aplicação Python em ambiente próprio e expõe só o comando; é a resposta certa à PEP 668 para ruff, httpie e afins — inclusive para instalar o uv e o Poetry.
  • uv é pip + venv + pip-tools + pyenv + pipx + build num binário em Rust: 0,1 s para criar ambiente contra 2,9 s, 0,16 s para instalar contra 2,1 s, e um terço do disco por usar link físico a partir de um cache global.
  • No modo compatível (uv venv, uv pip install), ele entra em projeto existente sem mudar nada. uv pip compile --generate-hashes gera a trava com hash e com o # via de quem pediu cada pacote — instalável por pip comum.
  • No modo projeto, uv add escreve no pyproject.toml, resolve, grava uv.lock e instala o próprio projeto em modo editável. uv sync reconstrói o ambiente em milissegundos; uv run executa sem ativar nada.
  • uv.lock e poetry.lock são travas de verdade: versão exata, hash, origem e várias plataformas num arquivo só. Vão para o Git; o .venv não.
  • uv python install resolve versão de interpretador sem pyenv; PEP 723 mais uv run script.py resolve o script solto que precisa de biblioteca.
  • Poetry faz quase tudo isso e está em milhares de projetos. Dois detalhes: configure virtualenvs.in-project e lembre que poetry install — não poetry add — é quem instala o seu pacote.
  • Critério para adotar ferramenta nova: se o que ela produz é padrão (PEP 621, venv, roda), sair dela é barato.
