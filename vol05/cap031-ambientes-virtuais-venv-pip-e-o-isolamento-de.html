31  Ambientes virtuais: venv, pip e o isolamento de dependências

O tutorial dizia pip install cowsay. O Kali respondeu com um muro:

pip3 install cowsay
error: externally-managed-environment

× This environment is externally managed
+-> To install Python packages system-wide, try apt install
    python3-xyz, where xyz is the package you are trying to
    install.

    If you wish to install a non-Kali-packaged Python package,
    create a virtual environment using python3 -m venv path/to/venv.
    Then use path/to/venv/bin/python and path/to/venv/bin/pip. Make
    sure you have python3-full installed.

    If you wish to install a non-Kali-packaged Python application,
    it may be easiest to use pipx install xyz, which will manage a
    virtual environment for you. Make sure you have pipx installed.

note: If you believe this is a mistake, please contact your Python installation
or OS distribution provider. You can override this, at the risk of breaking your
Python installation or OS, by passing --break-system-packages.
hint: See PEP 668 for the detailed specification.

Essa mensagem é o assunto do capítulo inteiro. Ela não é um bug da distribuição nem excesso de zelo: é a resposta certa a um problema real, e a última linha diz onde a decisão foi tomada — a PEP 668, de 2021, adotada por Debian, Ubuntu, Kali, Fedora e pelo Homebrew.

O motivo está em um número:

dpkg -l | grep -c '^ii  python3-'
529

Quinhentos e vinte e nove pacotes Python instalados pelo sistema, dos quais dependem apt, ufw, ferramentas de rede, scripts de inicialização e boa parte do Kali. Todos moram em /usr/lib/python3/dist-packages — a entrada 5 do sys.path que vimos no Capítulo 29. Se um pip install sobrescrever ali uma versão de urllib3 que o apt esperava, quem quebra não é o seu projeto: é o gerenciador de pacotes da máquina, e consertá-lo sem ele funcionando é um domingo perdido.

A solução tem trinta anos de maturidade e três linhas de comando.

31.1 O que é um ambiente virtual

python3 -m venv .venv
ls -1 .venv
bin
include
lib
lib64
pyvenv.cfg

É um diretório. Não há registro global, não há banco de dados, não há daemon: um venv é uma pasta com uma cópia mínima da estrutura de uma instalação de Python. O arquivo que a define tem cinco linhas:

cat .venv/pyvenv.cfg
home = /usr/bin
include-system-site-packages = false
version = 3.13.12
executable = /usr/bin/python3.13
command = /usr/bin/python3 -m venv /home/vitor/lab31/.venv

home aponta para o Python que criou o ambiente — e é ele que vai continuar rodando. O venv não copia o interpretador: o bin/python é um link para /usr/bin/python3.13. O que o venv troca é o contexto desse interpretador — para onde ele olha atrás de pacotes e onde ele os instala.

.venv/bin/python -c "
import sys, sysconfig
print('executable   :', sys.executable)
print('prefix       :', sys.prefix)
print('base_prefix  :', sys.base_prefix)
print('em venv?     ', sys.prefix != sys.base_prefix)
print('site-packages:', sysconfig.get_path('purelib'))
"
executable   : /home/vitor/lab31/.venv/bin/python
prefix       : /home/vitor/lab31/.venv
base_prefix  : /usr
em venv?      True
site-packages: /home/vitor/lab31/.venv/lib/python3.13/site-packages

Aí está o mecanismo inteiro. Ao iniciar, o Python descobre sys.prefix a partir do caminho do executável — e, achando um pyvenv.cfg ao lado, adota o diretório do venv como prefixo, deixando o prefixo original em sys.base_prefix. O site-packages calculado a partir do novo prefixo é um diretório vazio, seu, gravável sem sudo. A biblioteca padrão continua vindo de /usr/lib/python3.13, porque home diz onde ela está.

Comparado com o Python do sistema, onde os dois prefixos coincidem:

prefix      : /usr
base_prefix : /usr
em venv?     False

Essa comparação é, aliás, a forma canônica de um script perguntar “estou num venv?”.

O tamanho de um ambiente recém-criado, com 865 arquivos, é modesto:

du -sh .venv && find .venv -type f | wc -l
12M .venv
865

Doze megabytes por projeto é o preço do isolamento — e é barato. Quase tudo é o pip, a única coisa que vem instalada:

.venv/bin/pip list
Package Version
------- -------
pip     26.1.1

(Até o Python 3.11, setuptools e wheel vinham junto. Desde o 3.12 não vêm mais, e código antigo que fazia import setuptools sem declará-lo como dependência passou a falhar em ambiente novo — vale lembrar disso ao ressuscitar projeto parado.)

31.2 Ativar, e por que dá para não ativar

source .venv/bin/activate

O que esse comando faz cabe em três efeitos:

depois: /home/vitor/lab31/.venv/bin/python | /home/vitor/lab31/.venv/bin/pip
VIRTUAL_ENV=/home/vitor/lab31/.venv
PATH comeca com: /home/vitor/lab31/.venv/bin

Ele põe .venv/bin na frente do PATH, define VIRTUAL_ENV e altera o prompt. Só. Não há mágica de processo, não há variável secreta: é o PATH fazendo com que python e pip resolvam para os do venv. O deactivate desfaz — é uma função de shell que o próprio activate definiu, guardando o PATH anterior.

Consequência prática que economiza muita dor: ativar é conveniência, não requisito. .venv/bin/python script.py funciona igual, sem ativar nada, e é a forma certa de chamar código de venv em crontab, unidade systemd, Makefile ou hook de Git — lugares onde não há shell interativo para ativar coisa alguma.

No Windows o arquivo é outro (.venv\Scripts\activate.ps1 no PowerShell, activate.bat no cmd) e o diretório é Scripts em vez de bin, mas o mecanismo é o mesmo. Se o PowerShell recusar o script por política de execução, Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass resolve para aquela sessão. E vale a nota do Capítulo 3: ali o interpretador é python, não python3.

31.3 pip de verdade

Com o ambiente ativo, o comando do tutorial finalmente funciona:

pip install cowsay
Collecting cowsay
  Using cached cowsay-6.1-py3-none-any.whl.metadata (5.6 kB)
Using cached cowsay-6.1-py3-none-any.whl (25 kB)
Installing collected packages: cowsay
Successfully installed cowsay-6.1

Onde foi parar:

pip show cowsay
Name: cowsay
Version: 6.1
Summary: The famous cowsay for GNU/Linux is now available for python
Home-page: https://github.com/VaasuDevanS/cowsay-python
Author: Vaasudevan Srinivasan
License: GNU-GPL
Location: /home/vitor/lab31/.venv/lib/python3.13/site-packages
Requires:
Required-by:

Location é o site-packages do venv — nada foi escrito fora do diretório do projeto. E o pacote trouxe também um comando de terminal, instalado em .venv/bin:

cowsay -t "onu-00042 caiu"
  ______________
| onu-00042 caiu |
  ==============
              \
               \
                 ^__^
                 (oo)\_______
                 (__)\       )\/\
                     ||----w |
                     ||     ||

O isolamento se demonstra saindo dele:

python -c "import cowsay; print('dentro do venv: ok')"
deactivate
python3 -c "import cowsay"
dentro do venv: ok
ModuleNotFoundError: No module named 'cowsay'

Mesmo interpretador, mesma máquina, mesmo segundo: dentro do ambiente o pacote existe; fora, não. É o sys.path mudando com o prefixo, e nada além disso.

31.4 Dependências transitivas

Poucos pacotes vêm sozinhos:

pip install "rich==13.7.1"
Collecting rich==13.7.1
Collecting markdown-it-py>=2.2.0 (from rich==13.7.1)
Collecting pygments<3.0.0,>=2.13.0 (from rich==13.7.1)
Collecting mdurl~=0.1 (from markdown-it-py>=2.2.0->rich==13.7.1)
Installing collected packages: pygments, mdurl, markdown-it-py, rich
Successfully installed markdown-it-py-4.2.0 mdurl-0.1.2 pygments-2.20.0 rich-13.7.1

Você pediu um pacote e recebeu quatro. rich precisa de markdown-it-py e pygments; markdown-it-py precisa de mdurl. As restrições viajam nos metadados e o resolvedor do pip procura um conjunto de versões que satisfaça todas ao mesmo tempo.

Dá para ler esses metadados sem sair do Python, com importlib.metadata:

from importlib.metadata import requires, version

for p in ("rich", "cowsay"):
    print(p, version(p), "->", requires(p))
rich 13.7.1 -> ['ipywidgets (>=7.5.1,<9) ; extra == "jupyter"', 'markdown-it-py (>=2.2.0)', 'pygments (>=2.13.0,<3.0.0)', 'typing-extensions (>=4.0.0,<5.0) ; python_version < "3.9"']
cowsay 6.1 -> None

Duas coisas aparecem aí e valem para o Capítulo 32: extra == "jupyter" é dependência opcional, instalada só com pip install "rich[jupyter]"; e python_version < "3.9" é um marcador de ambiente, que faz a dependência valer só onde a condição bate. No nosso 3.13, typing-extensions não foi instalado — e é por isso que “as dependências” de um pacote não são uma lista fixa, mas uma função da plataforma.

Os operadores de versão que você vai encontrar:

forma significa quando usar
rich qualquer versão quase nunca
rich==13.7.1 exatamente esta arquivo de trava
rich>=13,<14 faixa dependência de biblioteca
rich~=13.7 >=13.7,<14 atalho da faixa acima
rich!=13.7.0 tudo menos esta contornar versão com defeito

31.5 requirements.txt e a reprodutibilidade

pip freeze despeja o que está instalado, no formato que o pip lê de volta:

pip freeze
cowsay==6.1
markdown-it-py==4.2.0
mdurl==0.1.2
Pygments==2.20.0
rich==13.7.1

E aqui mora a confusão mais comum do ecossistema. Esses cinco pacotes não são as dependências do seu projeto: são o resultado de instalá-las. Misturar as duas coisas num arquivo só é o que produz aquele requirements.txt de duzentas linhas que ninguém sabe mais para que serve.

A separação que funciona são dois arquivos com papéis diferentes:

# requirements.txt - o que EU peço, com a intenção
cowsay
rich==13.7.1
# requirements.lock - o que o resolvedor DECIDIU, com tudo
cowsay==6.1
markdown-it-py==4.2.0
mdurl==0.1.2
Pygments==2.20.0
rich==13.7.1

O primeiro é escrito à mão e revisado em code review; o segundo é gerado (pip freeze > requirements.lock) e commitado para que outra máquina reproduza o ambiente exato. A reprodução:

python3 -m venv .venv-copia
.venv-copia/bin/pip install -r requirements.lock
diff <(.venv/bin/pip freeze) <(.venv-copia/bin/pip freeze) && echo "identicos"
identicos

Isso resolve 90% dos casos, e é honesto dizer o que os outros 10% exigem: o .lock do pip freeze não guarda hashes (então não protege contra um pacote adulterado no caminho), não guarda de onde veio cada pacote, não distingue dependência de desenvolvimento da de produção, e é específico da plataforma onde foi gerado — congelar num Linux e restaurar num Windows pode instalar coisas diferentes. É exatamente esse vazio que uv, Poetry e pip-tools vieram preencher, com arquivos de trava multiplataforma e com hash. É o Capítulo 33.

Enquanto isso, pip sozinho ainda dá dois passos úteis: pip install --dry-run mostra o que aconteceria sem tocar em nada,

pip install --dry-run cowsay
Collecting cowsay
  Using cached cowsay-6.1-py3-none-any.whl.metadata (5.6 kB)
Would install cowsay-6.1

e pip install --require-hashes -r requirements.lock recusa a instalação se algum hash não estiver declarado no arquivo — a base do que ferramentas de auditoria automatizam.

31.6 O venv é descartável (e por que isso importa)

Um ambiente virtual não é património: é cache. Ele se reconstrói em segundos a partir do arquivo de dependências, e a prova de que não deve ser tratado como parte do projeto é o que acontece ao movê-lo de lugar:

head -1 .venv/bin/pip
mv .venv .venv-movido
.venv-movido/bin/pip --version
#!/home/vitor/lab31/.venv/bin/python3
bash: .venv-movido/bin/pip: /home/vitor/lab31/.venv/bin/python3: bad interpreter: No such file or directory

Os comandos instalados guardam o caminho absoluto do interpretador no shebang. Mover o diretório quebra todos eles de uma vez — e, pelo mesmo motivo, um venv nunca funciona em outra máquina, mesmo copiado inteiro. (Curiosidade útil: .venv-movido/bin/python continua rodando, porque é um link simbólico para o Python do sistema, não um script com shebang.)

Daí as regras que se seguem sem discussão:

  • .venv/ no .gitignore. Sempre. O que se versiona é o requirements.txt/.lock, não o resultado dele.
  • Corrigir venv quebrado é rm -rf .venv e recriar. Não perca a tarde investigando.
  • Um venv por projeto, dentro do próprio projeto, com o nome .venv — é o que VS Code, PyCharm, uv, pytest e a maioria das ferramentas procuram sozinhas.
  • Nunca copie um venv para outro caminho ou máquina; copie o arquivo de dependências.

31.7 Três casos que aparecem

Enxergar os pacotes do sistema. --system-site-packages cria um ambiente que também vê o dist-packages:

python3 -m venv --system-site-packages .venv-aberto
.venv-aberto/bin/python -c "import rich; print(rich.__file__)"
/usr/lib/python3/dist-packages/rich/__init__.py

É útil quando o sistema tem algo caro de compilar (python3-numpy, python3-gi, ligações de GTK ou de GDAL) e você quer aproveitar em vez de recompilar. O custo é abrir mão de metade do isolamento: o ambiente passa a depender do que a máquina tem instalado, e o problema volta a ser “na minha máquina funciona”.

pip desatualizado. O pip que vem no venv é o embutido no interpretador, que pode estar velho:

[notice] A new release of pip is available: 26.1.1 -> 26.2.1

python3 -m venv --upgrade-deps .venv já cria o ambiente com o pip mais recente do PyPI, o que evita o aviso em todo comando.

pip ou python -m pip. Dentro de um venv ativo, os dois são o mesmo programa. Fora dele, ou em máquina com vários Pythons, pip pode ser o de outra instalação — e você instala um pacote onde não queria, sem nenhum erro. python -m pip é sempre o pip daquele interpretador, por construção:

.venv/bin/python -m pip --version
pip 26.1.1 from /home/vitor/lab31/.venv/lib/python3.13/site-packages/pip (python 3.13)

Em script, em CI e em documentação, use a forma longa. Ela nunca erra o alvo.

31.8 Onde instalar o quê

Sobre a saída de emergência que a mensagem de erro oferece: --break-system-packages faz exatamente o que o nome diz. Existe para conserto de sistema já quebrado e para contêiner descartável onde não há nada a preservar. Em máquina de trabalho, é a linha que você digita hoje e lamenta em três meses, quando o apt parar de funcionar por causa de uma versão de urllib3. sudo pip install é a mesma coisa com privilégio, e não tem justificativa nenhuma.

31.9 🐍 Jeito Pythônico

Um venv por projeto, chamado .venv, no .gitignore. O fluxo completo de um projeto novo cabe em quatro linhas:

python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m pip freeze > requirements.lock

python -m pip, nunca pip solto, em script e em documentação.

Duas listas, dois papéis: requirements.txt escrito à mão com as dependências diretas; requirements.lock gerado por pip freeze. Quem confunde as duas acaba com um arquivo que ninguém ousa editar.

# antipadrão: um arquivo só, gerado, com tudo dentro
pip freeze > requirements.txt   # 200 linhas, 6 delas suas

Nunca sudo pip, nunca --break-system-packages em máquina que você usa para trabalhar.

Ferramenta de linha de comando vai com pipx, não no venv do projeto — ruff, httpie e black não são dependências do seu código, e instalá-las junto polui o requirements.lock de todo mundo.

Não versione o venv, não mova o venv, não conserte o venv. Recrie.

Fixe versão em aplicação, use faixa em biblioteca. Aplicação quer reprodutibilidade (==); biblioteca quer conviver com as escolhas de quem a usa (>=13,<14). Fixar versão exata numa biblioteca é a receita de conflito insolúvel para o resolvedor.

Sobre versões:

  • Python 3.3 — venv entrou na biblioteca padrão, substituindo o virtualenv externo (que ainda existe, é mais rápido e suporta Pythons antigos, mas raramente é necessário hoje).
  • Python 3.9 — importlib.metadata estabilizou, tornando pkg_resources desnecessário para descobrir versões e dependências instaladas.
  • Python 3.11 — venv passou a criar o ambiente bem mais rápido; PEP 668 começou a ser adotada pelas distribuições nesse período.
  • Python 3.12 — setuptools e wheel deixaram de ser instalados por padrão em venv novo; projetos que dependiam disso implicitamente precisaram declarar.
  • Python 3.13 — em ambientes com free-threading (a build sem GIL), pacotes com extensão em C precisam de roda própria; verifique sys._is_gil_enabled() antes de culpar o pip.

31.11 Resumo

  • error: externally-managed-environment (PEP 668) não é obstáculo a contornar: é a distribuição protegendo os 529 pacotes Python dos quais o sistema depende.
  • Um venv é um diretório com pyvenv.cfg, um link para o interpretador do sistema e um site-packages vazio e gravável. Ele muda sys.prefix, mantém sys.base_prefix, e é essa diferença que o define.
  • activate só mexe no PATH e em VIRTUAL_ENV. Chamar .venv/bin/python direto é equivalente — e é a forma certa em cron, systemd e CI.
  • pip install num venv escreve só dentro do projeto; fora dele, o mesmo import falha. É todo o isolamento que existe, e basta.
  • Um pacote pedido traz os que ele precisa: requirements.txt guarda o que você pediu, requirements.lock (gerado por pip freeze) guarda o que o resolvedor decidiu. São arquivos diferentes com donos diferentes.
  • pip freeze não guarda hash, origem nem plataforma — as travas de verdade são assunto do Capítulo 33.
  • Venv não é portátil: os comandos instalados guardam o caminho absoluto no shebang. Não versione, não mova, não conserte: recrie.
  • python -m pip acerta o interpretador sempre; pip solto, não. sudo pip e --break-system-packages não têm lugar em máquina de trabalho.
