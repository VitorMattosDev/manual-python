63  YAML, TOML e arquivos de configuração

O coletor dos dois capítulos anteriores tem, espalhados pelo código, um endereço de banco, um intervalo de 300 segundos, um limite de potência e o nível de registro. Todos escritos como literais. Mudar o intervalo para 60 segundos numa madrugada de incidente significa editar o fonte, e editar o fonte em produção significa que o que roda deixou de ser o que está no Git.

A saída é óbvia e antiga: pôr essas decisões num arquivo. A pergunta é qual formato — e aqui o Python tem uma resposta oficial desde a versão 3.11, além de uma segunda que domina o mundo dos contêineres e traz uma armadilha que já derrubou serviço de gente séria.

JSON, visto no Capítulo 62, é péssimo para isso: não aceita comentário, não perdoa vírgula sobrando e obriga a aspas em toda chave. Configuração é feita para ser lida e editada por gente, e é aí que TOML e YAML entram.

63.1 TOML: a resposta oficial

import tomllib

with open("config.toml", "rb") as f:
    cfg = tomllib.load(f)

tomllib entrou na biblioteca padrão no Python 3.11 (PEP 680) e é o formato que o próprio ecossistema já adotou — o pyproject.toml do Capítulo 32 é TOML. Não há dependência a instalar.

O arquivo se parece com isto:

# configuracao do coletor
nome = "coletor-zona-sul"
intervalo = 300
ativo = true
limite_potencia = -30.0

[banco]
host = "10.0.0.20"
porta = 5432
tempo_limite = 5.0

[banco.pool]
minimo = 2
maximo = 10

[[equipamento]]
nome = "olt-central"
ip = "10.0.0.1"
portas = [1, 2, 3]

[[equipamento]]
nome = "olt-norte"
ip = "10.0.0.2"
portas = [4, 5]

E vira estrutura Python sem cerimônia nenhuma:

cfg["nome"], cfg["banco"]["pool"]["maximo"]
[e["nome"] for e in cfg["equipamento"]]
coletor-zona-sul 10
['olt-central', 'olt-norte']

Três construções e o formato está explicado. chave = valor no topo é a raiz. [banco] abre uma tabela, que vira um dicionário aninhado — e [banco.pool] aninha mais um nível sem indentação nenhuma, o que evita a classe inteira de erros de espaçamento. [[equipamento]], com colchete duplo, é um vetor de tabelas: cada bloco repetido acrescenta um item à lista.

63.1.1 Os tipos vêm prontos

  nome             str
  intervalo        int
  ativo            bool
  limite_potencia  float

Diferente do CSV, onde tudo é string, TOML tem tipos declarados na sintaxe: aspas fazem string, algarismos fazem número, true/false fazem booleano. E, ao contrário do JSON, distingue inteiro de ponto flutuante.

Tem até tipos de data nativos, que já chegam como objetos do datetime (Capítulo 56):

lancamento = 2026-08-12
inicio = 2026-08-12T03:14:22-03:00
hora = 03:14:22
  lancamento  datetime.date(2026, 8, 12)                    date
  inicio      datetime.datetime(2026, 8, 12, 3, 14, 22, tzinfo=datetime.timezone(datetime.timedelta(days=-1, seconds=75600))) datetime
  hora        datetime.time(3, 14, 22)                      time

O deslocamento -03:00 virou um tzinfo correto — sem strptime, sem formato combinado por escrito, sem ambiguidade.

63.1.2 O modo binário, que não é opcional

with open("config.toml", "r", encoding="utf-8") as f:
    tomllib.load(f)
TypeError: File must be opened in binary mode, e.g. use `open('foo.toml', 'rb')`

tomllib.load exige "rb". A razão é boa: a especificação do TOML determina que o arquivo é UTF-8, então o módulo decodifica ele mesmo em vez de aceitar o que o encoding da plataforma tiver decidido. O erro é claro e vem com a solução — é dos poucos casos em que a mensagem ensina.

63.1.3 Quando o arquivo está errado

  'a = '                   -> Invalid value (at end of document)
  'a = "x"\na = "y"'       -> Cannot overwrite a value (at end of document)
  '[a]\nb = 1\n[a]\nc = 2' -> Cannot declare ('a',) twice (at line 3, column 3)
  'a = 01'                 -> Expected newline or end of document after a statement (at line 1, column 6)

tomllib.TOMLDecodeError é subclasse de ValueError. Repare na segunda e na terceira: chave duplicada é erro em TOML, ao contrário do JSON, onde a última vencia em silêncio. Numa configuração, isso é exatamente o que se quer — duas linhas intervalo = no mesmo arquivo é sempre um engano, e é bom saber disso na leitura e não em produção.

A quarta linha antecipa um assunto: 01 não é um inteiro válido em TOML, justamente porque zero à esquerda é ambíguo. Guarde essa, porque o YAML resolveu o mesmo problema de outro jeito.

63.1.4 tomllib só lê

tomllib tem dumps? False
['TOMLDecodeError', 'load', 'loads']

Três nomes, e nenhum escreve. Foi decisão deliberada: gerar TOML corretamente — preservando comentários, ordem e estilo — é bem mais difícil que analisá-lo, e a biblioteca padrão não quis carregar isso. Quando for preciso escrever, tomli-w gera um arquivo novo e tomlkit edita preservando comentários e formatação.

Mas vale perguntar se é preciso. Configuração é escrita por gente e lida por programa; programa que reescreve a própria configuração costuma ser um sinal de que aquilo era estado, e estado vai para um banco (Capítulo 65 trata disso) ou para um arquivo de dados, não para o config.toml que alguém versiona.

63.2 YAML: mais poderoso, e é esse o problema

YAML não está na biblioteca padrão. pip install pyyaml, e o mesmo conteúdo fica assim:

nome: coletor-zona-sul
intervalo: 300
ativo: true

banco:
  host: 10.0.0.20
  porta: 5432
  pool:
    minimo: 2
    maximo: 10

equipamento:
  - nome: olt-central
    ip: 10.0.0.1
    portas: [1, 2, 3]
  - nome: olt-norte
    ip: 10.0.0.2
    portas: [4, 5]

descricao: |
  coletor da zona sul
  roda de madrugada
import yaml

with open("config.yaml", encoding="utf-8") as f:
    cfg = yaml.safe_load(f)
coletor-zona-sul 10
['olt-central', 'olt-norte']
'coletor da zona sul\nroda de madrugada\n'

É inegavelmente mais enxuto: sem aspas, sem colchetes duplos, aninhamento por indentação. O | preserva quebras de linha num bloco de texto, o que TOML só faz com aspas triplas. E tem um recurso que nenhum outro formato de configuração tem — âncoras e mesclagem:

padrao: &padrao
  tempo_limite: 5.0
  tentativas: 3

producao:
  <<: *padrao
  host: 10.0.0.20

teste:
  <<: *padrao
  host: 127.0.0.1
  tentativas: 1
producao: {'tempo_limite': 5.0, 'tentativas': 3, 'host': '10.0.0.20'}
teste   : {'tempo_limite': 5.0, 'tentativas': 1, 'host': '127.0.0.1'}

&padrao define, *padrao referencia, <<: mescla — e teste sobrescreveu tentativas sem repetir o resto. É por isso que YAML domina onde há muito ambiente parecido: Kubernetes, GitHub Actions, Ansible, docker-compose.

63.2.1 O problema da Noruega

Agora o preço. YAML tenta adivinhar o tipo de cada valor não citado, e adivinha demais:

noruega: NO
sim: yes
versao: 1.20
octal: 0o17
cep: 01310
telefone: +55 11 99999-9999
vazio:
nulo: null
til: ~
  noruega    False                  bool
  sim        True                   bool
  versao     1.2                    float
  octal      '0o17'                 str
  cep        712                    int
  telefone   '+55 11 99999-9999'    str
  vazio      None                   NoneType
  nulo       None                   NoneType
  til        None                   NoneType

Leia devagar, porque cada linha é um incidente que já aconteceu.

NO, o código ISO da Noruega, virou False — o bug tem nome próprio e é conhecido como the Norway problem. yes também é booleano, e junto com ele on, off, y, n e true/false em qualquer combinação de maiúsculas.

1.20 virou 1.2: um número de versão perdeu o zero à direita e deixou de comparar igual à string que estava no outro arquivo.

E a pior: 01310 virou 712. Não é truncamento — é interpretação octal, herança do YAML 1.1 que o PyYAML implementa. Todo CEP, código de banco, número de agência e identificador com zero à esquerda é reinterpretado como base 8, em silêncio, e sai um número que existe e está errado. Compare com o TOML, que recusa a = 01 com erro de sintaxe: um formato diz “isso é ambíguo, decida”; o outro decide sozinho.

Ironicamente, 0o17 — a notação octal do YAML 1.2 e do próprio Python — virou string, porque o PyYAML segue o 1.1. A inconsistência é completa.

A defesa é só uma: cite tudo que for identificador. noruega: "NO", cep: "01310", versao: "1.20". E, quando o dado vem de fora, validar com esquema em vez de confiar no que o analisador decidiu.

63.2.2 safe_load, nunca load

Historicamente, yaml.load construía objetos Python arbitrários a partir do arquivo, o que transforma um arquivo de configuração numa execução de código — a mesma classe de problema que o próximo capítulo detalha com o pickle. A partir do PyYAML 6 o descuido ficou impossível:

yaml.load sem Loader levanta? TypeError: load() missing 1 required positional argument: 'Loader'

yaml.safe_load é a função a usar, sempre, e constrói apenas os tipos básicos. yaml.safe_dump é a contraparte na escrita, com allow_unicode=True para não escapar acentos e sort_keys=False para preservar a ordem.

63.2.3 E a indentação

yaml.safe_load("a:\n\t- 1\n")
ScannerError
while scanning for the next token

Tabulação é proibida em YAML, e o erro não menciona a palavra “tab” na primeira linha. Como o significado depende inteiramente da indentação, um espaço a mais ou a menos reaninha um bloco inteiro sem gerar erro nenhum — o arquivo continua válido e significa outra coisa. É a razão pela qual arquivo YAML grande é notoriamente difícil de manter, e o motivo pelo qual o TOML abandonou a indentação como sintaxe.

63.3 As camadas de uma configuração

Nenhum programa sério é configurado por um arquivo só. O arranjo padrão tem quatro camadas, cada uma sobrescrevendo a anterior:

def carregar(caminho, prefixo="COLETOR_"):
    with open(caminho, "rb") as f:
        conf = tomllib.load(f)
    for chave, valor in os.environ.items():
        if chave.startswith(prefixo):
            conf[chave[len(prefixo):].lower()] = valor
    return conf
nome     : coletor-emergencia
intervalo: '60'

Note as aspas em '60': variável de ambiente é sempre string (Capítulo 55). Se a camada de arquivo entregou um int e a de ambiente entrega str, o programa passa a receber tipos diferentes para a mesma chave conforme o ambiente — um defeito que só aparece em produção. Converter na fronteira, com uma tabela de tipos por chave, é o que evita isso.

63.3.1 Segredos não moram no arquivo

A regra que merece uma linha própria: senha, token e chave de API nunca vão para o arquivo de configuração, porque ele é versionado. Um segredo commitado continua no histórico do Git depois de removido, e continua no clone de todo mundo que já baixou o repositório.

Eles entram por variável de ambiente, por arquivo .env fora do controle de versão (com .env no .gitignore e um .env.exemplo sem valores dentro dele), ou por um cofre de verdade. O config.toml versionado declara que existe uma senha de banco; o valor vem de outro lugar.

63.4 Escolher

Para configuração de aplicação escrita à mão, TOML: está na biblioteca padrão, tem tipos explícitos, recusa ambiguidade, e é o que o ecossistema Python já usa no pyproject.toml. Para empacotamento e ferramentas, TOML não é escolha — é o padrão.

YAML entra quando o ambiente já é YAML (Kubernetes, GitHub Actions, Ansible), quando há muita configuração repetida que as âncoras eliminam, ou quando há blocos longos de texto. Nesses casos, safe_load, aspas em todo identificador e validação por esquema.

JSON para configuração, só quando alguma ferramenta obriga. É o formato de troca entre programas, não de conversa com gente.

E .env para segredos e para as poucas chaves que mudam por ambiente — plano, sem tipos, sem aninhamento, e por isso mesmo difícil de errar.

63.5 🐍 Jeito Pythônico

TOML para configuração nova. Está na biblioteca padrão desde a 3.11 e não tem ambiguidade de tipos.

# antipadrão: JSON sem comentário, ou pior, configuração no código
INTERVALO = 300
# pythônico
with caminho.open("rb") as f:      # "rb" é obrigatório
    cfg = tomllib.load(f)

yaml.safe_load, nunca yaml.load. Arquivo de configuração não é lugar de executar código.

Cite todo identificador em YAML. "NO", "01310", "1.20" — sem aspas, o analisador decide por você e decide errado.

Converta os tipos na fronteira. Variável de ambiente é sempre string.

Padrões no código que funcionem sozinhos, para que o programa rode sem arquivo nenhum.

Segredo fora do arquivo versionado, sempre.

Valide a configuração no início do programa, não na hora de usar cada chave. Um erro de digitação em intervalo tem de falhar na partida, não três horas depois.

Um só ponto de leitura da configuração, devolvendo um objeto imutável (uma dataclass congelada, do Capítulo 46) em vez de um dicionário que qualquer módulo altera.

Sobre versões:

  • Python 3.11 — tomllib na biblioteca padrão (PEP 680), somente leitura.
  • Python 3.13 — mensagens de erro do tomllib com linha e coluna, como no exemplo de tabela duplicada.
  • PyYAML 6.0 — yaml.load passou a exigir o argumento Loader, encerrando o padrão inseguro.

Do ecossistema: tomli-w escreve TOML e tomlkit edita preservando comentários; python-dotenv carrega .env; e pydantic-settings faz o trabalho inteiro deste capítulo — camadas, conversão de tipos e validação — com uma classe declarativa. Em aplicação de porte, ele é o caminho mais curto entre uma configuração e uma configuração correta, e volta no Volume 14.

63.6 🧪 Laboratório

Objetivo: montar uma configuração em camadas e provocar, de propósito, cada armadilha de tipo.

1. Preparo.

mkdir -p ~/lab63 && cd ~/lab63
python3 -m venv .venv && source .venv/bin/activate
python -m pip install pyyaml

2. TOML básico. Escreva o config.toml da abertura e leia com tomllib. Imprima cfg["banco"]["pool"]["maximo"] e a lista de nomes dos equipamentos.

3. O modo binário. Abra o mesmo arquivo com "r" e confirme:

TypeError: File must be opened in binary mode, e.g. use `open('foo.toml', 'rb')`

Escreva num comentário por que a especificação justifica essa exigência.

4. Tipos. Imprima o type() de cada chave do topo. Acrescente as três linhas de data e confirme que voltam como date, datetime e time — com o fuso correto no segundo.

5. TOML quebrado. Provoque os quatro erros, incluindo chave duplicada e tabela declarada duas vezes:

  'a = "x"\na = "y"'       -> Cannot overwrite a value (at end of document)
  '[a]\nb = 1\n[a]\nc = 2' -> Cannot declare ('a',) twice (at line 3, column 3)

Compare com o que o json.loads fez com '{"a": 1, "a": 2}' no capítulo anterior.

6. Só leitura. Confirme que tomllib não tem dumps. Instale tomli-w, grave a configuração de volta e observe o que aconteceu com os comentários.

7. YAML equivalente. Escreva o mesmo conteúdo em YAML e confirme com == que as duas leituras produzem estruturas iguais nas chaves do topo.

8. O problema da Noruega. Carregue o bloco de armadilhas e reproduza a tabela:

  noruega    False                  bool
  cep        712                    int
  versao     1.2                    float

Explique o 712 em uma linha. Depois cite os três valores e confirme que voltam como str.

9. Segurança. Rode yaml.load("a: 1") sem Loader e confirme o TypeError. Leia a documentação do SafeLoader e escreva por que o padrão antigo era perigoso.

10. Indentação. Ponha uma tabulação num arquivo YAML e observe o ScannerError. Depois, sem tabulação, mova um bloco dois espaços para a direita e confirme que o arquivo continua válido e significa outra coisa.

11. Âncoras. Reproduza o bloco com &padrao, *padrao e <<:, e confirme que teste sobrescreveu só tentativas. Tente o equivalente em TOML e escreva quantas linhas custou.

12. Camadas. Implemente carregar() com as quatro camadas. Defina COLETOR_INTERVALO=60 e confirme:

intervalo: '60'

Corrija a conversão de tipo e confirme que passa a ser int. Depois acrescente um argumento de linha de comando que sobrescreve o ambiente.

13. Validação na partida. Faça a configuração ser lida para uma dataclass congelada com tipos anotados, e confirme que uma chave com nome errado falha na partida, com mensagem que diga qual chave.

14. Segredo. Ponha uma senha no config.toml, commite, remova e commite de novo. Recupere-a com git log -p. Refaça com variável de ambiente e .env no .gitignore.

63.7 Resumo

  • Configuração no código obriga a editar o fonte para mudar comportamento, e o que roda deixa de ser o que está no Git.
  • JSON é ruim para configuração: sem comentários, sem vírgula sobrando, aspas em toda chave.
  • tomllib está na biblioteca padrão desde a 3.11, só lê, e exige o arquivo aberto em "rb" porque TOML é sempre UTF-8.
  • TOML tem tipos na sintaxe — inteiro, ponto flutuante, booleano, data, hora e data-hora com fuso — e entrega objetos datetime prontos.
  • [tabela] aninha por nome e [[vetor]] repete blocos como itens de lista, sem depender de indentação.
  • Chave ou tabela duplicada em TOML é erro; em JSON, a última vencia em silêncio.
  • tomllib não escreve por decisão de projeto; tomli-w gera e tomlkit edita preservando comentários — mas programa que reescreve a própria configuração provavelmente está guardando estado no lugar errado.
  • YAML é mais enxuto, tem blocos de texto com | e âncoras com &/*/<<: que eliminam repetição — por isso domina Kubernetes, Ansible e GitHub Actions.
  • YAML infere tipos de valores não citados e erra: NO vira False, yes vira True, 1.20 vira 1.2 e 01310 vira 712 por leitura octal — tudo em silêncio.
  • A defesa é citar todo identificador e validar por esquema; TOML resolve o mesmo caso recusando 01 como erro de sintaxe.
  • yaml.safe_load sempre; o antigo yaml.load construía objetos arbitrários, e desde o PyYAML 6 exige Loader explícito.
  • Tabulação é proibida em YAML, e indentação errada produz arquivo válido com outro significado.
  • A configuração de produção tem quatro camadas — padrões, arquivo, ambiente, linha de comando — em ordem crescente de precedência.
  • Variável de ambiente é sempre string; sem conversão na fronteira, a mesma chave chega com tipos diferentes conforme o ambiente.
  • Segredo nunca vai para o arquivo versionado: o histórico do Git o preserva depois de removido, em todos os clones.
