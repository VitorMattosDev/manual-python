62  JSON, CSV e formatos tabulares

O extrator do Capítulo 61 funciona: as 40 mil linhas de log viraram dicionários com ip, rota, status e bytes. Agora começa a segunda metade do trabalho, que é onde os dados costumam se perder — alguém precisa guardar isso, e outro alguém precisa ler o que foi guardado.

A tentação, nesse ponto, é escrever o próprio formato: um campo por linha, separado por vírgula, fácil de gerar com f-string. Ele funciona por três semanas, até o dia em que um campo contém uma vírgula. Ou uma quebra de linha. Ou aspas. Aí o arquivo inteiro fica ilegível e ninguém sabe dizer quando começou.

Este capítulo é sobre os dois formatos que já resolveram isso: JSON, que carrega estrutura, e CSV, que carrega tabela. Os dois estão na biblioteca padrão, os dois têm armadilhas conhecidas, e as armadilhas são quase todas de ida e volta — o dado sai e não volta igual.

62.1 JSON: o formato universal de estrutura

import json

leitura = {
    "onu": "onu-00043",
    "potencia": -29.8,
    "ativa": True,
    "alarmes": ["temperatura", "sinal"],
    "vizinha": None,
}

print(json.dumps(leitura))
{"onu": "onu-00043", "potencia": -29.8, "ativa": true, "alarmes": ["temperatura", "sinal"], "vizinha": null}

Quatro nomes resolvem o módulo inteiro: dumps (objeto → string), loads (string → objeto), dump (objeto → arquivo) e load (arquivo → objeto). O s no fim significa string; sem ele, o destino é um arquivo.

Repare no que mudou: True virou true e None virou null. JSON não é Python — é um formato com seis tipos (objeto, vetor, string, número, booleano e nulo), e cada valor Python precisa caber num deles.

Para leitura humana, indent:

print(json.dumps(leitura, indent=2, ensure_ascii=False))
{
  "onu": "onu-00043",
  "potencia": -29.8,
  "ativa": true,
  "alarmes": [
    "temperatura",
    "sinal"
  ],
  "vizinha": null
}

62.1.1 ensure_ascii, que quase sempre atrapalha

d = {"cidade": "São João da Boa Vista", "situação": "não conectada"}

json.dumps(d)
json.dumps(d, ensure_ascii=False)
{"cidade": "S\u00e3o Jo\u00e3o da Boa Vista", "situa\u00e7\u00e3o": "n\u00e3o conectada"}
{"cidade": "São João da Boa Vista", "situação": "não conectada"}

O padrão escapa tudo que não seja ASCII, herança de uma época em que não se podia contar com o transporte preservar os bytes. Os dois textos são JSON válido e produzem o mesmo objeto na volta, mas o primeiro é ilegível e ocupa três vezes mais espaço em texto acentuado. Hoje, com UTF-8 em toda parte (Capítulo 14), ensure_ascii=False é o que se quer — e junto com ele, encoding="utf-8" explícito na abertura do arquivo.

62.1.2 A ida e volta que não é redonda

volta = json.loads(json.dumps(leitura))
volta == leitura
True

Para esse dicionário, sim. Mas basta um tipo a mais:

original = {"quando": (2026, 8, 12), "chave_int": {1: "um"}}
ida = json.loads(json.dumps(original))
tupla virou : list
chave int   : {'1': 'um'}

Duas perdas silenciosas, sem aviso nenhum. Tupla vira lista, porque JSON só tem um tipo de sequência. E chave numérica vira string, porque em JSON toda chave de objeto é string. Nenhuma das duas levanta exceção — o programa segue, e o dados[1] que funcionava passa a dar KeyError do outro lado da serialização.

Outros tipos são mais honestos e falham alto:

date      -> TypeError: Object of type date is not JSON serializable
Decimal   -> TypeError: Object of type Decimal is not JSON serializable
set       -> TypeError: Object of type set is not JSON serializable

datetime, Decimal, set, bytes, complex e qualquer classe própria não têm representação em JSON. O parâmetro default= recebe uma função chamada só para o que o módulo não sabe converter:

def conversor(obj):
    if isinstance(obj, (datetime.date, datetime.datetime)):
        return obj.isoformat()
    if isinstance(obj, decimal.Decimal):
        return str(obj)
    if isinstance(obj, set):
        return sorted(obj)
    raise TypeError(f"{type(obj).__name__} nao serializavel")

json.dumps(registro, default=conversor, ensure_ascii=False)
{"quando": "2026-08-12", "exato": "0.1", "alarmes": ["sinal", "temperatura"]}

Repare que o raise final é obrigatório: sem ele, um tipo esquecido devolveria None e viraria null no arquivo — trocando um erro barulhento por um dado errado.

Na volta, object_hook faz o caminho inverso:

def reidrata(dic):
    if "quando" in dic:
        dic["quando"] = datetime.date.fromisoformat(dic["quando"])
    return dic

json.loads(texto, object_hook=reidrata)
{'onu': 'onu-00043', 'quando': datetime.date(2026, 8, 12)} date

62.1.3 Números: onde a precisão escorre

json.dumps({"v": 0.1 + 0.2})
json.loads('{"v": 0.1}', parse_float=decimal.Decimal)
{"v": 0.30000000000000004}
{'v': Decimal('0.1')}

JSON tem um tipo numérico só, e o Python o lê como float — com todas as consequências do Capítulo 10. Para dinheiro e medição exata, parse_float=decimal.Decimal na leitura e default=str na escrita mantêm o valor íntegro.

Há ainda um detalhe que quebra interoperabilidade:

json.dumps({"v": float("nan")})
{"v": NaN}

Isso não é JSON válido — a especificação não tem NaN nem Infinity. O módulo os emite por padrão, e o analisador do outro lado (JavaScript, Go, um banco de dados) rejeita o arquivo. Em qualquer dado que saia do processo, allow_nan=False:

ValueError: Out of range float values are not JSON compliant: inf

62.1.4 Quando o texto não é JSON

'{"a": 1,}'  -> Illegal trailing comma before end of object (linha 1, coluna 8)
"{'a': 1}"   -> Expecting property name enclosed in double quotes (linha 1, coluna 2)
'{"a": 1'    -> Expecting ',' delimiter (linha 1, coluna 8)
''           -> Expecting value (linha 1, coluna 1)

json.JSONDecodeError é subclasse de ValueError e traz msg, lineno, colno e pos — o suficiente para apontar o problema num arquivo de 200 MB. As duas primeiras mensagens são o resumo das diferenças entre JSON e a sintaxe de dicionário do Python: nada de vírgula sobrando, nada de aspas simples.

Vale saber de uma última assimetria: chave repetida não é erro.

json.loads('{"a": 1, "a": 2}')
{'a': 2}

A última vence, em silêncio.

62.2 Arquivos, e o formato que resolve os grandes

with arq.open("w", encoding="utf-8") as f:
    json.dump([leitura], f, ensure_ascii=False, indent=2)

with arq.open(encoding="utf-8") as f:
    dados = json.load(f)

json.load lê o arquivo inteiro para a memória e constrói o objeto todo de uma vez. Para 200 MB de leituras isso é um problema — e é aqui que entra o formato que virou padrão de log estruturado, o JSON Lines (.jsonl): um objeto JSON completo por linha.

{"onu": "onu-00043", "potencia": -29.8}
{"onu": "onu-00045", "potencia": -31.7}
{"onu": "onu-00052", "potencia": null}
with jl.open(encoding="utf-8") as f:
    piores = [json.loads(l) for l in f if json.loads(l)["potencia"] is not None]
lidas sem carregar tudo: 2

Três vantagens que o JSON comum não tem: dá para processar linha a linha sem carregar o arquivo, dá para acrescentar ao fim sem reescrever nada, e uma linha corrompida não invalida o arquivo inteiro. É o formato natural para o log estruturado do Capítulo 60, e o que quase toda ferramenta de agregação espera.

Dois parâmetros que aparecem em produção: sort_keys=True torna a saída determinística, o que permite comparar duas serializações ou versioná-las no Git; e separators=(",", ":") remove os espaços:

padrao  : {"onu": "onu-00043", "potencia": -29.8, "ativa": true}
compacto: {"onu":"onu-00043","potencia":-29.8,"ativa":true}
54 vs 49 bytes

62.3 CSV: por que não dá para usar split

O formato parece trivial. Ele não é. Considere estas quatro linhas, geradas pelo csv.writer:

onu,potencia,observacao
onu-00043,-29.8,ok
onu-00045,-31.7,"abaixo do limite, ""grave"""
onu-00052,,"sem resposta
reiniciar"

Um registro tem uma vírgula dentro do campo, aspas dentro do campo e um campo vazio; outro tem uma quebra de linha dentro do campo — de modo que o arquivo tem quatro registros em cinco linhas físicas. Agora o que o split faz com a terceira:

bruto.split(",")
linha: 'onu-00045,-31.7,"abaixo do limite, ""grave"""'
split : ['onu-00045', '-31.7', '"abaixo do limite', ' ""grave"""']

Quatro campos onde havia três, com aspas espalhadas. E o csv.reader:

with csv_path.open(newline="", encoding="utf-8") as f:
    for linha in csv.reader(f):
        print(linha)
['onu', 'potencia', 'observacao']
['onu-00043', '-29.8', 'ok']
['onu-00045', '-31.7', 'abaixo do limite, "grave"']
['onu-00052', '', 'sem resposta\nreiniciar']

Três campos, aspas desfeitas, quebra de linha preservada dentro do valor. As regras de citação do CSV existem por um motivo, e reimplementá-las com split e replace é o caminho conhecido para um analisador que funciona nos dados de teste.

62.3.1 DictReader, DictWriter e o que eles fazem com o inesperado

with csv_path.open(newline="", encoding="utf-8") as f:
    for linha in csv.DictReader(f):
        print(linha["onu"], repr(linha["potencia"]))
onu-00043 '-29.8'
onu-00045 '-31.7'
onu-00052 ''

DictReader usa a primeira linha como cabeçalho e devolve dicionários, o que elimina os índices posicionais. Repare no ponto que custa caro: tudo é string. O -29.8 é o texto '-29.8', e o campo vazio é '', não None. Converter é trabalho de quem lê:

def para_float(v):
    return float(v) if v else None
[{'onu': 'onu-00043', 'potencia': -29.8}, {'onu': 'onu-00045', 'potencia': -31.7}, {'onu': 'onu-00052', 'potencia': None}]

E o comportamento com linha mal formada, que é bom conhecer antes de encontrá-lo:

{'onu': 'onu-1', 'potencia': '-29.8', 'obs': None}
{'onu': 'onu-2', 'potencia': '-30.1', 'obs': 'ok', None: ['sobrando']}

Campo faltando vira None; campo sobrando vai para uma chave None com uma lista. Nenhum dos dois levanta exceção — então validar o comprimento das linhas é responsabilidade de quem lê.

Na escrita, DictWriter é o inverso, com dois parâmetros úteis: extrasaction="ignore" descarta chaves que não estão no cabeçalho (sem ele, ValueError), e restval= preenche as que faltam.

'onu,potencia\r\nonu-00043,-29.8\r\n'
sem extrasaction: dict contains fields not in fieldnames: 'extra'
'onu-00099,SEM DADO\r\n'

62.3.2 newline="": o parâmetro que não é opcional

with ruim.open("w", encoding="utf-8") as f:            # errado
    csv.writer(f).writerow(["a", "b"])

with bom.open("w", newline="", encoding="utf-8") as f:  # certo
    csv.writer(f).writerow(["a", "b"])
sem newline='': b'a,b\r\r\n'
com newline='': b'a,b\r\n'

O módulo csv escreve \r\n por conta própria, porque é o que o formato manda. No Windows, a tradução automática de fim de linha do modo texto transforma o \r\n em \r\r\n, e o arquivo sai com uma linha em branco entre cada registro — ou, dependendo do leitor, simplesmente errado.

Todo arquivo CSV se abre com newline="", na leitura e na escrita. Na leitura, o motivo é ainda melhor: sem ele, uma quebra de linha dentro de um campo citado pode ser traduzida e corromper o registro. É uma linha de código, e ela é obrigatória em qualquer plataforma — o código que só roda no Linux é o que esconde o defeito até o primeiro colega de Windows.

62.3.3 Dialetos, separadores e a planilha do outro

Nem todo CSV usa vírgula. Em pt-BR, onde a vírgula é o separador decimal, o padrão de planilha é o ponto e vírgula:

w = csv.writer(saida, delimiter=";", quoting=csv.QUOTE_ALL)
w.writerow(["onu-00043", "-29,8", "ok"])
'"onu-00043";"-29,8";"ok"\r\n'

delimiter, quotechar, quoting (QUOTE_MINIMAL, QUOTE_ALL, QUOTE_NONNUMERIC, QUOTE_NONE), escapechar e lineterminator cobrem as variações. Para TSV, delimiter="\t".

Quando o arquivo vem de fora e ninguém sabe o formato, Sniffer chuta:

delimitador detectado: ';'
tem cabecalho: True

Chuta bem em arquivo limpo, e erra em arquivo pequeno ou irregular. Serve como padrão inicial, não como certeza — e nunca sem uma amostra de bom tamanho.

62.3.4 O BOM que o Excel deixa

p.write_text("onu,potencia\nonu-00043,-29.8\n", encoding="utf-8-sig")
bytes iniciais: b'\xef\xbb\xbfonu'
lido como utf-8    : ['\ufeffonu', 'potencia']
lido como utf-8-sig: ['onu', 'potencia']

Aqueles três bytes no início são o BOM (Capítulo 14), que o Excel escreve para reconhecer o arquivo como UTF-8. Lido como utf-8 puro, ele gruda no primeiro nome de coluna — e o resultado é um KeyError: 'onu' cuja mensagem parece dizer que a coluna não existe, quando ela está ali. encoding="utf-8-sig" na leitura resolve, e funciona igualmente bem em arquivo sem BOM. Para CSV destinado ao Excel, escrever com utf-8-sig evita que os acentos apareçam trocados.

62.4 Escolher entre os dois

json:  205000 bytes
csv :   85014 bytes
csv e 59% menor

Cinco mil registros de dois campos. O CSV é 59% menor porque não repete os nomes das colunas em cada registro — e a diferença cresce com o número de campos.

A decisão, porém, não é de tamanho: CSV é para tabela, JSON é para estrutura. Se todo registro tem os mesmos campos e nenhum deles é uma lista ou um objeto aninhado, CSV é mais compacto, abre em planilha e é lido por qualquer ferramenta. Se há aninhamento, campos opcionais ou tipos que importam, JSON. Achatar uma estrutura aninhada em colunas do tipo endereco.cidade funciona, mas é o sinal de que o formato está errado.

Para dados grandes de verdade — milhões de linhas, leitura repetida, colunas de tipos fixos — os dois perdem para formatos binários colunares como Parquet, assunto do Volume 13. E para dados que precisam ser consultados em vez de lidos por inteiro, a resposta é um banco, dois capítulos à frente.

62.5 🐍 Jeito Pythônico

ensure_ascii=False e encoding="utf-8" explícitos. O padrão escapa acento sem necessidade e o encoding implícito varia com a plataforma.

# antipadrão: encoding da plataforma, acentos escapados, sem newline
open("dados.csv", "w").write(",".join(campos))
# pythônico
with caminho.open("w", newline="", encoding="utf-8") as f:
    csv.writer(f).writerow(campos)

newline="" em todo arquivo CSV, leitura e escrita, em toda plataforma.

DictReader e DictWriter, não índices posicionais.

Converta os tipos na entrada. Tudo que sai do CSV é string, e '' não é None.

default= que termina em raise. Devolver None para tipo desconhecido troca erro por dado errado.

allow_nan=False em qualquer JSON que saia do processo — NaN não é JSON válido.

JSON Lines para log e fluxo, JSON comum para configuração e resposta de API.

sort_keys=True quando a saída for comparada ou versionada.

Nunca split(",") num CSV, nem eval num JSON.

Nada de escrever o próprio formato delimitado. As regras de citação parecem simples e não são.

Sobre versões:

  • Python 3.6 — json.load/loads aceitam bytes além de str.
  • Python 3.9 — csv ganhou desempenho perceptível na leitura.
  • Python 3.12 — csv.QUOTE_NOTNULL e csv.QUOTE_STRINGS, que distinguem campo vazio de None na ida e na volta.
  • Python 3.13 — mensagens de erro do json mais precisas, com a posição exata (a vírgula sobrando do exemplo é uma delas).

Sobre alternativas: orjson e ujson são bem mais rápidos que o módulo padrão e valem quando a serialização aparece no perfil de desempenho; orjson já lida com datetime e UUID sem default=. Para validar a estrutura do que chegou — e não só a sintaxe —, pydantic é o padrão do ecossistema, tema do Volume 14. E pandas.read_csv resolve a leitura tabular com conversão de tipos, no Volume 13.

62.6 🧪 Laboratório

Objetivo: escrever e ler os dois formatos, e provocar de propósito cada perda silenciosa.

1. Preparo.

mkdir -p ~/lab62 && cd ~/lab62
python3 -m venv .venv && source .venv/bin/activate

2. Ida e volta. Serialize o dicionário leitura da abertura e confirme json.loads(json.dumps(x)) == x. Depois acrescente uma tupla e uma chave inteira e confirme que a igualdade quebra — sem exceção:

tupla virou : list
chave int   : {'1': 'um'}

3. Acentos. Compare dumps com e sem ensure_ascii=False sobre "São João da Boa Vista". Meça o tamanho dos dois em bytes e confirme que os dois produzem o mesmo objeto na volta.

4. Tipos que explodem. Tente serializar datetime.date, Decimal e set. Escreva o conversor com default=, confirme a saída, e depois remova o raise final e serialize um tipo não previsto. Observe o null aparecer no lugar do erro.

5. Volta com object_hook. Reconstrua o date na leitura e confirme o tipo.

6. Números. Rode json.dumps({"v": 0.1 + 0.2}) e explique a saída. Depois leia '{"v": 0.1}' com parse_float=decimal.Decimal. Por fim, serialize float("inf") com e sem allow_nan=False.

7. JSON quebrado. Provoque os quatro erros e imprima e.msg, e.lineno e e.colno:

'{"a": 1,}'  -> Illegal trailing comma before end of object (linha 1, coluna 8)

Depois leia '{"a": 1, "a": 2}' e explique o resultado.

sem newline='': b'a,b\r\r\n'

13. Linha torta. Leia um CSV com uma linha curta e uma longa demais, e observe o None e a chave None com lista. Escreva a verificação que rejeitaria as duas.

62.7 Resumo

  • dumps/loads trabalham com string, dump/load com arquivo; JSON tem seis tipos, e cada valor Python precisa caber num deles.
  • ensure_ascii=False deixa o acento legível e o arquivo menor; o padrão escapa tudo fora do ASCII por herança histórica.
  • Tupla volta como lista e chave numérica volta como string, sem exceção nenhuma — as duas perdas silenciosas do formato.
  • datetime, Decimal, set e bytes levantam TypeError; default= converte na ida e object_hook reconstrói na volta.
  • Toda função passada em default= termina com raise TypeError — sem isso, um tipo esquecido vira null.
  • JSON só tem float; parse_float=decimal.Decimal preserva valores exatos na leitura.
  • NaN e Infinity não são JSON válido, e o módulo os emite por padrão; allow_nan=False em tudo que sai do processo.
  • JSONDecodeError traz msg, lineno e colno; chave repetida não é erro e a última vence.
  • JSON Lines permite processar, acrescentar e sobreviver a linha corrompida — o formato certo para log e fluxo.
  • CSV cita campos com separador, aspas ou quebra de linha, e escapa aspas dobrando-a; um arquivo de N registros pode ter mais de N linhas físicas.
  • split(",") erra a contagem de campos sem levantar exceção; o módulo csv implementa as regras inteiras e não custa mais.
  • newline="" é obrigatório na leitura e na escrita de CSV, em toda plataforma — sem ele o Windows grava \r\r\n.
  • DictReader devolve strings para tudo, e campo vazio é '', não None; converter tipos é trabalho de quem lê.
  • Linha curta vira None e linha longa vira uma chave None com lista; nenhuma das duas levanta exceção.
  • BOM lido como utf-8 puro gruda no primeiro nome de coluna e produz um KeyError enganoso; utf-8-sig resolve nos dois casos.
  • CSV é para tabela e é bem menor; JSON é para estrutura. Achatar aninhamento em colunas é sinal de formato errado.
