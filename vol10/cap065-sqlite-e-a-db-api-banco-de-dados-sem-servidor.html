65  SQLite e a DB-API: banco de dados sem servidor

As 40 mil leituras do coletor estão num .jsonl, do jeito que o Capítulo 62 recomendou. O formato é bom: acrescenta ao fim, sobrevive a linha corrompida, qualquer ferramenta lê. Até chegar a pergunta:

Qual ONU teve mais respostas 504 entre 2h e 5h, nos últimos trinta dias?

Responder isso significa abrir trinta arquivos, ler cada linha, converter cada data, filtrar, agrupar e ordenar — em memória, do zero, toda vez. Funciona com 40 mil linhas. Com 40 milhões, não.

O que falta não é um formato melhor. É inverter a relação: em vez de carregar o dado para procurar dentro dele, deixar o dado no disco e mandar a pergunta até ele. Isso é um banco de dados, e o Python já traz um.

65.1 Um arquivo, nenhum servidor

import sqlite3

con = sqlite3.connect("coletor.db")
con.execute("""
    CREATE TABLE leitura (
        id        INTEGER PRIMARY KEY,
        onu       TEXT    NOT NULL,
        potencia  REAL,
        quando    TEXT    NOT NULL,
        UNIQUE (onu, quando)
    )
""")
con.commit()
SQLite  (motor) : 3.53.1
arquivo criado: coletor.db 12288 bytes

Não há serviço para instalar, porta para abrir, usuário para criar nem senha para guardar. sqlite3.connect abre (ou cria) um arquivo, e a biblioteca do SQLite roda dentro do seu processo. É o banco de dados mais implantado do mundo — está em todo celular, todo navegador e todo avião — e vem embutido no CPython.

O módulo sqlite3 implementa a DB-API 2.0 (PEP 249), a interface comum de todos os drivers de banco em Python. O que se aprende aqui é quase inteiramente transferível para PostgreSQL com psycopg ou MySQL com mysqlclient: connect, cursor, execute, fetchone, commit, rollback.

65.1.1 Inserir e consultar

dados = [
    ("onu-00043", -29.8, "2026-08-12T03:14:22"),
    ("onu-00045", -31.7, "2026-08-12T03:14:23"),
    ("onu-00052", None,  "2026-08-12T03:14:51"),
    ("onu-00043", -29.9, "2026-08-12T04:14:22"),
]
con.executemany(
    "INSERT INTO leitura (onu, potencia, quando) VALUES (?, ?, ?)", dados)
con.commit()

for linha in con.execute("SELECT onu, potencia FROM leitura WHERE potencia < -30"):
    print(linha)
('onu-00045', -31.7)

execute devolve um cursor, e o cursor é iterável — o que traz as linhas sob demanda, sem carregar o resultado inteiro. fetchone() traz uma, fetchall() traz todas e fetchmany(n) traz um lote. Para um SELECT que pode devolver um milhão de linhas, iterar é a única forma que não estoura a memória.

As linhas chegam como tuplas, o que é rápido e ilegível. sqlite3.Row resolve:

con.row_factory = sqlite3.Row
linha = con.execute("SELECT * FROM leitura LIMIT 1").fetchone()
por indice: onu-00043
por nome  : onu-00043 -29.8
colunas   : ['id', 'onu', 'potencia', 'quando']
como dict : {'id': 1, 'onu': 'onu-00043', 'potencia': -29.8, 'quando': '2026-08-12T03:14:22'}

Acesso por nome e por índice, com keys() e conversão direta para dicionário. É uma linha de configuração, e deveria ser a primeira coisa depois de todo connect.

65.2 Injeção de SQL: o ? não é opcional

Esta é a parte do capítulo que importa mais que todas as outras juntas.

A forma intuitiva de filtrar por um valor que veio de fora é montar a consulta com f-string. Funciona:

# ERRADO — nunca monte SQL com interpolação de texto
sql = f"SELECT count(*) FROM leitura WHERE onu = '{alvo}'"
consulta montada: SELECT count(*) FROM leitura WHERE onu = 'onu-00043'
resultado       : 2

Duas leituras da onu-00043, correto. Agora o mesmo código com um valor diferente:

entrada_hostil = "x' OR '1'='1"
consulta montada: SELECT count(*) FROM leitura WHERE onu = 'x' OR '1'='1'
resultado       : 4 <- devolveu TUDO

O texto fechou a aspa, acrescentou um OR sempre verdadeiro e deixou a aspa final casando com a que o programa ia pôr. O filtro deixou de existir. Com SELECT count(*) o dano é vazamento; com DELETE ou UPDATE na mesma consulta, é destruição — e a mesma técnica lê a tabela de usuários de um sistema inteiro.

A correção é passar o valor separado da consulta:

con.execute("SELECT count(*) FROM leitura WHERE onu = ?", (entrada_hostil,))
resultado       : 0 <- correto: nenhuma

Zero, que é a resposta certa: nenhuma ONU se chama x' OR '1'='1. O ? não é uma “interpolação mais segura” — é uma coisa diferente. A consulta vai ao motor primeiro, é analisada e vira um plano de execução; só então o valor é ligado a um espaço reservado. Não existe caminho pelo qual o valor vire estrutura, porque a estrutura já foi decidida.

Parâmetros também têm forma nomeada, que é melhor quando são muitos:

con.execute(
    "SELECT onu, potencia FROM leitura WHERE potencia < :limite AND onu LIKE :p",
    {"limite": -29.85, "p": "onu-000%"})
[('onu-00045', -31.7), ('onu-00043', -29.9)]

E têm um limite que é importante conhecer:

OperationalError: near "?": syntax error

Parâmetro substitui valor, não identificador. Nome de tabela, nome de coluna e direção de ordenação são estrutura, e não podem vir do usuário por ?. Quando precisam ser dinâmicos, a única forma segura é validar contra uma lista fechada de nomes permitidos no seu código — nunca interpolar o que chegou.

65.3 Tipos, e a tipagem que não é bem tipagem

  1            int
  1.5          float
  'texto'      str
  b'\x00\xff'  bytes

O SQLite tem cinco tipos de armazenamento — NULL, INTEGER, REAL, TEXT e BLOB — e o módulo os mapeia para None, int, float, str e bytes. Não há date, datetime, Decimal nem booleano: datas se guardam como texto ISO-8601 (que ordena corretamente como string) ou como número, e booleanos como 0 e 1.

Agora a surpresa:

con.execute("CREATE TABLE tipos (n INTEGER)")
con.execute("INSERT INTO tipos VALUES (?)", ("isto nao e um numero",))
guardado numa coluna INTEGER: 'isto nao e um numero'

O SQLite tem tipagem dinâmica: o tipo declarado da coluna é uma sugestão de afinidade, não uma restrição. Texto numa coluna INTEGER entra sem reclamar. Quem vem de PostgreSQL leva um susto justificado aqui.

Desde o SQLite 3.37 existe a saída:

con.execute("CREATE TABLE estrito (n INTEGER NOT NULL) STRICT")
con.execute("INSERT INTO estrito VALUES (?)", ("texto",))
IntegrityError: cannot store TEXT value in INTEGER column estrito.n

STRICT no fim do CREATE TABLE faz os tipos valerem. Em tabela nova, use sempre.

65.3.1 Restrições são validação que não se pode contornar

IntegrityError: UNIQUE constraint failed: leitura.onu, leitura.quando

O UNIQUE (onu, quando) da definição impediu a leitura duplicada. Essa é uma diferença de fundo em relação a todos os formatos dos capítulos anteriores: NOT NULL, UNIQUE, CHECK, PRIMARY KEY e FOREIGN KEY são regras que o dado carrega, verificadas em toda escrita, por qualquer programa que use o arquivo. Validação em Python protege o caminho que passa pelo seu código; restrição no banco protege o arquivo.

Uma pegadinha vale registro: chave estrangeira não é verificada por padrão no SQLite, por compatibilidade histórica. É preciso PRAGMA foreign_keys = ON em cada conexão.

65.4 Transações: with con, e o commit esquecido

try:
    with con:
        con.execute("INSERT INTO leitura (onu, quando) VALUES (?, ?)",
                    ("onu-99999", "2026-08-12T05:00:00"))
        raise RuntimeError("falha no meio do lote")
except RuntimeError as e:
    print("erro:", e)
erro: falha no meio do lote
a linha entrou? 0

with con: não fecha a conexão — ele delimita uma transação: commit na saída normal, rollback se escapar exceção. É a forma correta de escrever qualquer operação que precise ser tudo-ou-nada, e o motivo pelo qual um lote interrompido não deixa metade dos dados gravados.

O contrário disso é o defeito silencioso mais comum do módulo:

con = sqlite3.connect("esquecido.db")
con.execute("CREATE TABLE t (x)")
con.execute("INSERT INTO t VALUES (1)")
con.close()          # sem commit
linhas apos close sem commit: 0

O INSERT foi executado, não deu erro nenhum, e o dado não existe. close() não faz commit — descarta a transação aberta. Programa que grava e não encontra o que gravou tem, quase sempre, exatamente esta causa.

65.4.1 Por que um commit por linha é catastrófico

executemany + 1 commit :   0.015 s
commit por linha       :  91.282 s
6077x mais lento

Vinte mil linhas. Quinze milissegundos contra um minuto e meio.

A razão é física. Cada commit precisa garantir que o dado sobreviva a uma queda de energia, e para isso pede ao sistema operacional que force a escrita ao disco de verdade. Uma transação custa quase o mesmo tenha ela uma linha ou vinte mil — o custo está na garantia, não no volume. Vinte mil commits são vinte mil esperas pelo disco.

executemany com um commit no fim é a forma certa. E commit dentro de laço é um dos erros de desempenho mais caros e mais fáceis de cometer em Python.

65.5 Índices, e como saber se o banco está usando um

200 buscas sem indice:   2.627 s
200 buscas com indice:   0.009 s
289x mais rapido

Duzentas mil linhas, duzentas buscas. Sem índice, o motor lê a tabela inteira a cada busca; com índice, vai direto. A diferença é de quase 300 vezes, e cresce com o tamanho da tabela.

Não é preciso adivinhar se o índice está sendo usado:

EXPLAIN QUERY PLAN SELECT potencia FROM t WHERE onu = ?
sem indice:  SCAN t
com indice:  SEARCH t USING INDEX idx_onu (onu=?)

SCAN é a tabela inteira. SEARCH ... USING INDEX é a busca dirigida. Toda consulta lenta começa por essa linha, e ela responde a maior parte das perguntas sozinha.

Índice não é grátis: ocupa espaço e torna a escrita mais lenta, porque precisa ser mantido. A regra é indexar as colunas que aparecem em WHERE, JOIN e ORDER BY das consultas que realmente se faz — não todas, por precaução.

65.6 O que se ganha de verdade

A pergunta da abertura, agora:

SELECT onu, count(*) AS n, round(avg(potencia), 2) AS media
FROM leitura
WHERE potencia IS NOT NULL
GROUP BY onu
ORDER BY media
  ('onu-00045', 1, -31.7)
  ('onu-00043', 2, -29.85)

Filtro, agrupamento, agregação e ordenação em cinco linhas — e o trabalho acontece em C, sobre dados que nunca precisaram caber na memória. Reescrever isso em Python sobre um .jsonl custa trinta linhas e é ordens de grandeza mais lento a partir de um certo tamanho.

Dois recursos que costumam surpreender: o SQLite lê JSON com json_extract, o que permite guardar um campo semiestruturado numa coluna TEXT e ainda consultá-lo; e :memory: cria um banco que existe só na RAM, ideal para teste automatizado e para processamento intermediário.

soma em memoria: 499500

65.7 Quando SQLite, e quando não

Ele é a resposta certa em muito mais casos do que a fama sugere: aplicação de um processo, ferramenta de linha de comando, aplicativo de desktop ou celular, cache local, formato de arquivo de aplicação, análise de dados de até dezenas de gigabytes, e teste automatizado de código que fala com banco.

O limite é a escrita concorrente. O SQLite permite muitos leitores simultâneos, mas apenas um escritor por vez, com um bloqueio no nível do arquivo — o OperationalError: database is locked aparece quando dois processos tentam escrever ao mesmo tempo. O modo WAL (PRAGMA journal_mode = WAL) melhora bastante, permitindo leitura durante escrita, mas não muda o essencial.

Quando há vários processos escrevendo com frequência, quando o banco precisa ficar num servidor separado dos clientes, ou quando são necessários controle de acesso por usuário e replicação, a resposta é PostgreSQL. A boa notícia é que a DB-API é a mesma, e o SQL muda pouco — o Volume 14 trata dessa transição com SQLAlchemy.

E há o meio-termo que vale conhecer: sqlite3 na biblioteca padrão é a interface crua. Para uma aplicação com muitas tabelas e relacionamentos, um mapeador objeto-relacional evita escrever SQL à mão para tudo — sem que isso dispense entender o que ele gera.

65.8 🐍 Jeito Pythônico

Parâmetro ? ou :nome, sempre. Nenhum valor de fora entra na consulta por f-string, % ou +.

# antipadrão: injeção de SQL
con.execute(f"SELECT * FROM leitura WHERE onu = '{onu}'")
# pythônico
con.execute("SELECT * FROM leitura WHERE onu = ?", (onu,))

Repare na vírgula em (onu,): sem ela não é uma tupla, e o erro é Incorrect number of bindings.

with con: em volta de cada unidade de trabalho. Delimita transação, não fecha conexão.

Um commit por lote, nunca por linha. A diferença medida foi de 6.077 vezes.

con.row_factory = sqlite3.Row logo depois de conectar.

STRICT em toda tabela nova, e PRAGMA foreign_keys = ON em toda conexão.

Itere o cursor em vez de fetchall() quando o resultado puder ser grande.

Deixe o banco agregar. GROUP BY e count() no SQL, não laço em Python.

EXPLAIN QUERY PLAN antes de otimizar. SCAN numa tabela grande é a resposta.

Datas em ISO-8601 (2026-08-12T03:14:22), que ordenam corretamente como texto.

:memory: nos testes, para cada teste começar com um banco limpo.

Sobre versões:

  • Python 3.11 — PRAGMA de otimização e melhorias de desempenho no módulo.
  • Python 3.12 — parâmetro autocommit na conexão, que finalmente permite controle explícito do modo de transação; e sqlite3 ganhou uma interface de linha de comando (python -m sqlite3).
  • Python 3.12 — os conversores implícitos de datetime (detect_types) foram depreciados: converta você mesmo, explicitamente.
  • Python 3.14 — sqlite3.version (a versão do módulo, que nunca serviu para nada) foi removido; sqlite3.sqlite_version é o que interessa.
  • SQLite 3.37 — tabelas STRICT, disponíveis conforme a biblioteca embutida no seu Python.

65.9 🧪 Laboratório

Objetivo: construir a tabela de leituras, provocar uma injeção de SQL controlada, e medir o custo de um commit mal colocado.

1. Preparo.

mkdir -p ~/lab65 && cd ~/lab65
python3 -m venv .venv && source .venv/bin/activate

2. Criação. Crie coletor.db com a tabela leitura, incluindo NOT NULL e UNIQUE (onu, quando). Confirme o tamanho do arquivo recém-criado.

3. Inserção. Use executemany com as quatro leituras e um commit. Confirme a contagem.

4. Consulta e cursor. Itere o cursor e compare com fetchall(). Depois configure row_factory = sqlite3.Row e acesse por nome, por índice e via dict().

5. A injeção. Monte a consulta com f-string e rode com "onu-00043". Depois rode com "x' OR '1'='1" e confirme:

consulta montada: SELECT count(*) FROM leitura WHERE onu = 'x' OR '1'='1'
resultado       : 4 <- devolveu TUDO

Refaça com ? e confirme o 0. Escreva em uma frase por que o parâmetro não é “uma interpolação mais segura”.

6. O limite do parâmetro. Tente con.execute("SELECT * FROM ?", ("leitura",)) e confirme o OperationalError. Escreva como você permitiria ordenar por uma coluna escolhida pelo usuário sem interpolar a escolha dele.

7. Tipagem dinâmica. Insira texto numa coluna INTEGER e confirme que entra. Recrie a tabela com STRICT e confirme:

IntegrityError: cannot store TEXT value in INTEGER column estrito.n

8. Restrições. Insira a mesma (onu, quando) duas vezes e observe o IntegrityError. Depois crie uma segunda tabela com FOREIGN KEY, insira uma referência inexistente e confirme que passa. Ligue PRAGMA foreign_keys = ON e confirme que passa a falhar.

9. Transação. Rode um with con: que levanta exceção no meio e confirme que nada foi gravado.

10. O commit esquecido. Insira, feche sem commit, reabra e confirme as zero linhas. Este é o passo que explica metade das dúvidas sobre o módulo.

11. A medida. Insira 20 mil linhas das duas formas e compare:

executemany + 1 commit :   0.015 s
commit por linha       :  91.282 s

Explique de onde vem a diferença. (Seja paciente com a segunda medição.)

12. Índice e plano. Com 200 mil linhas, meça 200 buscas antes e depois de CREATE INDEX. Rode EXPLAIN QUERY PLAN nas duas situações:

sem indice:  SCAN t
com indice:  SEARCH t USING INDEX idx_onu (onu=?)

Meça também o tamanho do arquivo antes e depois de criar o índice.

13. Agregação. Escreva a consulta com GROUP BY, count, avg e ORDER BY. Depois escreva o equivalente em Python puro sobre a mesma origem e compare o número de linhas de código.

14. Concorrência. Abra duas conexões, comece uma escrita numa e tente escrever pela outra. Provoque o database is locked. Ligue PRAGMA journal_mode = WAL e repita com um leitor no lugar do segundo escritor.

15. Migração do .jsonl. Carregue um arquivo JSON Lines do Capítulo 62 para dentro da tabela e responda à pergunta da abertura do capítulo com uma consulta só.

65.10 Resumo

  • Formato de arquivo obriga a carregar tudo para procurar; banco de dados deixa o dado no disco e leva a pergunta até ele.
  • sqlite3.connect abre um arquivo e roda a biblioteca dentro do processo: sem servidor, sem porta, sem usuário.
  • O módulo implementa a DB-API 2.0 (PEP 249), então connect, cursor, execute, fetchone e commit valem também para PostgreSQL e MySQL.
  • O cursor é iterável e traz linhas sob demanda; fetchall() carrega tudo na memória.
  • con.row_factory = sqlite3.Row dá acesso por nome, keys() e conversão para dicionário, ao custo de uma linha.
  • Montar SQL com f-string permite que o texto do usuário vire estrutura da consulta: x' OR '1'='1 apagou o filtro e devolveu a tabela inteira.
  • O parâmetro ? é outro mecanismo, não uma interpolação mais cuidadosa: a consulta é analisada antes, e o valor é ligado a um espaço reservado depois.
  • Parâmetro substitui valor, nunca identificador; nome de tabela ou coluna dinâmico exige lista fechada de nomes permitidos no código.
  • O SQLite tem cinco tipos de armazenamento e nenhum de data; ISO-8601 em TEXT ordena corretamente.
  • A tipagem é dinâmica — texto entra em coluna INTEGER sem erro — e STRICT no CREATE TABLE é o que faz o tipo valer.
  • NOT NULL, UNIQUE e CHECK protegem o arquivo contra qualquer programa; validação em Python protege só o caminho que passa pelo seu código.
  • Chave estrangeira não é verificada sem PRAGMA foreign_keys = ON.
  • with con: delimita transação (não fecha conexão): commit na saída normal, rollback na exceção.
  • close() sem commit descarta a transação em silêncio, e é a causa mais comum de “gravei e sumiu”.
  • Um commit por linha foi 6.077 vezes mais lento que um por lote, porque o custo está na garantia de durabilidade, não no volume.
  • Índice deu 289 vezes em 200 mil linhas; EXPLAIN QUERY PLAN mostra SCAN contra SEARCH ... USING INDEX e responde à maioria das perguntas de lentidão.
  • O limite do SQLite é escrita concorrente — um escritor por vez; WAL melhora, PostgreSQL resolve.
