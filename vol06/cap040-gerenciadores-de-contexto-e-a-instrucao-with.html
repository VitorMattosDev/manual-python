40  Gerenciadores de contexto e a instrução with

O coletor rodava a cada cinco minutos e abria um arquivo por ONU. Depois de algumas horas, começou isto:

limite de descritores do processo: 10240
quebrou depois de 10237 arquivos abertos
  OSError: [Errno 24] Too many open files: '/dev/null'

Nenhum arquivo era grande. Nenhum estava corrompido. O problema era que ninguém fechava nada, e todo processo tem um teto de descritores abertos — dez mil e duzentos e quarenta nesta máquina. Ao bater no teto, toda abertura passa a falhar: o log, a configuração, a conexão de rede. O programa morre num lugar que não tem nada a ver com o vazamento.

Este capítulo fecha o Volume 6 com a instrução que resolve essa classe inteira de problema — e que, uma vez entendida por dentro, você passa a escrever para os seus próprios recursos.

40.1 O que o with garante

with open("leituras.csv", encoding="utf-8") as f:
    conteudo = f.read()

A promessa é simples: o arquivo é fechado ao sair do bloco, de qualquer maneira que se saia dele — no fim natural, num return, num break, numa exceção. É o try/finally do Capítulo 38, empacotado num objeto e reutilizável.

Sem ele, a versão honesta do mesmo código é:

f = open("leituras.csv", encoding="utf-8")
try:
    conteudo = f.read()
finally:
    f.close()

Cinco linhas em vez de duas, e é preciso lembrar delas toda vez.

40.2 O protocolo

Qualquer objeto com dois métodos serve de gerenciador de contexto:

class Cronometro:
    def __enter__(self):
        print("  __enter__  chamado")
        return "o que o as recebe"

    def __exit__(self, exc_type, exc_valor, tb):
        print(f"  __exit__   chamado com {exc_type}")
        return False
sem excecao:
  __enter__  chamado
  dentro do bloco, x = 'o que o as recebe'
  __exit__   chamado com None

com excecao:
  __enter__  chamado
  __exit__   chamado com <class 'ValueError'>
  a excecao saiu do with: algo deu errado

Traduzido para o que o interpretador de fato faz, o with é isto:

gerente = Recurso()
recurso = type(gerente).__enter__(gerente)
try:
    ...                                     # o corpo do bloco
except BaseException:
    if not type(gerente).__exit__(gerente, *sys.exc_info()):
        raise
else:
    type(gerente).__exit__(gerente, None, None, None)
com with:
  abre
  usa
  fecha
na mao:
  abre
  usa
  fecha

Dois detalhes que a expansão revela. Os métodos são procurados no tipo, não na instância — atribuir obj.__enter__ = f não funciona, como acontece com todos os métodos especiais. E o except é BaseException, não Exception: a limpeza acontece até no Ctrl-C.

40.2.1 O __exit__ que engole

class Engole:
    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc_valor, tb):
        print(f"  engolindo {exc_type.__name__}: {exc_valor}")
        return True
  engolindo ValueError: essa nao vai sair
o programa continuou

Suprimir por padrão é quase sempre errado — é o except: cru do Capítulo 38 escondido dentro de um objeto. A versão útil é seletiva:

class Filtra:
    def __init__(self, *tipos):
        self.tipos = tipos

    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc_valor, tb):
        return exc_type is not None and issubclass(exc_type, self.tipos)
FileNotFoundError foi suprimido
Traceback (most recent call last):
  File "/home/vitor/lab40/engolir.py", line 31, in <module>
    raise ValueError("essa passa")
ValueError: essa passa

Você acabou de reescrever contextlib.suppress, que existe pronto e é o que se usa na prática.

40.3 Um gerenciador que serve para alguma coisa

Cronometrar um trecho é o exemplo canônico, e mostra por que o finally embutido importa:

import time


class Cronometro:
    def __init__(self, rotulo):
        self.rotulo = rotulo

    def __enter__(self):
        self.inicio = time.perf_counter()
        return self

    def __exit__(self, *exc):
        self.decorrido = time.perf_counter() - self.inicio
        print(f"{self.rotulo}: {self.decorrido * 1000:.1f} ms")
        return False
somar um milhao: 7.1 ms
e o objeto guarda o valor: 0.0071 s
com falha no meio: 3.4 ms
mesmo com erro, o tempo saiu: a coleta caiu

O tempo saiu mesmo quando o bloco levantou — que é exatamente o que se quer de um cronômetro, e o que uma dupla de perf_counter() solta jamais garante. E __enter__ devolveu self, então o objeto continua acessível depois do bloco, com o resultado guardado.

40.4 @contextmanager: o atalho

Escrever uma classe para cada gerenciador é cerimônia demais na maioria dos casos. O contextlib oferece um decorador que transforma um gerador em gerenciador:

from contextlib import contextmanager


@contextmanager
def cronometro(rotulo):
    inicio = time.perf_counter()
    try:
        yield rotulo
    finally:
        print(f"{rotulo}: {(time.perf_counter() - inicio) * 1000:.1f} ms")
somar um milhao: 6.9 ms
o yield entregou: 'somar um milhao'

O try/finally dentro do gerador não é enfeite. Sem ele:

@contextmanager
def ruim():
    print("  abre")
    yield
    print("  fecha")          # não roda se o bloco levantar
  abre
  <- repare que 'fecha' nao apareceu

A exceção do bloco é relançada dentro do gerador, no ponto do yield, e a linha seguinte nunca executa. Todo @contextmanager que libera recurso precisa de try/finally.

Um exemplo com valor prático real, o padrão de transação:

@contextmanager
def transacao(conexao):
    try:
        yield conexao
    except Exception:
        conexao.rollback()
        raise
    else:
        conexao.commit()
  commit
  rollback
linhas na tabela: 1
quais           : [('onu-00042', -21.4)]

Duas inserções, uma com falha no meio: só a primeira sobreviveu. O raise depois do rollback é essencial — sem ele, o gerenciador desfaz a transação e engole o erro, e quem chamou acha que deu tudo certo.

40.5 Vários de uma vez

with (
    open("a.txt", "w", encoding="utf-8") as a,
    open("b.txt", "w", encoding="utf-8") as b,
):
    a.write("conteudo A\n")
    b.write("conteudo B\n")

Os parênteses em volta da lista são do Python 3.10 (PEP 617), e resolvem o velho problema de quebrar um with longo em várias linhas sem barra invertida. A forma sem parênteses, with A() as a, B() as b:, funciona desde sempre.

A ordem de desmontagem é a inversa da de montagem:

  abre  primeiro
  abre  segundo
  abre  terceiro
  corpo
  fecha terceiro
  fecha segundo
  fecha primeiro

Isso importa quando os recursos dependem uns dos outros: a conexão abre antes do cursor e fecha depois dele, e o with garante essa ordem sem que você pense nela.

40.6 A caixa de ferramentas do contextlib

from contextlib import chdir, redirect_stdout, suppress

with suppress(FileNotFoundError):
    Path("nao-existe.csv").unlink()

buffer = io.StringIO()
with redirect_stdout(buffer):
    print("isto nao vai para o terminal")

with chdir("/tmp"):
    print(Path.cwd())
-- suppress
   nao existia, e ninguem reclamou
-- redirect_stdout
   capturei: 'isto nao vai para o terminal\nnem isto\n'
-- chdir (3.11+)
   antes : lab40
   dentro: /tmp
   depois: lab40

Os quatro que valem conhecer:

ferramenta para quê
suppress(*excs) ignorar exceções específicas sem try/except/pass
redirect_stdout(f) / redirect_stderr(f) capturar a saída de código que só sabe imprimir
closing(obj) dar with a objeto que tem close() mas não tem o protocolo
nullcontext(x) um gerenciador que não faz nada, para uniformizar o código
chdir(p) trocar o diretório atual e voltar (3.11+)

Uma armadilha do suppress que merece um exemplo:

with suppress(FileNotFoundError):
    Path("a").unlink()
    Path("b").unlink()
    print("nao chega aqui se a primeira falhar")
o suppress aborta o bloco inteiro, nao so a linha

Ele suprime a exceção e abandona o resto do bloco — como qualquer try/except. Um suppress com cinco linhas dentro é quase sempre um bug esperando: uma linha por with.

O nullcontext resolve o caso em que às vezes há recurso a gerenciar e às vezes não:

def escrever(linhas, destino=None):
    gerente = open(destino, "w", encoding="utf-8") if destino else nullcontext(sys.stdout)
    with gerente as saida:
        for linha in linhas:
            print(linha, file=saida)
onu-00042 -21.4
onu-00043 -29.8
no arquivo: onu-00042 -21.4
stdout continua aberto? True

Sem ele, seria preciso duplicar o laço ou escrever um if em volta de cada with. E o sys.stdout não é fechado no fim — que é o ponto: nullcontext devolve o objeto e não faz nada na saída.

40.7 ExitStack: quando o número é desconhecido

O with com lista fixa resolve dois ou três recursos escritos à mão. Quando a quantidade só é conhecida em tempo de execução, a ferramenta é o ExitStack:

from contextlib import ExitStack

with ExitStack() as pilha:
    handles = [pilha.enter_context(open(n, encoding="utf-8")) for n in ARQUIVOS]
    print(f"{len(handles)} arquivos abertos ao mesmo tempo")
3 arquivos abertos ao mesmo tempo
   coleta-01.csv -> onu-00001,-21.4
   coleta-02.csv -> onu-00002,-22.4
   coleta-03.csv -> onu-00003,-23.4
todos fechados? True

Cada enter_context registra o gerenciador na pilha; ao sair do with, todos são desmontados na ordem inversa, mesmo que um deles levante no meio. É a resposta certa para “abrir todos os CSV de um diretório”, em que o número depende do glob do Capítulo 37.

O ExitStack também faz desfazimento condicional, que é o padrão de transação generalizado:

def publicar(destinos, falhar=False):
    with ExitStack() as pilha:
        publicados = []
        for d in destinos:
            publicar_em(d)
            publicados.append(d)
            pilha.callback(desfazer, d)
        if falhar:
            raise RuntimeError("o terceiro destino recusou")
        pilha.pop_all()          # deu tudo certo: cancela o desfazer
        return publicados
sucesso:
  publica em norte
  publica em central
  -> ['norte', 'central']
falha:
  publica em norte
  publica em central
  desfaz central
  desfaz norte
  -> o terceiro destino recusou

callback registra uma função qualquer para rodar na saída; pop_all() transfere tudo para uma pilha nova que ninguém desmonta — em outras palavras, cancela a limpeza quando a operação inteira deu certo. Publicar em três lugares e desfazer os dois primeiros se o terceiro falhar é exatamente o problema que isso resolve.

40.8 Duas armadilhas

Um @contextmanager só serve uma vez. O gerador se esgota:

g = uma_vez("reutilizado")
with g:
    print("  primeiro uso")
with g:
    print("  segundo uso")
  entra reutilizado
  primeiro uso
  sai   reutilizado
Traceback (most recent call last):
  File "/home/vitor/lab40/reentra.py", line 17, in <module>
    with g:
         ^
AttributeError: '_GeneratorContextManager' object has no attribute 'args'

O que se reutiliza é a função, chamando-a de novo: with uma_vez("x"): cada vez. Um gerenciador escrito como classe pode ser reutilizável, se você o escrever assim — mas então precisa cuidar do estado entre os usos.

O with não cria escopo. Ao contrário do que a indentação sugere:

with open("a.txt", encoding="utf-8") as f:
    conteudo = f.read()
print("conteudo sobrevive :", repr(conteudo))
print("f tambem sobrevive :", f)
print("mas esta fechado   :", f.closed)
f.read()
conteudo sobrevive : 'conteudo A\n'
f tambem sobrevive : <_io.TextIOWrapper name='a.txt' mode='r' encoding='utf-8'>
mas esta fechado   : True
ValueError: I/O operation on closed file.

Só def e class criam escopo em Python (Capítulo 20). O f continua existindo depois do bloco — apenas fechado. Isso é útil (o c.decorrido do cronômetro depende disso) e é armadilha quando alguém tenta usar o arquivo depois.

40.9 async with, de passagem

O protocolo tem uma versão assíncrona, com __aenter__ e __aexit__, e o decorador correspondente:

from contextlib import asynccontextmanager


@asynccontextmanager
async def coleta(olt):
    print(f"  conecta {olt}")
    try:
        yield olt
    finally:
        print(f"  desconecta {olt}")


async def main():
    async with coleta("olt-borda-01") as c:
        print(f"  coletando de {c}")
  conecta olt-borda-01
  coletando de olt-borda-01
  desconecta olt-borda-01

A forma é idêntica; o que muda é que a montagem e a desmontagem podem ceder o controle ao laço de eventos. Conexão de banco, sessão HTTP e cliente de rede assíncrono são todos gerenciadores desse tipo. O mecanismo é assunto do Volume 15.

40.10 🐍 Jeito Pythônico

Todo recurso vai dentro de um with. Arquivo, socket, trava, conexão, sessão, diretório temporário.

# antipadrão
f = open("leituras.csv", encoding="utf-8")
dados = f.read()
f.close()          # não roda se o read levantar — e ninguém percebe até o Errno 24
# pythônico
with open("leituras.csv", encoding="utf-8") as f:
    dados = f.read()

@contextmanager para o caso simples; classe quando há estado a expor. O decorador vence quando a limpeza cabe num finally; a classe vence quando o objeto precisa de atributos e métodos.

try/finally obrigatório dentro do @contextmanager. Sem ele, o código depois do yield não roda quando o bloco levanta.

__exit__ devolve falso, a não ser que suprimir seja o propósito declarado do gerenciador. Esquecer o return devolve None, que é falso — e é o comportamento certo.

contextlib.suppress em vez de try/except/pass, com uma linha dentro do bloco.

ExitStack quando o número de recursos é dinâmico; nullcontext quando às vezes não há recurso.

Parênteses para vários gerenciadores em linhas separadas (3.10+).

Não reutilize um @contextmanager: chame a função de novo.

Sobre versões:

  • Python 2.5 — a PEP 343 introduz with, __enter__ e __exit__.
  • Python 3.2 — contextlib.ContextDecorator permite usar o mesmo objeto como decorador de função.
  • Python 3.3 — ExitStack entra no contextlib.
  • Python 3.7 — nullcontext e asynccontextmanager; async with fica completo.
  • Python 3.10 — parênteses em with de vários gerenciadores (PEP 617).
  • Python 3.11 — contextlib.chdir.
  • Python 3.12 — @contextmanager fica mais rápido; a PEP 709 (compreensões embutidas) reduz o custo do laço que abre recursos.

40.11 🧪 Laboratório

Objetivo: esgotar os descritores de propósito, implementar o protocolo à mão, comparar a classe com o @contextmanager, usar ExitStack com número dinâmico de arquivos e escrever um gerenciador de transação com rollback.

1. O vazamento.

mkdir -p ~/lab40 && cd ~/lab40

vazamento.py:

import resource

limite = resource.getrlimit(resource.RLIMIT_NOFILE)[0]
print("limite de descritores do processo:", limite)

abertos = []
try:
    for i in range(limite + 10):
        abertos.append(open("/dev/null"))
except OSError as e:
    print(f"quebrou depois de {len(abertos)} arquivos abertos")
    print(f"  {type(e).__name__}: {e}")
finally:
    for f in abertos:
        f.close()

quebrou depois de 10237 arquivos abertos

O número exato varia com o sistema — ulimit -n mostra o seu.

40.12 Resumo

  • O with garante a limpeza em qualquer saída do bloco — fim natural, return, break ou exceção. É try/finally empacotado num objeto reutilizável.
  • O protocolo são dois métodos: __enter__ devolve o que o as recebe; __exit__ recebe sempre três argumentos (classe, instância e traceback) ou três None.
  • __exit__ devolvendo verdadeiro suprime a exceção. Devolver None — o padrão de quem esquece o return — a deixa subir, que é o certo em quase todos os casos.
  • Os métodos são procurados no tipo, e a limpeza roda até para BaseException, o que inclui Ctrl-C.
  • @contextmanager transforma um gerador em gerenciador: antes do yield é a montagem, o finally é a desmontagem. Sem try/finally, a limpeza não roda quando o bloco levanta.
  • A exceção do bloco é relançada dentro do gerador, no ponto do yield — por isso um except ali captura o erro do corpo do with.
  • Vários gerenciadores no mesmo with são desmontados na ordem inversa; os parênteses para quebrar em linhas são do Python 3.10.
  • contextlib traz suppress (uma linha por bloco), redirect_stdout, closing, nullcontext e chdir.
  • ExitStack gerencia um número dinâmico de recursos, e callback mais pop_all() implementam desfazimento condicional — o padrão de transação sem banco de dados.
  • Um @contextmanager serve uma vez só; e o with não cria escopo, então o nome do as sobrevive ao bloco, já fechado.

Com isso fecha o Volume 6. O programa saiu do próprio processo: lê e escreve texto e binário sem corromper, navega o sistema de arquivos sem concatenar strings, falha com mensagem que resolve e devolve os recursos que pegou emprestado. O que falta agora é organizar o que ele manipula — e é aí que entram as classes, os objetos e o modelo de dados de Python, que ocupam os dois volumes seguintes.
