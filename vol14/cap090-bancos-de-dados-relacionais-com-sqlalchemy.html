90  Bancos de dados relacionais com SQLAlchemy

O sqlite3 da biblioteca padrão (Capítulo 65) resolve muita coisa, e resolve bem enquanto o programa é pequeno. Aí o SQL começa a virar f-string, cada consulta repete o mesmo JOIN, alguém troca o SQLite por PostgreSQL e descobre que ? virou %s em cento e vinte lugares, e o row[3] de uma função não é o mesmo row[3] de outra porque a ordem das colunas mudou.

SQLAlchemy é a resposta madura para isso no Python. Ele tem duas camadas: um Core, que constrói SQL como expressões Python e abstrai o dialeto do banco, e um ORM, que mapeia classes para tabelas e acompanha o estado dos objetos. Dá para usar só o Core, e muita gente séria usa.

Este capítulo usa SQLAlchemy 2.0.52 com Alembic 1.19.1. A versão 2.0 mudou o estilo de consulta o suficiente para que exemplos antigos (session.query(...)) ainda funcionem mas não sejam mais o caminho recomendado — o estilo novo é select().

pip install sqlalchemy alembic
pip install aiosqlite          # para a parte assincrona

90.1 Duas camadas, um pacote

90.2 O modelo declarativo

Em 2.0, o mapeamento usa anotações de tipo de verdade (Capítulo 68) — o mesmo Mapped[int] que o verificador de tipos entende:

from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship

class Base(DeclarativeBase):
    pass

class Autor(Base):
    __tablename__ = "autor"

    id: Mapped[int] = mapped_column(primary_key=True)
    nome: Mapped[str] = mapped_column(String(80))
    livros: Mapped[list["Livro"]] = relationship(back_populates="autor",
                                                 cascade="all, delete-orphan")

class Livro(Base):
    __tablename__ = "livro"

    id: Mapped[int] = mapped_column(primary_key=True)
    isbn: Mapped[str] = mapped_column(String(13), unique=True)
    titulo: Mapped[str] = mapped_column(String(120))
    preco: Mapped[Decimal] = mapped_column(sa.Numeric(9, 2))
    autor_id: Mapped[int] = mapped_column(ForeignKey("autor.id"))
    autor: Mapped[Autor] = relationship(back_populates="livros")

A anotação carrega informação real: Mapped[str] significa NOT NULL, e Mapped[str | None] significa nulo permitido. O DDL sai daí:

CREATE TABLE livro (
    id INTEGER NOT NULL,
    isbn VARCHAR(13) NOT NULL,
    titulo VARCHAR(120) NOT NULL,
    preco NUMERIC(9, 2) NOT NULL,
    autor_id INTEGER NOT NULL,
    PRIMARY KEY (id),
    UNIQUE (isbn),
    FOREIGN KEY(autor_id) REFERENCES autor (id)
)

Duas escolhas do exemplo que merecem nota:

Numeric(9, 2) para dinheiro, nunca Float. É a mesma razão do Capítulo 10: 0.1 + 0.2 não é 0.3, e num sistema financeiro isso vira diferença de centavos que ninguém consegue explicar. O SQLAlchemy devolve Decimal do outro lado. (O SQLite não tem tipo decimal nativo; o SQLAlchemy converte, e a precisão declarada é o que mantém a saída limpa.)

back_populates nos dois lados. Ele mantém as duas pontas do relacionamento sincronizadas em memória: acrescentar um livro a autor.livros também define livro.autor, sem ida ao banco.

90.3 Consultar: select() é a interface

q = select(Livro).where(Livro.preco > 150).order_by(Livro.titulo)
for livro in s.scalars(q):
    print(livro, livro.preco)
  SQL: SELECT livro.id, livro.isbn, livro.titulo, livro.preco, livro.autor_id
       FROM livro WHERE livro.preco > :preco_1 ORDER BY livro.titulo
    Livro(id=3, titulo='Effective Python') 159.00
    Livro(id=1, titulo='Fluent Python') 189.00

Repare no :preco_1. O valor nunca entra no texto do SQL — ele vai parametrizado, o que elimina injeção de SQL por construção. É o argumento de segurança mais forte a favor de qualquer construtor de consultas sobre f-string.

O mesmo select() faz agregação e junção:

s.scalar(select(func.sum(Livro.preco)))

s.execute(
    select(Autor.nome, func.count(Livro.id), func.sum(Livro.preco))
    .join(Livro)
    .group_by(Autor.nome)
    .order_by(func.count(Livro.id).desc())
).all()
  soma dos precos: 497.00 Decimal
  agregado por autor: [('Luciano Ramalho', 2, Decimal('338.00')), ('Brett Slatkin', 1, Decimal('159.00'))]

A distinção entre os dois métodos de execução vale decorar:

  • s.scalars(q) devolve a primeira coluna de cada linha — use quando a consulta seleciona entidades (select(Livro)), e você recebe objetos Livro.
  • s.execute(q) devolve linhas (tuplas nomeadas) — use quando a consulta seleciona colunas (select(Autor.nome, func.count(...))).
  • s.scalar(q) devolve um único valor — para count, sum e afins.

Trocar um pelo outro produz o erro mais comum de quem migra do estilo 1.x: uma lista de tuplas de um elemento onde se esperava uma lista de objetos.

90.4 O N+1, de novo — e o SQLAlchemy tem mais respostas

Com vinte autores, cada um com seus livros:

for autor in s.scalars(select(Autor)):
    _ = [livro.titulo for livro in autor.livros]        # lazy, o padrao

for autor in s.scalars(select(Autor).options(selectinload(Autor.livros))):
    _ = [livro.titulo for livro in autor.livros]        # uma consulta a mais, so

s.execute(select(Autor.nome, Livro.titulo).join(Livro)).all()   # sem ORM
  autores no banco: 20
  lazy (padrao)          : 21 consultas
  selectinload           : 2 consultas
  join direto (sem ORM)  : 1 consulta, 21 linhas

Vinte e uma consultas contra duas contra uma. O padrão do relacionamento é preguiçoso: autor.livros só vai ao banco quando alguém toca no atributo, e num laço isso vira uma consulta por iteração. É o mesmo defeito do Capítulo 89, com as mesmas consequências e uma escolha maior de curas:

estratégia como resolve quando usar
selectinload uma segunda consulta com IN (...) coleções (o caso comum)
joinedload LEFT JOIN numa consulta só um-para-um e muitos-para-um
subqueryload subconsulta correlacionada herdado; prefira selectinload
raiseload levanta erro se alguém carregar preguiçosamente para proibir o acidente
sem ORM select() de colunas com join() relatório, exportação, listagem grande

raiseload merece destaque: configurar o relacionamento com lazy="raise" faz qualquer carga preguiçosa acidental estourar uma exceção em desenvolvimento, em vez de virar 300 consultas em produção. É a forma mais confiável de manter o problema fora do sistema.

E a última linha da medição sugere algo que se esquece com facilidade: quando o resultado é um relatório, não um grafo de objetos, o ORM só atrapalha. Selecionar colunas devolve tuplas, gasta uma consulta e não constrói objeto nenhum.

90.5 A Session: unidade de trabalho e mapa de identidade

Esta é a parte do SQLAlchemy que mais confunde, e a que mais vale entender.

with Session(engine) as s:
    livro = s.scalar(select(Livro).where(Livro.isbn == "9781492056355"))
    print(livro.preco)              # 189.00
    livro.preco = Decimal("199.90") # nenhum UPDATE ainda
    print(livro in s.dirty)         # True
    s.flush()                       # agora sim o UPDATE foi ao banco
    print(livro in s.dirty)         # False
    s.rollback()                    # ...e desfeito
  antes  : 189.00
  sujo?   True
  apos flush, sujo? False
  depois do rollback: 189.00

Você não escreve UPDATE. Alterar um atributo marca o objeto como sujo; a sessão acumula as mudanças e as envia — na ordem correta em relação às chaves estrangeiras — quando você chama flush() (ou commit(), que faz flush e confirma).

90.5.1 O mapa de identidade

with Session(engine) as s:
    a = s.scalar(select(Livro).where(Livro.id == 1))
    b = s.get(Livro, 1)
    print(a is b)                 # True

with Session(engine) as s1, Session(engine) as s2:
    print(s1.get(Livro, 1) is s2.get(Livro, 1))   # False
  a is b ? True | mesma sessao, mesma identidade
  sessoes diferentes: False

Dentro de uma sessão, uma linha corresponde a exatamente um objeto Python. Duas consultas diferentes que trazem a mesma linha devolvem o mesmo objeto — não uma cópia. Isso é o que impede duas partes do código de terem versões divergentes do mesmo registro, e é o que torna possível a sessão saber o que mudou.

Em sessões diferentes, são objetos diferentes. Daí a regra: não compare objetos ORM com is através de sessões — compare pela chave primária.

90.5.2 O objeto solto

with Session(engine) as s:
    solto = s.scalar(select(Autor).where(Autor.id == 1))

print(solto.nome)        # funciona: ja estava carregado
print(solto.livros)      # estoura
  fora do with, atributo ja carregado: Luciano Ramalho
  atributo preguicoso -> DetachedInstanceError
    Parent instance <Autor at 0x2458e393e00> is not bound to a Session; lazy load operation of attri...

(O endereço do objeto muda a cada execução; o que importa é a classe da exceção.)

Esse erro é a consequência direta do modelo de carga preguiçosa: fora da sessão, não há conexão para ir buscar o que faltou. As saídas, em ordem de preferência:

  1. Carregue tudo que vai precisar dentro da sessão, com selectinload/joinedload.
  2. Converta para o que você realmente vai devolver ainda dentro da sessão — um modelo Pydantic (Capítulo 87), um dict, uma dataclass.
  3. expire_on_commit=False evita que o commit invalide os atributos já carregados — útil, mas não faz relacionamento não carregado aparecer.

A segunda é a melhor prática numa API: a camada web devolve ProdutoSaida, não Produto do ORM. Isso resolve o DetachedInstanceError e, de quebra, o vazamento de campos do Capítulo 88.

90.6 Sessão por pedido

A regra de ouro do uso do ORM numa aplicação web: uma sessão por pedido, aberta no começo e fechada no fim. Com FastAPI, isso é uma dependência com yield:

Sessao = async_sessionmaker(engine, expire_on_commit=False)

async def sessao():
    async with Sessao() as s:
        yield s

@app.get("/livros/{livro_id}")
async def obter(livro_id: int, s: Annotated[AsyncSession, Depends(sessao)]):
    livro = await s.get(Livro, livro_id)
    if livro is None:
        raise HTTPException(404, "livro nao encontrado")
    return {"id": livro.id, "titulo": livro.titulo, "preco": str(livro.preco)}
  GET /livros/1  -> 200 {'id': 1, 'titulo': 'Fluent Python', 'preco': '189.00'}
  GET /livros/99 -> 404 {'detail': 'livro nao encontrado'}

O que não fazer: uma sessão global no módulo. Ela não é segura entre threads, acumula objetos indefinidamente e faz um erro em um pedido contaminar o seguinte.

90.6.1 A versão assíncrona

engine = create_async_engine("sqlite+aiosqlite:///:memory:")

async with Sessao() as s:
    livros = (await s.scalars(select(Livro).order_by(Livro.titulo))).all()
    print(await s.scalar(select(func.sum(Livro.preco))))
  titulos : ['Effective Python', 'Fluent Python']
  soma    : 348.00

A API é a mesma, com await na execução. Duas ressalvas concretas:

O driver precisa ser assíncrono: asyncpg ou psycopg (v3) para PostgreSQL, aiosqlite para SQLite, aiomysql para MySQL. A URL muda (postgresql+asyncpg://), e usar um driver síncrono com create_async_engine falha na criação do engine.

Carga preguiçosa não funciona em async — não há como um acesso a atributo esperar por I/O. Ou você usa selectinload/joinedload, ou usa await s.refresh(obj, ["livros"]), ou toma um erro. Na prática, o modo assíncrono obriga a boa prática que o síncrono só recomenda.

90.7 Migrações com Alembic

O modelo mudou; o banco em produção não sabe disso. Alembic gera e aplica a diferença.

alembic init alembic
# em alembic.ini:  sqlalchemy.url = sqlite:///catalogo.db
# em alembic/env.py:  from modelos import Base;  target_metadata = Base.metadata
alembic revision --autogenerate -m "esquema inicial"
alembic upgrade head
INFO  [alembic.autogenerate.compare.tables] Detected added table 'autor'
INFO  [alembic.autogenerate.compare.tables] Detected added table 'livro'
INFO  [alembic.runtime.migration] Running upgrade  -> 94fcd6644a04, esquema inicial

Agora acrescente um campo ao modelo e peça a diferença:

class Livro(Base):
    ...
    paginas: Mapped[int | None] = mapped_column(nullable=True)
alembic revision --autogenerate -m "livro ganha paginas"
alembic upgrade head
INFO  [alembic.autogenerate.compare.tables] Detected added column 'livro.paginas'
INFO  [alembic.runtime.migration] Running upgrade 94fcd6644a04 -> b6d817a17739, livro ganha paginas

E a migração gerada é um arquivo Python versionado junto com o código:

def upgrade() -> None:
    op.add_column('livro', sa.Column('paginas', sa.Integer(), nullable=True))

def downgrade() -> None:
    op.drop_column('livro', 'paginas')
94fcd6644a04 -> b6d817a17739 (head), livro ganha paginas
<base> -> 94fcd6644a04, esquema inicial
Aviso--autogenerate é um rascunho, não uma resposta

Os comentários que o próprio Alembic escreve no arquivo — “auto generated by Alembic - please adjust!” — são para ser levados a sério. Ele não detecta renomeação (vê DROP mais ADD, e isso apaga dados), tem dificuldade com mudança de tipo, ignora índices em alguns dialetos e não sabe migrar os dados existentes. Toda migração autogerada precisa ser lida antes de ser aplicada, e uma que mexe em dado de produção precisa ser testada numa cópia.

E o downgrade merece o mesmo cuidado: ele existe, mas reverter uma migração que apagou coluna não devolve o conteúdo dela.

90.8 Quando não usar o ORM

Vale ser explícito, porque o ORM não é obrigatório nem sempre adequado:

  • Relatório e exportação: selecione colunas com o Core. Construir dez mil objetos para somar uma coluna é desperdício.
  • Carga em massa: insert() do Core com lista de dicionários, ou o COPY do PostgreSQL. O ORM tem bulk_save_objects, mas o Core é mais direto.
  • Consulta que o ORM deixa feia: CTE recursiva, função de janela, LATERAL, extensão específica do banco. Use sa.text() — sempre com parâmetros nomeados:
s.execute(sa.text("SELECT titulo, preco FROM livro WHERE preco > :minimo"),
          {"minimo": 150}).all()
  parametrizado: [('Fluent Python', 189), ('Effective Python', 159)]

Note o :minimo com o dicionário separado. sa.text() com f-string é injeção de SQL, e é o único jeito de reintroduzir num projeto com SQLAlchemy o problema que ele resolve de graça.

90.9 🐍 Jeito Pythônico

Estilo 2.0: select(), não session.query(). O antigo funciona e não é o caminho recomendado; select() é o mesmo objeto no Core e no ORM.

Mapped[T] e mapped_column() para que o verificador de tipos veja o modelo. Mapped[str] é NOT NULL; Mapped[str | None] permite nulo.

Numeric para dinheiro, nunca Float.

scalars para entidades, execute para colunas, scalar para valor único. Confundir devolve tupla onde você esperava objeto.

Estratégia de carga explícita. selectinload para coleções, joinedload para muitos-para-um. Medido: 21 consultas viraram 2.

lazy="raise" nos relacionamentos durante o desenvolvimento: transforma N+1 acidental em erro alto, em vez de lentidão silenciosa.

Uma sessão por pedido, com with ou dependência yield. Sessão global de módulo não é segura entre threads.

Não devolva objeto do ORM pela API. Converta para Pydantic dentro da sessão — resolve DetachedInstanceError e vazamento de campo de uma vez.

Migração é código versionado. --autogenerate produz rascunho: leia antes de aplicar, principalmente quando houver renomeação ou mudança de tipo.

sa.text() sempre com parâmetros nomeados. f-string em SQL é injeção, com ORM ou sem.

Para relatório, dispense o ORM. Colunas com o Core custam uma consulta e nenhum objeto.

90.11 Resumo

  • SQLAlchemy tem Core (expressões SQL, Engine, MetaData) e ORM (classes mapeadas, Session). O Core funciona sozinho e é a escolha certa para relatório e carga em massa.
  • Em 2.0, o mapeamento usa Mapped[T] e mapped_column(): Mapped[str] vira NOT NULL, Mapped[str | None] permite nulo, e o verificador de tipos entende o modelo.
  • select() é a interface de consulta, com scalars para entidades, execute para colunas e scalar para valor único. Valores vão parametrizados (:preco_1), o que elimina injeção por construção.
  • Numeric para dinheiro, nunca Float.
  • O N+1 é o padrão preguiçoso em ação: 21 consultas com 20 autores, 2 com selectinload, 1 selecionando colunas. lazy="raise" transforma o acidente em erro alto.
  • A Session é unidade de trabalho e mapa de identidade: você altera atributos e ela decide os UPDATE; dentro dela, uma linha é sempre o mesmo objeto Python.
  • Fora da sessão, o objeto fica destacado e qualquer carga preguiçosa levanta DetachedInstanceError. A cura boa é converter para Pydantic dentro da sessão.
  • Uma sessão por pedido, aberta e fechada por dependência com yield; nunca uma sessão global de módulo.
  • O modo assíncrono tem a mesma API com await e exige driver assíncrono — e proíbe carga preguiçosa, o que obriga a estratégia explícita.
  • Alembic versiona o esquema. --autogenerate detectou tabela nova e coluna nova, mas não detecta renomeação (propõe DROP mais ADD) nem migra dados: toda migração se lê antes de aplicar.
